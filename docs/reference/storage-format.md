# Storage format

This is the storage contract shared by the Go `evt` packages and the Rust `photon-evt` crate. Both
implementations read and write the same DynamoDB items, PostgreSQL rows, serialized JSON, and
stream envelopes, so services in either language can share one event log.

The golden fixtures in [`compat/fixtures/`](../../compat/fixtures) are the executable form of this
document. The Go implementation generates them, and both test suites check against them. If this
document and the fixtures disagree, the fixtures are what the code enforces. Fix whichever is wrong.
See [`compat/README.md`](https://github.com/photon-grove/evt/blob/main/compat/README.md) and
[ADR 0003](../adr/0003-rust-implementation-and-cross-language-compatibility.md).

The v0.9 core reshape
([ADR 0004](../adr/0004-core-reshape-multi-stream-transactions-and-outcomes.md)) adds the sections
[Read fences](#read-fences), [Command outcomes](#command-outcomes),
[Fence-aware retry](#fence-aware-retry), [Reserved namespaces](#reserved-namespaces),
[Feature marker](#feature-marker) and [Rebuild fence](#rebuild-fence), and changes the existing
[Writes](#writes) (multi-stream commits), [Metadata](#metadata) (metadata extensions) and
[Views](#views) (commit-wide projectors). Paragraphs marked `(v0.9)` describe behavior added in Go
evt v0.9.0 and `photon-evt` 0.2. A reader implementing the earlier format can skip them and the
sections they introduce. All of it is normative for both implementations.

Every stream has a head item at `sk = -1` that records its highest committed sequence
([ADR 0007](../adr/0007-per-stream-head-item.md)). A commit conditions on it for concurrency, and a
read fence is one check of it. [Stream heads](#stream-heads) has the normative format, and the
sections that describe a commit's actions, fences and failures follow it.

The journal ([ADR 0005](../adr/0005-rust-first-extensions-journal-and-lambda.md)) is the first
Rust-first extension: per-scope ordered delivery rows and counters written in the commit, with each
event's positions stored in its metadata. It adds no core item and changes no core shape. The
normative description is [Journal](#journal), and its fixture, `compat/fixtures/journal.json`, is
generated by the Rust implementation. Go doesn't implement it and refuses a table that declares it.

## Identifiers

| Name                    | Type   | Notes                                                                                  |
| ----------------------- | ------ | -------------------------------------------------------------------------------------- |
| entity ID               | string | One aggregate instance, one stream. The DynamoDB `pk` and PostgreSQL `entity_id`.      |
| entity type             | string | The aggregate type, such as `account`.                                                 |
| event sequence          | int64  | 1-based position in the stream. Contiguous: each commit continues from the last event. |
| event ID                | string | `{entityId}:{sequence}`, such as `acct-1:7`.                                           |
| event type              | string | The event kind, such as `account:deposited`.                                           |
| event version           | int64  | The payload schema version, starting at 1.                                             |
| snapshot sequence       | int64  | 1 for an entity's first snapshot, then incremented by one per snapshot.                |
| snapshot event sequence | int64  | The last event sequence folded into the snapshot.                                      |

## JSON encoding

Every JSON document in this format is produced by Go's `encoding/json` (`json.Marshal`). The Rust
crate reproduces it byte for byte (`photon_evt::json`):

- No insignificant whitespace and no trailing newline.
- Object keys appear in struct declaration order. Map keys are sorted by their encoded string, so
  integer keys sort as text (`10` before `2`). Rust maps with non-string keys use
  `photon_evt::json::go_key_order` to match.
- `<`, `>`, and `&` are escaped as `\u003c`, `\u003e`, and `\u0026`. U+2028 and U+2029 are escaped as
  `\u2028` and `\u2029`. Other non-ASCII text is written as UTF-8. Control characters, `"`, and `\` use the
  standard JSON escapes.
- Byte fields (`payload` in serialized events and snapshots) are standard, padded base64.
- Floating-point numbers are not normalized: Go and Rust format some floats differently. Payloads
  that must be identical across languages should use integers (for example, cents). The one
  exception is a stored rejection's `details`, whose numbers take a canonical text
  ([Rejections](#rejections)).

Decoding is lenient in both languages: missing fields and `null` decode to the zero value, and
unknown fields are ignored.

### Payloads

An event payload is the JSON encoding of the domain event, and a snapshot payload is the JSON
encoding of the aggregate state. Payload bytes are stored verbatim: as a DynamoDB string, as
PostgreSQL `bytea`, or base64-encoded inside serialized JSON. Neither implementation re-encodes a
stored payload except through an upcaster.

## Serialized event

The JSON form of one stored event. It is the `detail` of a stream envelope.

```json
{
  "id": "acct-1:1",
  "sequence": 1,
  "type": "account:opened",
  "version": 1,
  "entityId": "acct-1",
  "entityType": "account",
  "payload": "eyJvd25lciI6IkFkYSIsIm9wZW5lZEF0IjoiMjAyNi0wMS0wMlQwMzowNDowNS4xMjNaIn0=",
  "metadata": {
    "commandId": null,
    "trace": null,
    "origin": null,
    "address": null,
    "region": "us-west-2",
    "timestamp": "2026-10-12T00:00:00Z",
    "principalId": null,
    "causationId": null,
    "extensions": {},
    "commitId": "01JDXK7Q3W9B5N2M8P4R6TAVHY"
  }
}
```

Keys, in order: `id`, `sequence`, `type`, `version`, `entityId`, `entityType`, `payload` (base64),
`metadata` (an object carrying every key from [Metadata](#metadata): the example shows the
defaults a command with none of the optional metadata produces: `principalId` and `causationId`
`null`, `extensions` `{}`. The event's `commandId` is `null`, so its engine-generated `commitId`
is a ULID).

Go's `evt.SerializedEvent` owns this JSON encoding: `encoding/json` uses the same canonical
codec as the public `evt.MarshalEvent` / `evt.UnmarshalEvent` helpers. Encode-time metadata
defaults apply to the event envelope, not to standalone `evt.Metadata`, which has no JSON methods
and can be embedded in application DTOs without hiding sibling fields.

## Metadata

Every key is always written. Absent values are `null` (or `""` for `region` and `timestamp`).

```json
{
  "commandId": "cmd-0001",
  "trace": {
    "baggage": "tenant=example",
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "tracestate": "vendor=value"
  },
  "origin": { "source": "billing-api", "endpoint": "POST /accounts" },
  "address": "203.0.113.7",
  "region": "us-west-2",
  "timestamp": "2026-10-12T00:00:00Z",
  "principalId": "user:42",
  "causationId": "cmd-0001",
  "extensions": { "requestSource": "cli" },
  "commitId": "cmd-0001"
}
```

| Key           | Type           | Notes                                                                                  |
| ------------- | -------------- | -------------------------------------------------------------------------------------- |
| `commandId`   | string or null | The command that produced the event. Used to reject duplicate commands.                |
| `trace`       | object or null | W3C trace-context carrier. Keys sorted.                                                |
| `origin`      | object or null | `{"source": ..., "endpoint": ...}`, both strings.                                      |
| `address`     | string or null | Optional caller address. An empty address is written as `null`.                        |
| `region`      | string         | The region the command ran in.                                                         |
| `timestamp`   | string         | RFC 3339 UTC with second precision: `2026-01-02T03:04:05Z`.                            |
| `principalId` | string or null | Who issued the command (the caller's identity), for audit and per-principal checks.    |
| `causationId` | string or null | The command that caused this command. Defaults to `commandId` when unset (see below).  |
| `extensions`  | object         | String-keyed application-specific metadata. Keys sorted. `{}` when unset or empty.     |
| `commitId`    | string         | The commit that wrote the event. Set by the engine. Identical across the whole commit. |

The last four keys are new in v0.9 (ADR 0004) and are appended after the existing keys, so
stored events remain readable without upcasters: decoding is lenient in both languages. They are
always written:

- `principalId` is the caller's identity as a string, `null` when the command carries no principal.
- `causationId` is written with its effective value: the explicitly set causation, otherwise the
  `commandId`, otherwise `null`. Two events written by the same command therefore carry the same
  `causationId` even when neither set it explicitly.
- `extensions` is always an object, `{}` when the command carries no extensions. Values are strings.
  Keys are sorted by their encoded string, like every map.
- `commitId` identifies the commit that wrote the event: every event of one commit (across every
  stream a multi-stream commit touches) carries the same value, which is what lets a rebuild
  recover the commit's grouping ([Views](#views)). It is set by the engine, not the caller: the
  default is the command ID when the store records outcomes (outcomes require a command ID),
  otherwise a generated ULID, unique per commit.

A metadata object without the four keys (an event written before v0.9) decodes with `principalId`
and `causationId` `null`, `extensions` empty, and `commitId` empty. Such events replay as
single-event commits ([Views](#views)).

## Serialized snapshot

```json
{
  "entityType": "account",
  "entityID": "acct-1",
  "sequence": 2,
  "eventSequence": 10,
  "payload": "eyJvd25lciI6IkFkYSIsInN0YXR1cyI6Im9wZW4iLCJiYWxhbmNlQ2VudHMiOjEyMDB9"
}
```

Keys, in order: `entityType`, `entityID` (capital `ID`, unlike the event's `entityId`), `sequence`,
`eventSequence`, `payload` (base64).

## DynamoDB

One table holds every stream: a string partition key `pk` and a number sort key `sk`. Events use
`sk = 1, 2, 3, …`. The entity's single snapshot lives inline at `sk = 0`.

| Attribute    | Type | Event item                    | Snapshot item (`sk = 0`)        |
| ------------ | ---- | ----------------------------- | ------------------------------- |
| `pk`         | S    | entity ID                     | entity ID                       |
| `sk`         | N    | event sequence                | `0`                             |
| `type`       | S    | event type                    |                                 |
| `version`    | N    | event version                 |                                 |
| `entityType` | S    | entity type                   | entity type                     |
| `payload`    | S    | event payload JSON (raw text) | aggregate state JSON (raw text) |
| `metadata`   | S    | metadata JSON                 |                                 |
| `seq`        | N    |                               | snapshot sequence               |
| `eventSeq`   | N    |                               | snapshot event sequence         |
| `ttl`        | N    | optional, epoch seconds       | optional, epoch seconds         |

Each stream also has one head item at `sk = -1`, below the snapshot at `0` and the events from
`1`, holding only `head` (and `ttl` for retained types). It is concurrency metadata, not an event
or a snapshot ([Stream heads](#stream-heads)).

`ttl` is written only for entity types with a positive retention, on event items and on the
snapshot item alike. Its value is the commit time plus the retention, in whole Unix seconds,
rounded down after adding. Commit-wide view items never carry it (the view repository can
write one, see [Views](#views)). An event item with missing or empty
`metadata` is invalid. Readers ignore other attributes.

### Writes

A commit is one `TransactWriteItems` call, at most 100 actions. The actions appear in this order:

1. The feature-marker check (`SYSTEM#FEATURES`), present in every v0.9 commit
   ([Feature marker](#feature-marker)).
2. The rebuild-lock check (`SYSTEM#REBUILD`), present in every v0.9 commit
   ([Rebuild fence](#rebuild-fence)).
3. Projector operations, in projector declaration order. Within one projector, in emission order
   ([Views](#views)). In Go, the operations of the per-entity
   transaction groups come first, then those of the commit-wide projectors. A commit that
   carries projector operations must also write at least one event: views are projections of
   committed events, so operations with no backing event are refused with a typed error
   (`ProjectorOnlyCommit` in Go, `ProjectorWithoutEvents` in Rust) before any write, on every
   backend.
4. The written streams, in ascending entity-ID byte order. Each stream is one contiguous group,
   in this order:
   1. The head update, an `Update` of the stream's head item ([Stream heads](#stream-heads)).
   2. One put per event, in ascending sequence.
   3. The stream's snapshot put, when the commit writes one.

   The layout is interleaved by stream, not two phases: stream A's snapshot put comes before
   stream B's head update. Streams are never split across groups. There is no continuation check
   and no floor check: the head update owns both.

5. The fence checks for each read-only fenced stream in the read set, in ascending entity-ID
   byte order: one `ConditionCheck` of the stream's head item ([Read fences](#read-fences)). A
   stream that is both fenced and written contributes no fence check. Its head update supersedes
   it. The fence checks come after every written stream's group.
6. The outcome row put, when the store records command outcomes
   ([Command outcomes](#command-outcomes)).

Step 6 applies only when command outcomes are enabled for the store. The feature-marker check
(step 1) and the rebuild-lock check (step 2) are not optional: every commit in a v0.9 store
carries both, in this order, and a store that never declares features or runs a rebuild still
validates the marker against `attribute_not_exists(pk)` and the lock row against
`attribute_not_exists(pk)`. The order is pinned so fixtures byte-match across implementations: the shared compatibility scenarios record the action
order of every multi-stream and fenced transaction, and both languages assert it
([Compat scenarios](#compat-scenarios)).

For example, a commit that appends to streams `b` and `a` (declared in that order, `a` carrying
a snapshot) and fences the read-only streams `z` and `m` sends, with no outcome:

```text
1. ConditionCheck (SYSTEM#FEATURES, sk = 0)
2. ConditionCheck (SYSTEM#REBUILD, sk = 0)   attribute_not_exists(pk)
3. Update         (a, sk = -1)    a's head: head = n - 1 -> last        (a's first sequence n > 1)
4. Put            (a, sk = n)     event puts for a, ascending sequence
5. Put            (a, sk = 0)     a's snapshot put (sequence chain only)
6. Update         (b, sk = -1)    b's head: create, attribute_not_exists(head)
7. Put            (b, sk = 1)     event puts for b
8. ConditionCheck (m, sk = -1)    m's fence: head = :head
9. ConditionCheck (z, sk = -1)    z's fence: head = :head
```

Capacity. Every v0.9 commit carries the feature-marker check and the rebuild-lock check, and
every written stream carries one head update, whether it creates or appends. A single-stream commit
therefore holds at most 97 event/projector operations when it writes no snapshot, creating or
appending, and 96 when it also writes its snapshot. The budget counts exactly the actions a
commit emits. A commit that creates a stream and writes its first snapshot in the same commit costs one action
more than it did before head items, because the snapshot put used to replace the floor check.

Multi-stream commits (v0.9). A commit may append to any number of streams. Each written
stream keeps its event-put protection (`attribute_not_exists(sk)` on every event put), is protected
by its head update, and the sequence-contiguity rule applies per written stream. Nothing else about
the item shapes changes.

The item budget is the same for the single-aggregate shortcut and a multi-stream commit:

```text
items = Σ over written streams (events_s + 1 + [snapshot put in this commit])
                                                 event puts + head update + snapshot put
      + fenced read-only streams × 1             head check
      + 1                                        outcome put, when outcomes are enabled
      + 1                                        feature-marker check, always in v0.9 stores
      + 1                                        rebuild-lock check, always in v0.9 stores
      + projector puts and deletes
```

A commit whose budget exceeds 100 fails with a typed `CommitTooLarge` error before any write.
It is never split: splitting would break atomicity, because an error after an earlier chunk
commits would leave only part of the aggregate set updated.

The item count is not the only limit. `TransactWriteItems` also caps the whole request at
4,000,000 bytes in aggregate and every item at 400 KB, so a commit of individually valid items
(twenty 250 KB event items, say) would still be rejected by DynamoDB while PostgreSQL could
commit the same data. The preflight therefore covers bytes as well as items, and it runs in both
languages regardless of backend, so `CommitTooLarge` fires identically everywhere. The estimator
mirrors DynamoDB's item-size rules: an item's size is the sum over its attributes of the
attribute name's UTF-8 byte length plus the value's encoded byte length (strings as UTF-8,
numbers as their decimal text, binary as raw bytes), and the request's size is the sum of its
items' sizes. The preflight compares the estimates against 95% of the backend limits:
3,800,000 bytes in aggregate and 380,000 bytes for any single item, a 5% safety margin
for key-encoding and rounding differences. It covers every item the transaction carries: the
event puts, the snapshot items, the head updates, the projector operations, the fence checks, the
outcome row, and the control checks the commit emits (the feature-marker check and the
rebuild-lock check, each sized by its two key attributes). A head
update or fence check counts by the rule below for updates and checks: its key attributes plus
its expression strings, name placeholders and names, and attribute values (the number of a value
counts as its decimal text). A head update's `:t` is estimated with the commit's own `ttl`. A
commit over either byte budget fails with the same typed `CommitTooLarge` error before any write,
and is never split. A store never stages a snapshot over the per-item budget, so an aggregate whose
state outgrows it keeps committing without snapshots
([Oversized snapshots](#oversized-snapshots)).

The preflight counts projector operations on every backend that writes them. DynamoDB sizes
each projector item exactly: a put counts its item, and an update, delete, or condition check
counts its key attributes plus its expression strings, attribute-name placeholders (both the
placeholder and the name), and attribute values. A commit-wide view put therefore counts its five
attributes (its owner is the `entityID`. The owner condition on the put is not budgeted, like the
condition of any put), and a view delete counts its two key attributes plus its condition
expression string (`attribute_not_exists(pk) OR entityID = :owner`, or `attribute_exists(pk) AND
entityID = :owner`) and the `:owner` placeholder with the owner's bytes. The in-memory repository sizes view operations the same way. A PostgreSQL
repository counts each statement as one action sized by its SQL text. The bound parameters are
opaque, so the byte estimate is a lower bound while the action count is exact. Both languages'
PostgreSQL repositories execute commit-wide view operations and count them this way. A Go commit
that carries operations of a transaction group no backend-specific executor handles (a group
built for another storage type) is refused before any write with `ProjectorOperationsUnsupported`,
never silently dropped.

| Write                                       | Condition                                                        |
| ------------------------------------------- | ---------------------------------------------------------------- |
| head update, create (first sequence 1)      | `attribute_not_exists(head)`                                     |
| head update, append (first sequence > 1)    | `head = :prev` (`:prev` = first sequence − 1)                    |
| event put                                   | `attribute_not_exists(sk)`                                       |
| first snapshot put in a commit              | `attribute_not_exists(seq)`                                      |
| later snapshot put in a commit              | `seq = :seq`                                                     |
| snapshot put outside a commit               | `attribute_not_exists(eventSeq) OR eventSeq <= :new`             |
| head guard of a snapshot put outside a commit | `head >= :new` ([Stream Heads](#snapshot-writes-outside-a-commit)) |
| fenced stream, head 0                       | `attribute_not_exists(head)`                                     |
| fenced stream, head `:head` ≥ 1             | `head = :head`                                                   |
| outcome row put (v0.9)                  | `attribute_not_exists(pk)`                                       |
| feature-marker check (v0.9)             | `attribute_not_exists(pk) OR version = :v`                       |
| rebuild-lock check (v0.9)              | `attribute_not_exists(pk)`                                       |

`:seq` is the new snapshot sequence minus one, `:new` is the new `eventSeq`, and `:prev` and
`:last` are the stream's first sequence minus one and its last sequence in the commit. The first
snapshot must have sequence 1, and every later one the stored sequence plus one. A snapshot put
carries the sequence chain only: continuity and the floor are the head update's. The head
condition `head = first − 1` means events `1..first − 1` were committed, so nothing is skipped,
and a snapshot never covers more than the head ([Stream Heads](#invariants)), so the commit starts
above the snapshot's floor. A writer that loaded before another writer appended, snapshotted, and
compacted has a stale `:prev` and conflicts, because the other writer's commit raised the head.

`TransactWriteItems` reports one cancellation reason per item, indexed by the item's position in
the transaction, and both implementations classify a failed commit by those indexes (v0.9). Where
several items failed, the engine ranks them, identically on every backend
([Classification](#failure-classification)): the feature-marker check, the rebuild-lock check, the outcome
put, `StreamHeadDrift`, a sequence gap, then any other conflict.

- A fence-check failure means another writer moved the stream
  ([Read fences](#read-fences)). The classification keys off the failing item itself: a failed
  head update, event put, or snapshot condition is an ordinary conflict regardless of the
  commit's fences, and only a failed caller-stamped fence yields an immediate stale-fence rejection
  per its provenance, per [Fence-aware retry](#fence-aware-retry). Conflicts that keep
  re-preparing until the attempts run out end in a stale-fence rejection too.
- A feature-marker check failure means the feature set changed under the writer: the writer
  re-validates the feature set, then retries the commit ([Feature marker](#feature-marker)).
- A rebuild-lock check failure means the rebuild generation is unsettled: a rebuild holds the
  lock, or a force-release left its item in place of the lock. The commit fails with a
  `RebuildInProgress` error, retryable once a rebuild ends ([Rebuild fence](#rebuild-fence)).

The two control rows are store-level state, unrelated to the caller's decision: neither
failure is ever routed through the fence path: neither produces a stale-fence rejection, and
neither consumes fence-aware retry, even when the commit carries caller-stamped fences. On
PostgreSQL the same classification applies to the feature-marker `SELECT` and the rebuild-lock
assertion.

A failed outcome put is not one of these conflicts. It means another writer already recorded
an outcome for this command ID, and re-preparing the command as a conflict can never resolve it.
It outranks every other failed item except the feature-marker and rebuild-lock checks: when the same
cancellation also reports a failed head update, event put, or fence, the commit is classified as an
outcome conflict (`OutcomeConflict`), because the row is where the answer lives. PostgreSQL
reports the same classification for a unique violation (`23505`) on the outcomes table:
every attempt begins by reading the outcome row by command ID, and a commit whose outcome put
failed resolves through that row: the winner of the race has by then written it, so the next
attempt's read returns the stored outcome (same digest) or `IdempotencyKeyReuse` (different
digest). See [Command outcomes](#command-outcomes).

Both implementations reject a commit whose sequences are not contiguous for each entity (each one
more than the last), or start below 1, before writing anything. Sequence 0 is the DynamoDB snapshot
slot. Both languages reject an event whose ID is not `{entityId}:{sequence}`, with a typed invalid-commit
error before anything is written (Go `*InvalidCommitError`, Rust `Error::InvalidCommit`), because
DynamoDB does not store the ID and rebuilds it from the key on read, and an outcome receipt names
events by that ID. A Go commit that records no outcome tolerates an absent ID, as before v0.9. The head
update's condition and the snapshot's `eventSeq` both depend on that order, and loads reject a stream
with a gap. Every backend also enforces that a written stream continues from its stored head
(next section).

#### Continuity

A commit's first sequence for a stream must be the stream's stored head plus one, so no sequence is
ever skipped. The head is the stream's head item (and, equivalently, the larger of its highest event
and its snapshot's `eventSeq`: [Stream Heads](#invariants)). A first sequence above head plus one,
including any first sequence above 1 on a stream with no events, is refused with a typed
sequence-gap error (`SequenceGapError` in Go, `Error::SequenceGap` in Rust), which is a conflict
(reload and retry). A first sequence at or below the head is not a gap. It is an ordinary conflict.

- DynamoDB. The head update's condition is the check: `head = first − 1` (or
  `attribute_not_exists(head)` for a stream that starts at 1). There are no reads before the commit.
  A failed head update is told apart by the [failure-path probe](#failure-classification): a stored head
  below `first − 1` is a gap, anything else a conflict. Compaction never moves the head, so a
  writer whose load is still current never conflicts with a compaction.
- PostgreSQL. Under the per-entity advisory locks the commit runs the head statement of each
  written stream ([PostgreSQL](#postgresql)).
- In-memory. The same assertion, directly.

A transaction cancelled with a `ConditionalCheckFailed` reason on a head update, an event put, or
the snapshot put is an optimistic-concurrency conflict (unless the probe finds drift or a gap):
another writer committed the same sequence, moved the snapshot, or compacted past the commit.
The caller reloads and retries. A failed out-of-band snapshot condition is not an error. The newer
snapshot stays.

The languages report the other cancellations differently:

| Cancellation                                         | Go                                    | Rust                            |
| ---------------------------------------------------- | ------------------------------------- | ------------------------------- |
| head, event, or snapshot condition                   | `dynamo.ErrSnapshotRaceCondition`     | `Error::Conflict`               |
| projector operation condition                        | `*evt.ProjectorOperationError`, not retried (a legacy transaction group's `HandleError`) | `Error::ProjectorOperation`, not retried |
| `TransactionConflict`                                | classified as transient               | `Error::Conflict`, retried      |
| `ThrottlingError` or `ProvisionedThroughputExceeded` | classified as transient               | `Error::Transient`, retried     |

In Rust, a commit that times out, loses its response, or fails with an internal server error is
`Error::Backend`, not retried: the transaction may have been applied, and running the command again
could write its events twice. Reload the entity to find out.

### Reads

- Events: query `pk = :id AND sk > :after`, ascending, skipping `sk = 0`. Reads are strongly
  consistent by default. A negative `after` reads as 0, so no query ever returns the head item.
- Snapshot: get item `(pk, sk = 0)`.
- Entity heads (rebuilds and diagnostics only): scan `pk`, `sk`, and `eventSeq`, optionally
  filtered by `entityType`. An entity's head is the larger of its highest `sk` and its snapshot's
  `eventSeq`. A head item (`sk < 0`) contributes nothing. Enumeration, heads, and rebuild scans skip
  the reserved namespaces ([Reserved namespaces](#reserved-namespaces)) and every row below
  `sk = 1` that is not a snapshot ([Stream Heads](#event-writing-paths-reads-and-consumers)).

### Views

`ViewProjector` (Go `dynamo.NewViewProjector`, Rust `photon_evt::dynamodb::ViewProjector`) writes
one item per entity to a separate views table, in the same transaction as the events:

| Attribute    | Type | Value                     |
| ------------ | ---- | ------------------------- |
| `pk`         | S    | `{entityType}#{entityId}` |
| `sk`         | S    | `VIEW`                    |
| `entityID`   | S    | entity ID                 |
| `entityType` | S    | entity type               |
| `payload`    | S    | aggregate state JSON      |

View repository. The views table is also read and written outside the commit path by Go's
`dynamo.ViewRepository` and Rust's `DynamoViewRepository` (`photon_evt::ViewRepository`), over the
same five attributes, with one more: `ttl` (N, epoch seconds), written only when it is not zero.
The table has string `pk` and `sk` keys and a global secondary index `entityType-index` with hash
key `entityType` (no range key).

- A write is a `BatchWriteItem` put or delete with no condition (no owner check), chunked to 25
  requests, retrying `UnprocessedItems` (three attempts in all). A repeated `(pk, sk)` in one batch keeps its last row in Rust (Go leaves DynamoDB to refuse the request). An empty `sk` is stored as `VIEW`.
- A single-item read is a strongly consistent `GetItem` at `(pk, sk = VIEW)`. A batch read is a
  strongly consistent `BatchGetItem` chunked to 100 keys.
- A list is a `Query` (`pk = :pk` on the table, `entityType = :entityType` on the index). A
  partition list on the table is strongly consistent (`ConsistentRead: true`), so a page read after
  a commit returns sees that commit's rows. Go's `ViewRepository.WithConsistentRead(false)` and
  Rust's `DynamoViewRepository::with_consistent_read(false)` send `ConsistentRead: false` instead.
  An entity-type list on the index sends no `ConsistentRead` (a global secondary index is only
  eventually consistent). A bounded page sets `Limit`. With no limit the page is DynamoDB's
  response cap.
- A pagination cursor is the `LastEvaluatedKey`'s string attributes (`pk`, `sk`, and for the
  index `entityType`) as a JSON object, keys sorted and escaped like every other Go JSON, in
  padded base64url. Go and Rust cursors are interchangeable. An empty cursor is the first page.
- A reader treats an absent string attribute as empty, an absent `ttl` as zero, and a number in a
  string attribute as its text. A `ttl` that is not an integer is a corrupt row.

`compat/fixtures/views.json` pins the items, request keys and expressions, cursors, and the
payload bytes of the typed codec (`viewcodec.Codec` in Go, `ViewCodec` in Rust: the payload is the
`json.Marshal` of the value).

Commit-wide projectors (v0.9). A commit-wide projector is a pure function over the whole
commit: the engine calls it once for every commit that writes at least one event, after every
stream of the commit is staged and its snapshot decided, so a fence-aware retry derives its
operations again with the rest of the commit ([Re-preparing](#re-preparing)). It receives a
commit view and returns view operations in emission order. The view holds:

| Field      | Meaning                                                                                       |
| ---------- | --------------------------------------------------------------------------------------------- |
| `commitId` | The one `commitId` every event of the commit carries ([Metadata](#metadata)).                 |
| `streams`  | Every written stream, ascending by entity-ID bytes (the order of the transaction's groups).  |

and each stream holds its entity ID, its entity type, the commit's events for it in ascending
sequence (serialized: type, version, payload, metadata), and its state after the commit: the
JSON the aggregate's snapshot would carry. Which of these a projector is given depends on its
kind, below. Streams that were only read (fenced) are not in the
view. A command that writes no event (a plain rejection, an accepted no-op, an outcome-only
commit) runs no projector, and a rejection that [carries events](#rejections-that-carry-events)
projects them exactly like an accepted command's. The view carries no outcome context: a
rebuild regroups stored events by `commitId` and has no outcome row to read, so a row that
depended on the outcome's status could not be rebuilt.

Two kinds of projector, declared (v0.9). A projector states which entity types it reads
the *events* of (`History` in Go, `history` in Rust). The view it is given is what a rebuild of its
kind can give it again, and the declaration is enforced, not trusted:

- A current-state projector states none. It is given every written stream's entity ID, entity
  type, and state after the commit, and nothing else: no events and an empty `commitId`. A
  row it writes can depend only on the states the commit's streams reach, never on which commit
  produced them.
- A history-dependent projector states the entity types whose events it reads. It is given the
  `commitId`, and the events *and state* of the streams of those types only. Every other written
  stream is present by entity ID and entity type, with no events and no state: its history is not
  covered by the declaration, and may have been compacted.

Before the first commit that runs a history-dependent projector, the store durably adds its entity
types to the manifest's `historyDependent` set ([Feature marker](#feature-marker)). A repository
that cannot declare (Go `evt.HistoryDeclarer`, Rust `Repository::declare_history_dependent`)
refuses the commit with `HistoryDeclarationUnsupported` before any write, and so does a repository
whose feature-marker table does not match its events table. So `CompactBelow` refuses those types
in every process, whether or not it registered the projector.

Ownership (v0.9). The log keeps one commit order only: the sequence order of each stream.
Commit IDs and timestamps are not causal, so a replay cannot order two commits on different streams
that write the same row. Every operation of every projector therefore names the owner of
its row: a stream the commit wrote (`ViewOperation.Owner`, `owner`). The engine checks it before
any write (`InvalidViewOperation`: no owner, an owner the commit did not write, or, for a
history-dependent projector, an owner whose entity type the projector did not declare in `History`,
since its row is rebuilt from the events of the declared types alone). The repository stores the
owner as the row's `entityID` and conditions every write to the row on it, puts and deletes,
with or without a presence condition (see the conditions below), so a write by any other stream
fails the commit with `ProjectorOperation`/`ConditionalCheckFailed` when it is made.

A row's owner must never change. The writes to one row can be put back in order only while they
all come from commits that wrote the same stream, ordered by that stream's sequence. A key does
not change hands by a delete by one stream and a put by another: the delete leaves the row absent,
so the second owner's put would pass its condition live, and a replay, which has no order between
the two streams, would have to guess which came last. It refuses with `SharedViewKey` instead. To
reuse a key, keep the row with its owner and rewrite it with a tombstone payload (a tombstone
put), or give the key to a stream every claimant writes. Deleting a row is for the owner's own
end of life: a later put by the same owner is fine, by another is the handoff this rule forbids.

A projector's operations are appended to the commit in projector declaration order, each
projector's in its emission order, after the marker check and the rebuild-lock check and before the written streams
([Writes](#writes)). Operations are backend-neutral. Each is a put or a delete of one row at the
`pk`/`sk` the projector chooses, including partitions that do not name an entity, which is what
makes cross-entity read models atomic with the commit:

| Operation | Fields                                                        | Optional                                                    |
| --------- | ------------------------------------------------------------- | ----------------------------------------------------------- |
| put       | `pk`, `sk`, `owner`, `entityType`, `payload`                  | condition `absent` (the row must not exist), a mapped error |
| delete    | `pk`, `sk`, `owner`                                           | condition `present` (the row must exist), a mapped error    |

`owner` is written as the row's `entityID` attribute. `entityType` is informational (readers never
interpret it) and always written. `payload` is the view state JSON. A put overwrites the owner's
row unless it carries the `absent` condition, and a delete of an absent row succeeds unless it
carries the `present` condition. In either case, a row that exists and belongs to another owner
fails the operation. The mapped error is the projector's own error value for the case where the
operation's condition fails (a claim that is already taken, say). It is in-memory commit data and
is never stored. Commit-wide view items never carry `ttl`.

Stored as a DynamoDB item (the views table is the one the repository is configured with), a put
is a transaction `Put` of the item. Its condition is `attribute_not_exists(pk)` for `absent`, and
otherwise `attribute_not_exists(pk) OR entityID = :owner` with `:owner` bound to the owner:

```json
{
  "pk": "username-claims",
  "sk": "handle#ada",
  "entityID": "acct-1",
  "entityType": "account",
  "payload": "{\"status\":\"claimed\",\"accountId\":\"acct-1\"}"
}
```

A delete is a transaction `Delete` of the `(pk, sk)` key, with the condition
`attribute_exists(pk) AND entityID = :owner` for `present` and `attribute_not_exists(pk) OR
entityID = :owner` otherwise, with `:owner` bound to the owner. The row above is a commit-wide row at a `pk` outside any `{entityType}#{entityId}`
pattern, written in the same transaction as the events that produced it. The per-entity `VIEW`
row above remains the special case "one entity's events".

Engine checks (v0.9). Before any write, on every backend, the engine checks each
operation in order and returns the first failure as a typed error:

1. `InvalidViewOperation`: a `pk`, `sk`, or `owner` that is empty, or any text field (`pk`, `sk`,
   `owner`, and on a put `entityType` and `payload`) that is not valid UTF-8 or contains U+0000 (PostgreSQL cannot store
   it), so a commit has the same result on every backend.
2. `ViewKeyTooLong`: a `pk` over 2,048 UTF-8 bytes or an `sk` over 1,024 UTF-8 bytes
(DynamoDB's key limits) so a projector whose keys fit PostgreSQL but not DynamoDB fails
   identically on both backends instead of committing on one and raising a validation error on
   the other.
3. `DuplicateViewKey`: an operation whose `(pk, sk)` an earlier operation of the commit already
   targets, since DynamoDB would otherwise fail the whole transaction with an unclassified
   `ValidationException`.

An operation whose owner the commit did not write, or (history-dependent) whose owner's type is not
declared, is `InvalidViewOperation`, reported when the projector returns.

A commit that carries operations but no event is `ProjectorOnlyCommit` / `ProjectorWithoutEvents`
first ([Writes](#writes)). Operations count against `CommitTooLarge` ([Budget](#writes)) and are
sized as described there. A repository that was given view operations but has no place to write
them (no views table, no view writer) refuses the commit before any write with
`ViewsNotConfigured`, never dropping them. A repository that has not declared it writes view
operations at all (Go `evt.ViewWritingRepository`, Rust `Repository::writes_views`) (a custom
backend written before v0.9) is refused by the store before any write with `ViewsUnsupported`, and
Go's `CheckProjectorOperationsSupported` guard stays fail-closed for view operations.

Failure mapping (v0.9). A projector operation fails when its condition fails: or, on
PostgreSQL, when the database rejects its statement. The failure maps to a typed error that names
the projector (its name and its position in declaration order) and the operation (its
index among that projector's emitted operations, with its kind, `pk`, and `sk`), plus the
backend's reason: `ProjectorOperationError` in Go, `Error::ProjectorOperation` in Rust. When the
operation carried a mapped error, the typed error wraps it (`errors.Is` in Go, `source()` in
Rust), so the application matches its own error value. A projector operation failure is not a
conflict and not transient: re-preparing the command cannot fix it, so it is returned at once,
never retried, and records no outcome (internal failures write none). The reasons are:

| Backend    | Reason                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| DynamoDB   | The item's cancellation reason code: `ConditionalCheckFailed`, `ValidationError`, or `ItemCollectionSizeLimitExceeded`. |
| PostgreSQL | `ConditionalCheckFailed` for an `absent` put (a violation of the named `(pk, sk)` key constraint, `23505`), for any other put or `present` delete that affects no row, and for an unconditional delete that reports a row of another owner. Otherwise the SQLSTATE the database raised. |
| In-memory  | `ConditionalCheckFailed`.                                                                                |

Where several items of a cancelled DynamoDB transaction failed, the failure classification ranks
them ([Failure classification](#failure-classification)): the marker check, the rebuild-lock
check, the outcome put, `StreamHeadDrift`, a gap, any conflict on a written stream or a fence, and only then projector
operations: a projector condition is reported only when nothing ranked above it failed, and the
first failed projector operation in transaction order is the one named. PostgreSQL runs its
projector statements after the head statements and the event inserts
([PostgreSQL](#postgresql)), so a writer that lost a race fails on its head first, which is the
same order. A projector function that itself returns an error fails the command before any
write, as an internal failure (Go `*ProjectorError`, Rust `Error::Projector`).

Determinism (v0.9). A projector must be a pure function of its commit view: the same
view always yields the same operations, in the same order, byte for byte. It may not read a
clock, a random source, the environment, or the stores. It may not depend on the order of a hash
map's iteration. It may not remember anything between calls. This is what keeps views derived
state that can be wiped and rebuilt by replaying events: every row a projector writes must be a
projection of the events already committed, never a record of something that happened only
outside the event log, and a mutable decision, an externally observed signal, or an
accept-or-reject verdict is event-sourced first and projected second. A commit that carries
operations but no event is refused for the same reason. The engine does not police purity, but
the contract is testable: grouping stored events by `commitId` (see "Rebuilding a
history-dependent projector" below) and running the projector over each group, with the state each
stream had after that commit, must reproduce the operations the live commit produced, and replaying
them must reproduce the rows.

Commit boundaries (v0.9). The only durable record of which events belong to one
commit is the events' metadata: every event of a commit carries the same `commitId`
([Metadata](#metadata)), including the events a multi-stream commit writes to different streams.

Current-state rows (v0.9). A commit-wide projector produces current-state rows: every
row it puts is a deterministic function of that commit's events plus the post-commit aggregate
states (the state of each written stream after the commit) never of earlier commits' rows or
event history. A row encodes what the projection says _now_, not what happened once, so the same
rows can be produced again without replaying the events that preceded the commit.

Two kinds of commit-wide projector (v0.9). Every commit-wide projector declares which
of two kinds it is, and the declaration is durable: the entity types of history-dependent
projectors are recorded in the feature manifest's `historyDependent` set
([Feature marker](#feature-marker)), not in one process's registration:

- Current-state projectors (the default) compute rows from the current state of the
  aggregates they read. Their rebuild never replays history, and compaction is irrelevant to
  them: no event a compaction might delete is ever an input to their rebuilt rows.
- History-dependent projectors need the commit stream itself: an append-only feed, say.
  Their entity types are declared in the `historyDependent` set, which forbids compaction for
  them (below), and their rebuild replays every commit grouped by `commitId`.

State entry point (v0.9). *Not implemented in this release.* The design below is the target
for the rebuild ports. No interface or entry point for it exists in either language, and nothing
in the commit path uses it. Until it lands, Go rebuilds no durable view table of commit-wide
projectors: its in-memory replay of history-dependent projectors (`GroupCommits` and
`ReplayViews`) reproduces their rows, and a current-state projector's rows only with the caller
supplying each commit's post-commit state. Rust's `ProjectionRebuild` rebuilds the views table of
both kinds under the rebuild lock (see "The Rust projection rebuild" below), standing in for the
state entry point with one view per stream. The target: every commit-wide projector
implements a second entry point alongside the per-commit one: the state entry point, called with a lookup by stream ID over
the final state of every aggregate in scope and returning the projector's complete current row
set. "Final state" is what a load at the head returns: the snapshot plus the events after it,
for each stream. Because the entry point sees _all_ the final states at once, a row that combines
several aggregates' states is derived from the complete, consistent input, not from one stream's
snapshot: this is what keeps cross-entity rows reproducible when the commits that produced them
have been compacted away.

Rebuilding a current-state projector (v0.9): target design, not implemented. A wipe-and-rebuild never replays history
for one. It loads the final state of every aggregate of the entity types in scope, calls the
projector's state entry point once with the by-stream-ID lookup over all of them, deletes the
rows the projector owns, and writes the returned set. Ownership is declared at registration:
each commit-wide projector declares the key space it writes (for the per-entity `VIEW` row, the
`{entityType}#{entityId}` partitions of its entity types), which is the space the rebuild wipes
before writing. The result is a pure function of the final
states, so it is identical whether or not any prefix of the log was compacted: no seed over a
single stream's snapshot is involved, and a compacted multi-stream commit contributes exactly
what its streams' final states say. (A per-stream snapshot seed cannot do this (a row derived
from several aggregates is not a function of any one of their snapshots) which is why the entry
point takes the complete state.) Compaction never invalidates such a rebuild, and `CompactBelow`
never refuses these entity types.

The Rust projection rebuild (v0.9, `photon_evt::ProjectionRebuild`). It takes the rebuild lock
([Rebuild fence](#rebuild-fence)) for the whole run, so no commit lands and readers under the
epoch check are fenced while it reads the log. It writes through the guarded writer in batches of
at most 99 operations, renews the lease as it goes, and releases the lock at the end, which
settles the generation. Only streams of the aggregate types registered with it are read. It
computes every operation before the first write and refuses, before writing, a row two owners would
write (`SharedViewKey`), a key planned twice (`DuplicateViewKey`), and an operation too large for
any batch (`CommitTooLarge`); batches hold at most 99 operations within the commit byte budget.
Each operation is written without its condition or mapped error (a replay applies what the live
commits wrote), so a rebuild runs over existing rows and is idempotent. It does not wipe: rows no
projector produces any more stay until the caller deletes them. It needs strongly consistent reads
of the log, or a commit that landed just before the lock was taken can be missed. Given the
journal's configuration (`with_journal`), the same run also rebuilds the [journal](#journal): it
reads every event of the journal's entity types under the lock (each type read once, shared with
the history replay), derives the rows and counters as the journal's rebuild does, checks their keys
against the view rows (`SharedViewKey`, `DuplicateViewKey`), and writes them in the same guarded
batches, so the views and the journal move through one generation.

- A current-state projector runs once per stream of every registered type, over a view of that
  stream alone: its final state (the snapshot plus the events after it, so a compacted stream is
  seeded from its snapshot, the `StreamEntitiesFromSnapshots` enumeration), no events, and an
  empty `commitId`. This is the state entry point with one stream in scope. It reproduces every row
  whose owner's state alone determines it. A row that reads another stream's state from the same
  commit is recomputed from the one stream, so such a projector must not be rebuilt this way until
  the state entry point exists; a row owned by another stream fails the rebuild with
  `InvalidViewOperation` before anything is written.
- A history-dependent projector is replayed as the next paragraph specifies, from the events of
  the types the history-dependent projectors name; a commit's streams of other types, which a live
  view carries by ID and type only, are absent from the replayed view. The rows the replay leaves
  are written as puts, and a row the replay deleted last as a delete. A stream of those types whose history does not run from sequence 1 to its
  enumerated head fails the rebuild with `CompactionUncovered` before anything is written: an early
  part was compacted (`through` is the sequence before its first event), or, with retention, TTL
  deleted a tail while an earlier event and the snapshot remain (`through` is the head). TTL deletes
  lazily and in no order, so the remaining events alone cannot show that the tail is gone.

A run that acquired the lock from a settled generation and fails before attempting a write releases
the lock and leaves the rows as they were. Once a write was attempted (even one whose result is
unknown) a failure keeps the lock, because the rows may be half-written, until a retry takes over the
lapsed lease. A run that took over an expired lease, or acquired from a force-released generation,
starts from rows an earlier rebuild may have half-written, so it keeps the lock on any failure, a
failure before its own first write included: only a rebuild that completes settles that generation.
The run tells the cases apart by reading the generation just before it begins: the generation only
grows, so a lease exactly one above a settled generation read then was acquired from it.

Rebuilding a history-dependent projector (v0.9). A wipe-and-rebuild replays every
commit grouped by `commitId`: each group's events, ordered by stream ID bytewise then by
sequence (the same pinned order as the commit's transaction), form one `CommitView`, and the
projector runs once per group, exactly as it did at commit time, with the state each stream had
after that commit. The groups are applied in an order every stream agrees with: a commit that
wrote a stream's sequence 3 precedes the commit that wrote its sequence 4, for every stream (Go
`GroupCommits`, Rust `group_commits`. Commits that no stream relates come in the order of their
first event's stream ID bytes and sequence, which carries no meaning). Events whose commits cannot
be ordered that way (a cycle) are not a log this engine wrote and fail with `CommitOrder`. The
replay applies each operation to the rows, and refuses with `SharedViewKey` (Go
`ReplayViews`, Rust `replay_views`) when two operations of different owner streams touch one row,
because the final row would then depend on an order the log does not keep. Conditions are not
evaluated in a replay: it applies what the live commits wrote. Nothing may have deleted the
history, so compaction is forbidden for the entity types in the manifest's `historyDependent`
set, and the prohibition is durable ([Feature marker](#feature-marker)):

- `CompactBelow` reads the manifest (consistent read) and refuses an entity type in
  `historyDependent` with a typed `HistoryDependentProjection` error before deleting anything:
  in every process that opens the log, whether or not it registered the projector.
- A wipe-and-rebuild that finds such a stream already compacted fails with `CompactionUncovered`
  ([Compaction](#compaction)): the replay cannot stand in for the deleted commits.

Pre-v0.9 events, whose metadata has no `commitId`, replay as single-event commits (one
`CommitView` per event, in stream and sequence order) which reproduces the per-entity projector
behaviour an old log was written under. The events of a live `CommitView` carry the metadata a
stored event has (the command ID as the effective `causationId`), so a projector reads the same
metadata live and on replay.

## Read fences

A read-only stream in a transaction is fenced with one `ConditionCheck` on its head item (v0.9,
ADR 0007). The fence fails the commit when any writer has written the stream since the reader
saw it:

```text
ConditionCheck (pk, sk = -1)   head = :head                 :head ≥ 1
ConditionCheck (pk, sk = -1)   attribute_not_exists(head)   :head = 0 (the reader saw no events)
```

`:head` is the head the reader derived when it loaded the stream: the larger of the stream's
highest event sequence and its snapshot's `eventSeq` (invariant H4, [Stream Heads](#invariants)).
The check passes exactly when no commit has written the stream since. Because `head` only
increases (H1), a value that matches cannot have been reached by a different history, so the
compaction ABA does not exist: another writer could append `head + 1`, snapshot it, and compact
it away, but the head item still says `head + 1`, and a stale fence fails. There is no snapshot
companion, and no reader-side distinction between a stream that snapshots and one that does not. A
fenced stream that is also written contributes only its head update.

Retention conflicts with fences (v0.9). Fences are refused outright for entity types
that have retention, with a typed `RetentionConflict` error returned before any write: in both
languages, regardless of backend. The refusal is the union of two sources: the feature
manifest's durable `retention` set ([Feature marker](#feature-marker)), and the repository's own
retention configuration (`WithRetention` in Go, `with_retention` in Rust), which needs no I/O. The
durable set binds writers configured differently: an instance that configured no retention still
refuses fences for a type another instance declared. The local configuration protects a writer
whose retained types were never declared. It cannot protect any other process, so declare every
retained type in the marker as well. A retained stream's head item carries a `ttl` at least that of
every other item, so it survives the expiry of `head + 1`, but TTL deletion is lazy: a reader can
load a stream that has expired but is not yet deleted at head 1, the head item and event can then
expire, another writer can create the stream afresh and reach head 1, and `head = 1` passes for a
different incarnation. Closing that needs an incarnation token in the head item, so the refusal
stands. A retention-enabled stream is an append-only log with an expiring tail, not a fenced input.
A caller that needs a fenced read uses a stream without retention.

A `ConditionalCheckFailed` on a fence check is an optimistic-concurrency conflict (another writer
moved the stream) classified and retried like a head-update conflict, unless the failure-path
probe finds drift ([Classification](#failure-classification)). Whether the engine may re-prepare the
command depends on fence provenance. See [Fence-aware retry](#fence-aware-retry).

The conflict error carries the fenced stream ID, the head the transaction fenced it at, and the
fence's provenance (engine-filled or caller-stamped). It does not carry the transaction item
index: backends classify a failure internally by the cancellation reason's position (or the
failing statement), which is neither stable nor comparable across backends. In Go an
engine-filled fence conflict is classified transient (`policy.Classify` reports
`ClassTransient`) and matches `evt.IsOptimisticConflict`, so fence-aware retry re-prepares it
exactly like a head-update conflict. A caller-stamped one is not classified retryable. In Rust the
same split is `Error::is_retryable`.

Worked example. A transaction loads `claim#ada` at head 3 and fences it. The one item is:

```json
{
  "ConditionCheck": {
    "Key": { "pk": "claim#ada", "sk": -1 },
    "ConditionExpression": "head = :head",
    "ExpressionAttributeValues": { ":head": 3 }
  }
}
```

Fences are declared per read. A fence the caller fills from outside the engine is a
caller-stamped fence, and [Fence-aware retry](#fence-aware-retry) treats it differently from
an engine-filled one. Fence provenance is in-memory commit metadata, never stored.

## Command outcomes

A store with outcomes enabled (v0.9) records every command on a global, reserved
`command-outcome#<commandId>` stream: one row per command, written inside the commit transaction
alongside the events. The row is written once, in its final state, with a `Put` conditioned on
`attribute_not_exists(pk)`: a committed transaction never leaves a half-written outcome, and
there is no reserved-then-resolved intermediate state.

| Attribute   | Type | Outcome item (`pk = command-outcome#<id>`, `sk = 1`)                |
| ----------- | ---- | ------------------------------------------------------------------- |
| `pk`        | S    | `command-outcome#<commandId>`                                       |
| `sk`        | N    | `1`                                                                 |
| `status`    | S    | `accepted` or `rejected`, final at write time                       |
| `digest`    | S    | identity digest (below)                                             |
| `response`  | S    | standard padded base64 of the response bytes. Absent when none      |
| `events`    | S    | JSON array of event IDs the commit wrote. Absent when none          |
| `rejection` | S    | serialized rejection (below). Present only when `status = rejected` |
| `code`      | S    | the rejection code. Present only when `status = rejected`           |

The row has no snapshot, no `ttl`, and never compacts. `response` is base64 rather than raw text
so a response of arbitrary bytes round-trips exactly in both languages. The decoded bytes are the
stored response returned to a retried command. An empty response is no response: the attribute is
absent (PostgreSQL: `NULL`), and a reader returns no response bytes either way. `events` is a JSON array of event IDs
(`{entityId}:{sequence}` strings) encoded with the shared JSON rules, in ascending order by
stream ID bytewise, then by sequence: the same order as the transaction's event puts. A
rejected row lists events only when its rejection carries some
([Rejections that carry events](#rejections-that-carry-events)). A plain rejection has no `events`
attribute.

The stored values are bounded before any write: the `response` bytes and the encoded
`rejection` (the `rejection` attribute's JSON, its `message` and `details` included) are each
limited to 65536 bytes. A command that exceeds the bound fails with a typed
`OutcomeTooLarge` error returned before any write, in both languages, so a valid-looking command
behaves identically regardless of backend instead of exceeding DynamoDB's 400 KB item limit in
one and succeeding in the other. The bound keeps the outcome row (whose other attributes are
short) far under that item limit.

The command ID itself is bounded before any write: it must be at most 512 UTF-8 bytes.
A longer ID fails with a typed `CommandIdTooLong` error before any write (before the outcome key
`command-outcome#<id>` is even constructed) in both languages and on both backends, so a
command that PostgreSQL would accept is not rejected by DynamoDB's 2,048-byte partition-key
limit (the outcome `pk` is the 16-byte prefix plus the ID) while its events commit in the other.
The check precedes the response and rejection bounds, and a rejected ID writes nothing.

An accepted outcome with events and a stored response:

```json
{
  "pk": "command-outcome#cmd-0001",
  "sk": 1,
  "status": "accepted",
  "digest": "08f63bf06ef7167f79dda7f5de9307e1ffb626de015ecbc1c1482d1e67e5abd6",
  "response": "eyJhY2NvdW50SWQiOiJhY2N0LTEiLCJiYWxhbmNlQ2VudHMiOjB9",
  "events": "[\"acct-1:1\"]"
}
```

An accepted multi-stream outcome. The array's order is pinned: `claim#ada` sorts before
`profile#u-1`, so `claim#ada:1` comes first regardless of the order the command declared its
streams in. The digest is the [multi-stream digest example](#identity-digest) with the principal
`user:42` added:

```json
{
  "pk": "command-outcome#cmd-0004",
  "sk": 1,
  "status": "accepted",
  "digest": "56d01f5b9788b60e12a686e40807c28d9dfde802d82faf46888adda0acee7050",
  "events": "[\"claim#ada:1\",\"profile#u-1:1\"]"
}
```

An accepted no-op (a command that produced zero events, or an outcome-only commit) is the
same row without `events` (and without `response` when the command returned none). It is a
durable, observable outcome, not an error. An outcome-only commit writes only the outcome row
plus its checks: no event puts, no snapshot or head updates.

```json
{
  "pk": "command-outcome#cmd-0003",
  "sk": 1,
  "status": "accepted",
  "digest": "d24c7d5ce955a76c936a83e6eca2c3bc277d936c88a76460ed2d221e285a215a"
}
```

No `events` and no `response`. The `digest` here is `account:ping` on `acct-1` with an absent
payload (`lp("")` in the canonical bytes) and principal `user:42`.

A rejected outcome:

```json
{
  "pk": "command-outcome#cmd-0002",
  "sk": 1,
  "status": "rejected",
  "digest": "21c04bf818ab67db244dc184ae98197928309a4b3a3533acba69dacf992b6d79",
  "rejection": "{\"code\":\"username-taken\",\"message\":\"handle ada is taken\",\"details\":{\"handle\":\"ada\"}}",
  "code": "username-taken"
}
```

Every attempt reads the outcome row first. Before preparing each attempt (the first one
included) the engine gets `(command-outcome#<id>, sk = 1)`:

- Present with the same identity digest → return the stored outcome, including the stored
  response and events, and write nothing.
- Present with a different digest → `IdempotencyKeyReuse`.
- Absent → prepare and commit normally.

The same read is public as an outcome lookup by identity (Go `Store.ResolveCommand`, Rust
`Store::resolve_command`): the caller passes the command's identity and metadata, the engine
digests them with the store's digester and reads the row, and the branches are the same except
that an absent row is reported as not found and nothing is prepared or written. A
single-aggregate command's identity is the one its execution digests: its command type, its one
entity as the only target, and its payload (Go: the command value; Rust: its canonical payload).

Every outcome read (the pre-check above, the lookup, the race resolution after a failed outcome put,
and the ambiguous-write recovery below) is strongly consistent: on DynamoDB, `GetItem` with
`ConsistentRead = true`, regardless of the repository's read-consistency setting. An eventually
consistent read can return absent after the transaction applied, and the absent branch would then
re-execute a command that already committed. PostgreSQL's reads are transactionally consistent, so
the rule needs no flag there.

A commit whose outcome put fails its condition is resolved by the same rule on the next attempt,
never by re-preparing the command as a generic conflict ([Writes](#writes)): the losing writer's
next attempt reads the winner's row and returns whichever branch applies.

### Identity digest

The default digest is SHA-256 over the canonical bytes of the command's identity, computed
before the command executes. The identity is the caller's intent: what the request _is_
(its type, the streams it names, its payload, its principal) and nothing that depends on state. It
is never the streams a command ends up reading, fencing, or writing. A retry, a re-preparation
(see [Fence-aware retry](#fence-aware-retry)), a client retry that arrives after the command
landed, and an ambiguous-write recovery therefore all compute the same digest without running the
command, even when a re-preparation derives a different write set. A repeat with the same digest
returns the stored outcome. A repeat with a different digest is `IdempotencyKeyReuse`. The
canonical bytes are:

```text
"evt-cmd-digest-v1" || 0x00
|| lp(command type)
|| uint32-le(target count) || lp(target stream ID) …    target stream IDs, sorted by byte order, deduplicated
|| lp(canonical payload JSON)
|| lp(principal)

lp(x)  = uint32 little-endian byte length of x, followed by x
```

- `command type` is the command's type string.
- The target stream IDs are the streams the request itself names (an account, a profile) and
  are known from the request alone, before any state is read. They are deduplicated and sorted by
  byte order. Whether the command goes on to write them is not part of the identity. A command that
  names no stream, such as an outcome-only command, has none.
- The streams a command derives from state it reads are not targets and are not in the digest:
  a rename releases whichever handle the profile currently holds, so the streams it writes (the
  released claim, the new claim, the profile) come from the profile's state and can differ from one
  attempt to the next. A command may read, fence, and append to any stream, named or not. The
  outcome row's `events` lists every stream the commit wrote. Fenced (read-only) streams are not
  part of the digest either. A fenced conflict is caught by the fence checks themselves.
- `canonical payload JSON` is the command payload encoded by the shared JSON rules (the same
  encoder as every JSON document in this format). A command with no payload contributes the
  zero-length byte string (`lp("")`). A payload of JSON `null` encodes as the four bytes `null`.
  Because floats are not normalized across languages, a float-bearing payload can digest
  differently in Go and Rust and surface as `IdempotencyKeyReuse`. Digest-stable payloads use
  integers, as under [JSON encoding](#json-encoding).
- `principal` is the command metadata's `principalId` as a string, `""` when unset.
- The `evt-cmd-digest-v1` tag pins the encoding. A future change to the input bumps the tag, and
  old command IDs then digest differently, which surfaces as `IdempotencyKeyReuse` rather than a
  silently matched outcome.

Why the write set is not identity (v0.9). Putting the streams a command will write in the
digest cannot express a command whose write set depends on state. Declared up front, the set is a
guess. Derived from the state one attempt read, it changes when the command is re-prepared against
newer state, and the same request then looks like an `IdempotencyKeyReuse` or cannot be replayed.
Identity is therefore what the caller can state before reading anything, and the effects are
recorded where they belong, in the outcome row's `events` list, which a replay returns verbatim.
A replay needs nothing more: it returns the stored outcome without running the command, so no
effect goes unrecorded, and a digest that omits the write set cannot hide one.

There is no wire-format change. The canonical bytes above are unchanged, the tag stays
`evt-cmd-digest-v1`, and every existing digest vector in `compat/fixtures/outcomes.json` is
byte-for-byte what it was. What changed is the meaning of the stream list and the API around it:
an append to a stream outside the identity is no longer refused, the digest-input vectors' `streams`
key became `targets`, and the Go and Rust identity types renamed the field and builder
(`Targets` / `with_targets`) to say what belongs in them.

The caller's contract. Because the digest sees only the type, the targets, the payload, and
the principal, everything that distinguishes one request from another must be in the targets or
the payload. Two requests with the same command ID, type, targets, payload, and principal are the
same command: the second replays the first's stored outcome and never runs. A transfer whose
destination is chosen only inside the decision step (read from state or supplied out of band) is
therefore a trap: a request moving 10 to account B and a later request moving 10 to account C,
both named `account:transfer` on account A and sent with one command ID, digest equal, and the
second silently returns the first's outcome. Name the destination in the payload (or as a second
target) and the second is `IdempotencyKeyReuse`, which is what it is. State a command derives
(which handle a profile currently holds) belongs outside the identity. A choice the caller
makes belongs inside it.

A custom digester stores its own opaque string in `digest`. Ambiguous-write recovery compares
digests for equality only.

Worked example. Command type `account:open`, target stream `acct-1`, payload
`{"owner":"Ada"}`, principal `user:42`:

```text
evt-cmd-digest-v1 00
0c000000 6163636f756e743a6f70656e                    "account:open"
01000000 06000000 616363742d31                       1 target: "acct-1"
0f000000 7b226f776e6572223a22416461227d              '{"owner":"Ada"}'
07000000 757365723a3432                              "user:42"
```

78 bytes. SHA-256 is
`08f63bf06ef7167f79dda7f5de9307e1ffb626de015ecbc1c1482d1e67e5abd6`: the `digest` in the accepted
example above.

A multi-stream example: command type `claim-username`, target streams `claim#ada` and
`profile#u-1` (sorted byte order), payload `{"handle":"ada"}`, no principal:

```text
evt-cmd-digest-v1 00
0e000000 636c61696d2d757365726e616d65                "claim-username"
02000000 09000000 636c61696d23616461                 "claim#ada"
         0b000000 70726f66696c6523752d31             "profile#u-1"
10000000 7b2268616e646c65223a22616461227d            '{"handle":"ada"}'
00000000                                             ""
```

SHA-256 is `21c04bf818ab67db244dc184ae98197928309a4b3a3533acba69dacf992b6d79`: the `digest` in
the rejected example above.

A command whose write set comes from state: command type `profile:rename`, target stream
`profile#u-1`, payload `{"handle":"grace"}`, principal `user:42`. The request names the profile. The
claims it releases and takes (`claim#ada`, `claim#grace`) come from the profile's state and are not
in the bytes:

```text
evt-cmd-digest-v1 00
0e000000 70726f66696c653a72656e616d65                "profile:rename"
01000000 0b000000 70726f66696c6523752d31             1 target: "profile#u-1"
12000000 7b2268616e646c65223a226772616365227d        '{"handle":"grace"}'
07000000 757365723a3432                              "user:42"
```

88 bytes. SHA-256 is `00c8f624f35c034dcd5dee3924a4c78245a8b40aab4c1661db5948bf07b55ed0`. A first
attempt that read the profile at one handle and a re-preparation that reads it at another write
different streams under this one digest, and the accepted outcome lists what the committing
attempt wrote:

```json
{
  "pk": "command-outcome#cmd-0008",
  "sk": 1,
  "status": "accepted",
  "digest": "00c8f624f35c034dcd5dee3924a4c78245a8b40aab4c1661db5948bf07b55ed0",
  "events": "[\"claim#ada:2\",\"claim#grace:1\",\"profile#u-1:2\"]"
}
```

A store with outcomes enabled requires a command ID on every command. A missing ID is a
programmer error returned before the commit: no outcome row, no events. Stores built without
outcomes keep the older behavior. The older load-time duplicate window still runs after the
outcome read misses, and only for command IDs recorded by events with no outcome row (pre-v0.9
commands) that were replayed since the latest snapshot. One already folded into a snapshot or
compacted away is not detected (see the upgrade limitation under Loading and Duplicate Commands).
A command executed with outcomes enabled always has its row. The window check precedes
recording any outcome: an accepted one, a rejection (including the engine's stale-fence
rejection): a command whose ID a read stream already carries has run, so it is a duplicate and no
terminal outcome is written for it. A multi-stream command performs the outcome read first, before
any stream is read, fenced, or appended to, and a transaction whose read returned a stored outcome
is finished.

Outcome-only commits and their checks. An accepted no-op, a persisted rejection that carries
no events, and an outcome-only command write no event, snapshot, or head update. Their transaction is the
feature-marker check, the rebuild-lock check, then (for a multi-stream transaction) the fence checks for the streams it
read (engine-filled and caller-stamped, in the pinned order), then the outcome put, so a
rejection or a no-op is recorded only if the state it was decided on still holds: a moved
engine-filled fence is an ordinary retryable conflict and records nothing. The
single-aggregate shortcut reads one stream without a fence (it never fenced a read), so its
outcome-only commit is the marker check, the rebuild-lock check, and the outcome put. The one exception is the
stale-fence rejection ([Fence-aware retry](#fence-aware-retry)), which omits the failed fences.

### Ambiguous-write recovery

After an indeterminate commit error (a timeout, a lost connection, a cancelled call: the caller
cannot know whether the transaction applied, and it may still land), poll the outcome row by
command ID (get `(command-outcome#<id>, sk = 1)`, strongly consistent as above) with bounded
exponential backoff (50 ms doubling to 1 s) for a recovery window, 10 seconds by default:

- Present with the same identity digest → the commit won. Return the stored outcome,
  including the stored response and events.
- Present with a different digest → `IdempotencyKeyReuse`.
- Still absent when the window ends → a retryable ambiguous-write error. An absent row is never
  proof that the commit did not apply (a transaction can land after any single read, including
  one that was still executing when the caller gave up) so the engine never reports "not applied".

The digest is the pre-execution digest defined above, computed from the command's identity alone,
so recovery never re-prepares the command to compute it.

The engine performs this recovery itself. A row still absent at the end of the window (or a
recovery read that fails) is returned as an `AmbiguousWrite` error (Go `*AmbiguousWriteError`,
classified transient. Rust `Error::AmbiguousWrite`, retryable): the same command ID can run again,
because every attempt reads the outcome row first and every write is conditional, and the retry
finds the outcome if the first commit lands later. The recovery reads do not depend on the caller's
cancellation: a context cancelled while the commit was in flight is the usual reason the result is
unknown. Which failures are indeterminate:
a commit that carries an outcome and fails with a timeout, a lost connection or response, a dispatch
failure, a server fault, or a cancelled context, or a PostgreSQL connection dropped while `COMMIT`
was in flight. Backends classify these themselves (Go `*AmbiguousWriteError` from the backend, Rust
`Error::Indeterminate`), and only they are recovered. A definitive refusal (a cancelled transaction
with known reasons, throttling, a validation, missing-table, or authorization error, a database
error at statement or `COMMIT` time) is returned as is.

DynamoDB's `TransactionInProgressException` is one more indeterminate result (the transaction is
still running and may yet commit), recovered by the same polling.

A concurrent attempt with the same command ID and the same digest that loses the race for the
outcome row returns only the winner's stored outcome (its result or rejection, marked
replayed). The loser's own handler error and local decision are neither returned nor reachable
through the error chain.

Stored rows are validated. A row read back must have a known `status`, a non-empty `digest`, a
`rejection` (one complete JSON document whose `details` is an object or `null`, with trailing
data refused) with a non-empty code exactly when the status is `rejected` (and a `code` attribute
or column present exactly then, equal to it), well-formed event IDs (`{entityId}:{sequence}`
with a positive, canonical sequence, on a rejection too), and a decodable `response`. A malformed row is a typed
corruption error (Go `*CorruptOutcomeError`, Rust `Error::InvalidRecord`) and is never replayed as a
result. `compat/fixtures/outcomes.json` carries the malformed rows both languages must refuse.

A command ID must be valid UTF-8 (Go strings can hold arbitrary bytes, while Rust `String`s are UTF-8 by
construction), as must the command type, target stream IDs, and principal that feed the digest:
anything else is a typed invalid-argument error before the outcome or the aggregate is read. A
first execution returns the rejection in its stored (decoded) form, with the numbers in `details`
read back as their stored, canonical text ([Rejections](#rejections)), so its result equals a
replay's on every backend.

A digest returned by a digester (the default or a custom one) must be non-empty (and valid
UTF-8, since it is stored as a string): anything else is a programmer error returned before the
outcome or the aggregate is read and before the handler runs.

U+0000 is refused everywhere it cannot be stored. PostgreSQL `text` and `jsonb` cannot hold a
NUL character, DynamoDB and the in-memory repository can. So that the same call has the same result
on every backend, a command ID, a digest, and a rejection's `code`, `message`, and `details` (every
string and every object key, at any depth, whatever Go or Rust type the details hold: the encoded
JSON is what is checked) must not contain U+0000. The same holds for every other caller-supplied
string the engine persists on the command's events: the principal, causation, and commit IDs, the
trace carrier, the origin, the address, the region, the timestamp, the extension keys and values,
and, for a commit that records an outcome, the event IDs and types and the entity IDs and types of
its events, snapshots, and fences. Go also requires valid UTF-8 for all of them. Violations are the
typed invalid-argument error (Go `ErrInvalidArgument`, Rust `Error::InvalidArgument`), returned
before the outcome or the aggregate is read, before the handler runs for a command ID, a digest, or
metadata, and before any write for a rejection or an event. The recovery window bounds the whole
recovery, including a read that hangs: no read extends it past the window plus one second for the
last poll. Go derives each read's timeout from the recovery context. Rust races every read against
`Repository::deadline`, so a read that never resolves ends recovery as a retryable ambiguous write.
A malformed row found during recovery is corruption (Go `*CorruptOutcomeError`, Rust
`Error::InvalidRecord`), never masked as an ambiguous write. The response bytes in a returned
outcome are a copy: a caller that reuses its buffer cannot change them.

A stored accepted outcome that carries a `code` attribute at all, even an empty one, is corrupt: the
attribute exists exactly when the outcome carries a rejection.

`IdempotencyKeyReuse` is returned as an error and is not stored: the existing outcome row
belongs to the first command that claimed the ID, and nothing overwrites it.

### Rejections

A domain rejection (the aggregate's own refusal: not-found, invalid, conflict-by-rule) is a
durable rejected outcome (v0.9):

```text
Rejection { code, message, details }
```

The `rejection` attribute is the JSON encoding of this struct, keys in order `code`, `message`,
`details`. `code` and `message` are strings. `details` is a JSON object of application details,
or `null` when the rejection carries none. A rejected outcome is terminal for that digest: a
retried command replays the original rejection verbatim from the stored row.

Numbers in `details` are stored in a canonical text: the text PostgreSQL's `jsonb` prints, so
every backend returns the same number text and a replayed rejection decodes to the same value
(DynamoDB and the in-memory repository keep the stored text verbatim. `jsonb` keeps the numbers
but reorders keys and adds whitespace). Each encoder rewrites every number literal it wrote,
leaving strings and keys untouched:

- No exponent: the digits are written out in full (`1e+21` → `1000000000000000000000`,
  `1.5e-7` → `0.00000015`).
- The scale is the literal's own fraction digits minus its exponent, never fewer than zero, and
  trailing zeros within it are kept (`1.50e1` → `15.0`, `0.0010e2` → `0.10`, `1E2` → `100`,
  `100.00` → `100.00`).
- Zero has no sign (`-0` → `0`, `-0.0` → `0.0`).

A literal without an exponent is already canonical unless it is a negative zero, and a zero is `0`
(or `0.0`…) whatever its exponent. A number whose canonical text PostgreSQL's numeric type cannot
hold (more than 16383 digits after the decimal point, or more than 131072 significant digits
before it) is a typed invalid-argument error (Go `ErrInvalidArgument`, Rust
`Error::InvalidArgument`) on every backend, before any write. The 65536-byte bound applies to the
canonical form, so an exponent that expands a rejection past it is `OutcomeTooLarge`. The size is
computed before the text is built. When a rejection breaks more than one rule, the checks run in
this order and the first failure is returned: an invalid-UTF-8 code or message (Go only, since Rust
strings are UTF-8), U+0000 anywhere, an unstorable number, then the size bound. The rewrite fixes
the stored text, not the value a language formats before it: Go writes `float64(100)` as `100` and
Rust writes `100.0_f64` as `100.0`, and both are canonical, so keep floats integral in details that
must be byte-identical across languages. Rust parses floats exactly (serde_json's
`float_roundtrip`), so a float's canonical text reads back as the same `f64`. One whose canonical
text is an integer (for example `1.5e16`) reads back as an integer `Number`. `compat/fixtures/outcomes.json`
(`rejectionNumbers`) carries the literal-by-literal vectors, checked against PostgreSQL itself by
the PostgreSQL integration suite.

Only domain rejections are durable. Internal failures (event encoding errors, bad events,
storage errors) are returned as errors and write no outcome, so a retry after the underlying
bug is fixed starts clean. A domain rejection whose encoded form exceeds the 65536-byte outcome
bound ([Command outcomes](#command-outcomes)) writes no outcome either: the command fails with
`OutcomeTooLarge` before any write, and the caller retries once the rejection is smaller.
Engine-provided rejection codes are `not-found` and `bad-command`
(Go's former `NotFoundError`/`BadCommandError`), and the engine's own stale-fence rejection
([Fence-aware retry](#fence-aware-retry)). Domain error enums map onto rejection codes in each
language. Codes are free-form strings beyond the engine-provided ones.

A `stale-fence` rejection is durable even though the condition it records is transient: exactly
one outcome per command ID is the contract, so the old ID stays terminal and its rejection replays
verbatim. The engine records it in two cases, both persisted by the outcome-only transaction
pinned in [Fence-aware retry](#fence-aware-retry), which deliberately omits the failed fences: a
caller-stamped fence failed, or fence-aware retry ran out of attempts. The remedy is a new command
ID, decided on fresh state, not a retry of the old one.

### Rejections that carry events

A rejection may carry domain events (v0.9): the domain refuses the command, and the
history still has to record what happened. A proposal whose apply finds its base revision stale is
the example: the client gets a rejection, and the proposal stream gets an `apply-failed` event in
the same commit, so the aggregate leaves its "applicable" state and the audit trail is complete.
Without this the choices are to accept the command, which gives the client the wrong answer, or to
write the event outside the outcome commit, which is not atomic.

Declaration. Go marks the handler or `Prepare` error with `evt.RejectWithEvents`, and
`Transaction.RejectWithEvents` finishes a transaction that way. Rust implements
`Aggregate::rejection_events` for the single-aggregate path, and returns
`Decision::reject_with_events` (`Transaction::reject_with_events`) for a transaction. The events are
the ones a command of the same shape would commit if accepted: for a single-aggregate command, new
events on the command's own stream. For a transaction, events appended to any stream the command
read (a stream it did not read cannot be appended to). A rejection with no events is the plain
rejection, and the plain forms (`Reject`, `Decision::reject`) keep discarding staged events.

Commit. The events and the rejected outcome row are one atomic commit, with the transaction
shape of an accepted commit ([Writes](#writes)): the feature-marker check, the rebuild-lock check,
projector operations,
the written streams (head updates, event puts, snapshot puts), the fence checks of
the streams the command read but did not write, and the outcome put last. Every rule of an accepted
commit applies unchanged:

- Optimistic concurrency and continuity: a stale head is a conflict, and neither the events nor the
  row are written.
- A caller-stamped fence that went stale is the `stale-fence` rejection, without these events.
- Reserved streams (`SYSTEM#`, `command-outcome#`) are refused, and projector operations need an
  event behind them ([Views](#views)), so a rejection that carries operations but no events is
  `ProjectorOnlyCommitError` (Go) / `ProjectorWithoutEvents` (Rust).
- The commit budget counts every action, the outcome item included, so an oversized rejection is
  `CommitTooLarge` before any write ([Writes](#writes)).
- Snapshots, projectors, event metadata (`commitId`, `commandId`, `causationId`), and the
  U+0000/UTF-8 rules are those of an accepted commit.

The response is not stored with a rejection. The `rejection` attribute and its bound are unchanged.

The row. It is the rejected row of [Command outcomes](#command-outcomes) with an `events`
attribute listing the event IDs the commit wrote, in the same stream-ID-then-sequence order as an
accepted row's. The attribute order and encoding are unchanged. The rejection `code` still repeats
`rejection.code`. For `proposal#p-1`, which a command read at sequence 3 and recorded two failure
events on:

```json
{
  "pk": "command-outcome#cmd-0010",
  "sk": 1,
  "status": "rejected",
  "digest": "21c04bf818ab67db244dc184ae98197928309a4b3a3533acba69dacf992b6d79",
  "events": "[\"proposal#p-1:4\",\"proposal#p-1:5\"]",
  "rejection": "{\"code\":\"apply-conflict\",\"message\":\"the proposal was decided on a stale base\",\"details\":{\"base\":3}}",
  "code": "apply-conflict"
}
```

Replay. Like any outcome, a rejection with events is terminal for its digest. A retry reads
the row first, returns the stored rejection (marked replayed, with the stored event IDs), runs
nothing, and writes nothing, so the events are never applied twice. The command ID is not reusable
for another command (`IdempotencyKeyReuse`).

Fence-aware retry. A conflict while committing a rejection with events re-prepares the command
like any commit-time conflict ([Re-preparing](#re-preparing)): the handler runs again on freshly
loaded state, and it may reach a different decision, such as accepting, in which case no failure
event is written. Only the committing attempt writes anything. When the attempts run out, the
engine persists the `stale-fence` rejection by the [outcome-only
transaction](#the-outcome-only-transaction) without the caller's events: the decision they
describe was made on state that kept changing, so none of it is recorded.

Wire compatibility. The row layout does not change: `events` is an existing attribute, and a
rejected row without it (every plain rejection, including both `stale-fence` forms) is
byte-identical to what v0.9 pre-release writers produced. What changes is the validation of a
stored rejected row: it no longer must be free of event IDs, and its event IDs are held to the
same rules as an accepted row's. A reader that predates this rule refuses a rejected row that lists
events as corrupt (fail closed, never replayed as a result). Outcomes ship in v0.9, so no
released reader exists. `compat/fixtures/outcomes.json` pins the new row (`rejected with events`),
and `compat/scenarios.json` the `outcomes-rejection-events` scenario. The row that was a malformed
vector (`rejected with events`) is a valid one now.

## Fence-aware retry

A command on a store with outcomes runs under fence-aware retry (v0.9): a bounded number
of attempts, each of which decides the command from scratch against freshly loaded state, and a
persisted answer when the attempts run out. It replaces blind whole-command retry
(Rust's `Store::execute_with_retry`) as the default path for commands with
outcomes. In Go, the `policy` package remains for backend-level transient classification.

### Classification

A failed commit is classified by the transaction item that failed (DynamoDB reports one
cancellation reason per item, indexed by position, and PostgreSQL maps the statement that raised
the error) and only then by fence provenance:

- A failed head update, event put, or snapshot condition at commit time is
  an ordinary optimistic-concurrency
  conflict, re-prepared like any other ([Writes](#writes)) (the command runs again against a
  fresh load) whether or not the commit carried caller-stamped fences. A caller-stamped
  fence that still passed says nothing about this failure: the commit's own write set moved, the
  fences are beside the point, and persisting a rejection for it would be false. Re-preparation
  re-derives the engine-filled fences from the fresh load in the usual way.
- A failed engine-filled fence check is re-prepared: the engine loaded the fenced streams
  itself, so it can reload them and decide again.
- A failed caller-stamped fence check (a head the caller supplied) fails fast: the engine
  cannot know the caller's decision is still valid, so it neither re-prepares nor waits. It
  persists the command's outcome at once as a rejection with the reserved code `stale-fence` and
  the message `a caller-stamped fence went stale`. Only a caller-stamped fence that itself failed
  produces this form.
- A DynamoDB `TransactionConflict` (another transaction was writing the same items) is a conflict
  in both languages. A throttled commit and an ambiguous write whose outcome row never appeared
  are transient: they run again after a backoff, but they are not conflicts, so they never
  exhaust into a rejection ([Exhausted attempts](#exhausted-attempts)). So is a load that
  found a sequence gap (a compaction raced it, or events expired): reloading resolves the first
  case, so it is retried, but it says the read was inconsistent, not that a decision went stale,
  and a gap that persists is returned as an error rather than recorded against the command ID.
  Only a failed read that a multi-stream prepare step passes on counts: an error the step makes up
  itself, even one shaped like a conflict or a transient failure, is the step's own failure and is
  returned at once in both languages.
- `StreamHeadDrift` is neither. A stream whose head item disagrees with its log
  ([Classification](#failure-classification)) is not a conflict and not transient: the engine returns it at
  once, like any internal failure, records no outcome, and never turns it into a `stale-fence`
  rejection. Re-preparing cannot repair it, and a recorded rejection for it would be false.
- Control-row failures (the feature-marker and rebuild-lock checks) are classified separately
  ([Writes](#writes)) and never reach this rule, and a lost outcome put is resolved through the
  outcome row, never by re-preparing ([Command outcomes](#command-outcomes)). A marker failure
  re-validates and runs again. A rebuild-lock failure (`RebuildInProgress`) is transient: the
  command runs again after the backoff, because a rebuild may end in the meantime, and when the
  attempts run out the error is returned as it is: it
  never exhausts into a `stale-fence` rejection and records no outcome, so the same command ID
  can run again once the rebuild is over. Every other error (an invalid argument, a handler's own
  error, `IdempotencyKeyReuse`, a corrupt row) is returned at once.

### Re-preparing

Re-prepare means running the command's decision step again from scratch, against state read
after the failure:

1. Read the command's outcome row again (every attempt starts with the pre-check, so a competing
   writer that recorded the same command, or an attempt that landed after an ambiguous result, is
   found and returned instead of run again).
2. Load the aggregates again.
3. Run the handler (single aggregate) or the caller's prepare step (multi-stream) again.
4. Commit again.

Nothing carries over from a failed attempt: its staged events, snapshot, fences, and projector
operations are discarded, and only the attempt that commits writes anything. The handler or
prepare step can therefore run several times for one command and must be safe to repeat. External
side effects it causes must be idempotent. In Go the entity the caller supplied is reset before each
re-preparation: its exported fields (the state a snapshot persists) are restored from a deep copy,
so events a failed attempt applied are not counted again, and its unexported fields are restored
shallowly, so an unexported map, slice, or pointer keeps what the failed attempt put in it. Keep
state that `Apply` changes in exported fields. The command value is reused by every attempt, so a
handler must not mutate it. An entity the engine cannot reset (not a pointer to a struct) is
attempted once and a conflict is returned as an error. Rust loads a fresh aggregate for every
attempt and clones the command.

The write set may change between attempts. The streams a command reads and writes come from
state, so a re-preparation can derive different ones: a rename that found the handle `ada` on the
first attempt and `ada2` on the second releases a different claim stream. That is one command: its
identity is the request's intent ([Identity digest](#identity-digest)), computed once before
any attempt and kept (never recomputed from the live command or metadata), so the digest is the
same on every attempt, on a client retry that arrives after the
command landed, and in a recovery read. The outcome row records the streams the committing attempt
wrote.

### Policy

The attempts are bounded and spaced by a policy that is configurable per store and has the same
defaults in both languages (`compat/fixtures/outcomes.json` pins them, and both implementations
assert them):

| Setting      | Default | Meaning                                                                    |
| ------------ | ------- | -------------------------------------------------------------------------- |
| Max attempts | 5       | Attempts in total, the first included. A value below 1 means 1.            |
| Base delay   | 25 ms   | The delay before the first retry, before jitter.                           |
| Max delay    | 1 s     | The upper bound for any delay.                                             |
| Deadline     | none    | Optional bound on the whole command (below).                               |

Unset fields take the defaults in both languages: a policy that only sets the attempts still backs
off and jitters. Waiting is switched off explicitly (`RetryPolicy::immediate` in Rust,
`snapshots.ImmediateRetryPolicy` or `Immediate: true` in Go), for tests.

The delay before retry _n_ (starting at 0) is `min(base × 2ⁿ, max)`, with jitter taking it
anywhere in `[delay / 2, delay]`, so writers that conflicted together do not retry together.
There is no wait after the last attempt. An optional deadline bounds the whole command: no
attempt starts once the deadline has elapsed since the first began, and no wait is taken that
would end past it (an attempt already running is not interrupted. Use the context or the
backend's timeouts). Hitting the deadline is treated as exhausted attempts, so a conflict is
recorded and a transient failure is returned. Go configures it with `snapshots.RetryPolicy` and
`Store.WithRetry` (a `Sleep` function and a `Jitter` function are injectable, and the wait ends
with the context's error if the context ends). Rust with `RetryPolicy` and
`OutcomeConfig::with_retry`, waiting on the repository's timer (`Repository::backoff`, the timer
ambiguous-write recovery already uses). The deadline is checked between attempts against the
system clock in both languages (`RetryPolicy.Deadline` in Go, `RetryPolicy::with_deadline` in
Rust). A caller that wants to own the loop uses the lower-level
calls (`BeginCommand`/`Complete`/`Reject` in Go, `begin_command`/`commit_with_outcome`/`reject`
in Rust) which attempt once and return an engine-filled conflict as an error.

Worst-case latency. A command takes at most the attempts, the waits between them, and any
recovery windows. With the defaults the waits are at most 25, 50, 100, and 200 ms, about 0.4 s in
total, so a burst of `TransactionConflict` on a hot key exhausts into a `stale-fence` rejection in
well under a second. An ambiguous write whose row never appears costs a full recovery window
([Ambiguous-write recovery](#ambiguous-write-recovery), 10 s plus up to a second of grace) per
attempt, so five attempts can take about a minute. Set a deadline, a shorter recovery window, or
fewer attempts to bound it.

### Exhausted attempts

When the last attempt also ends in a conflict, the engine persists a `stale-fence` rejection as the
command's outcome instead of returning the conflict, so a replay of the command ID gets the same
answer. Its shape is pinned in both languages: the code is `stale-fence`, the message is
`the state this command was decided on kept changing; retries were exhausted`, and `details` is
`{"attempts": N}` with `N` the number of attempts made, an integer so both languages store the same
bytes:

```json
{
  "pk": "command-outcome#cmd-0009",
  "sk": 1,
  "status": "rejected",
  "digest": "00c8f624f35c034dcd5dee3924a4c78245a8b40aab4c1661db5948bf07b55ed0",
  "rejection": "{\"code\":\"stale-fence\",\"message\":\"the state this command was decided on kept changing; retries were exhausted\",\"details\":{\"attempts\":5}}",
  "code": "stale-fence"
}
```

Only a conflict exhausts into a rejection. When attempts run out on a transient failure that is
not a conflict (throttling, an ambiguous write whose row never appeared), nothing says the state
went stale, so the error is returned and no rejection is recorded. The same command ID can run
again.

Although a stale fence is transient by nature, the rejection is a durable, terminal outcome
(exactly one outcome per command ID is the contract), so the remedy is not a retry of the same
command: the caller re-reads, re-decides, and submits a new command ID. The old ID replays its
stored `stale-fence` rejection verbatim, like any rejected outcome, and the same ID with another
identity is `IdempotencyKeyReuse`.

### The outcome-only transaction

The rejection is persisted by an outcome-only transaction that carries none of the failed
commit's other items: no fences (they are stale by definition), no event puts, no snapshot or
head updates, no projector operations. Like every attempt, it begins with the outcome pre-check
read. On DynamoDB its item list is exactly:

```text
1. ConditionCheck (SYSTEM#FEATURES, sk = 0)   the feature-marker check, as in every commit
2. ConditionCheck (SYSTEM#REBUILD, sk = 0)    the rebuild-lock check, as in every commit
3. Put (command-outcome#<id>, sk = 1)         the rejected outcome, attribute_not_exists(pk)
```

On PostgreSQL the same shape is the feature-marker `SELECT`, the rebuild-lock assertion, and the
outcome `INSERT`, inside one transaction. If one of its two control checks fails, the ordinary
control-row classification applies ([Writes](#writes)): a feature-marker failure re-validates and
retries the rejection write, and a rebuild-lock failure is `RebuildInProgress`, retried after the
rebuild: neither turns the pending rejection into something else. If the outcome put loses its
condition, the standard
resolution applies: the next read of the row returns the winner's outcome (same digest) or
`IdempotencyKeyReuse` (different digest) ([Command outcomes](#command-outcomes)). A persisted
`stale-fence` row for a caller-stamped fence: command `account:rename` on `acct-1`, payload
`{"name":"Grace"}`, principal `user:42`, whose caller-stamped fence on `referral#r-3` at head 2
went stale before the commit:

```json
{
  "pk": "command-outcome#cmd-0005",
  "sk": 1,
  "status": "rejected",
  "digest": "ba4a6a859dcf103a00261515d7e309b31e8f07ca21732a4b7872b7fdebb92c1b",
  "rejection": "{\"code\":\"stale-fence\",\"message\":\"a caller-stamped fence went stale\",\"details\":null}",
  "code": "stale-fence"
}
```

The command never wrote. The engine persisted the rejection instead of retrying it.

The same rule covers the outcome put itself: an attempt whose outcome put lost a race is never
re-prepared as a generic conflict. The next attempt's outcome pre-check resolves it: the
winner's row returns the stored outcome (same digest) or `IdempotencyKeyReuse` (different digest)
([Command outcomes](#command-outcomes)).

Fence provenance (engine-filled vs caller-stamped) is in-memory commit metadata, not stored. The
only stored trace of fence-aware retry is the exhausted rejection above, which is an ordinary
outcome row, so there is no wire-format change beyond the pinned message and details of that
rejection. The outcome-only transaction never carries a caller's events, even when the command
that failed was a [rejection with events](#rejections-that-carry-events).

## Reserved namespaces

Two partition prefixes are reserved for engine-managed rows (v0.9): `SYSTEM#` (the feature
marker, the rebuild fence) and `command-outcome#` (outcomes). Matching is a case-sensitive byte
prefix on `pk`.

- Enumeration, entity heads, and rebuild scans skip every partition whose `pk` begins with a
  reserved prefix. Engine-managed rows are not ordinary aggregates and never compact.
- Explicit reads by entity ID (`GetEvents`, `GetLatestEvents`, `GetRecentEvents` / `latest(n)`,
  and `GetSnapshot`) do not filter reserved prefixes. Legacy streams and their snapshots remain
  readable for migration. Only enumeration, heads, and rebuild scans hide them.
- Every entity-addressed write path refuses an entity ID that begins with a reserved prefix,
  before any request, with a typed `ReservedEntityId` error: commits (multi-stream included:
  one reserved stream fails the whole commit), out-of-band snapshot writes (`PutSnapshot`),
  snapshot writes by a rebuild's seeding, and `CompactBelow` (which writes no new rows but is
  refused all the same, so the engine never touches a reserved stream). Commit-time-only refusal
  is not enough: an out-of-band snapshot put at `(SYSTEM#FEATURES, sk = 0)` passes its
  `attribute_not_exists(eventSeq) OR eventSeq <= :new` condition against an engine row (which
  has no `eventSeq`) and would overwrite the feature marker or the rebuild lock.
- Entity IDs were never restricted before, so a pre-existing stream such as `SYSTEM#account`
  would become silently invisible to enumeration, heads, and rebuild after upgrading. `evt-doctor`
  reports pre-existing streams whose IDs fall in a reserved namespace (on DynamoDB by scanning
  the table, on PostgreSQL with the queries below against the configured events and snapshots
  tables) and the upgrade note requires renaming (migrating) such streams before enabling the
  v0.9 features. Real stored data is never silently skipped.

  ```sql
  SELECT DISTINCT entity_id FROM evt_events
  WHERE entity_id LIKE 'SYSTEM#%' OR entity_id LIKE 'command-outcome#%';

  SELECT entity_id FROM evt_snapshots
  WHERE entity_id LIKE 'SYSTEM#%' OR entity_id LIKE 'command-outcome#%';
  ```

  `evt_events` and `evt_snapshots` stand for the configured table names. `evt-doctor` runs the
  same two queries and reports every ID they return. The upgrade procedure migrates those streams
  to non-reserved IDs before the v0.9 features are enabled.

### latest(n)

`latest(n)` is a bounded, newest-first read of a stream's last `n` events (descending), for
"recent activity" reads that must not replay a long stream. No item shape changes.

- DynamoDB: query `pk = :id AND sk > :zero`, `ScanIndexForward = false`, `Limit = min(n, 100)`. The `sk > 0`
  key condition excludes the snapshot item, so the result is the `n` highest event sequences,
  descending.
- PostgreSQL: `SELECT … FROM evt_events WHERE entity_id = $1 ORDER BY sequence DESC LIMIT $2`.

`n < 1` is a programmer error returned before any request, in both languages: nothing is read.
The result is at most `n` events: DynamoDB uses bounded pages and follows `LastEvaluatedKey`
until it has collected `n` items or the stream runs out, including when large items close a page
early. Initial buffer allocation is bounded by a page or the available events, not by an
arbitrarily large `n`. PostgreSQL's `LIMIT n` returns the same at-most-`n` window in one statement.

## Feature marker

A feature marker is created from its repository and bound to both its client handle and events
table at construction. Marker reads and transactional checks must use that same client and table.
Matching table names alone do not identify a physical log. Attaching a marker for another client
or table is a typed configuration error. Subsequent writes (including snapshots and compaction)
must fail with a typed mismatch error if the repository no longer matches the binding. Rust
repositories own marker access directly rather than accepting a separately constructed marker.

A store declares the extensions it uses on a single `SYSTEM#FEATURES` marker row (v0.9). Any
writer that does not support a declared feature refuses to write to the table.

| Attribute          | Type | Feature-marker item (`pk = SYSTEM#FEATURES`, `sk = 0`)                                        |
| ------------------ | ---- | --------------------------------------------------------------------------------------------- |
| `pk`               | S    | `SYSTEM#FEATURES`                                                                             |
| `sk`               | N    | `0`                                                                                           |
| `version`          | N    | bumped on every change to the manifest                                                        |
| `features`         | S    | JSON object mapping declared feature name → its stored-format version (a number), keys sorted |
| `historyDependent` | S    | JSON array of entity types whose projectors are history-dependent, sorted. Absent when empty  |
| `retention`        | S    | JSON array of entity types with retention (TTL), sorted. Absent when empty                    |

```json
{
  "pk": "SYSTEM#FEATURES",
  "sk": 0,
  "version": 3,
  "features": "{\"journal\":1,\"journal-compaction\":1}",
  "historyDependent": "[\"audit-feed\"]",
  "retention": "[\"session\"]"
}
```

The manifest has three parts. The `features` map declares extensions by name. Each maps to the
stored-format version of that feature, a number starting at 1: the features this spec defines
are `journal` and `journal-compaction` (the Rust-first extensions, ADR 0005), both at format
version 1, and `stream-heads` (ADR 0007), which every writer models and requires: a store
declares it before a writer writes, by an explicit initialization or by a lazily initializing writer
([Stream Heads](#required-feature)). `photon-evt` models
`journal` and `journal-compaction` at format version 1 when built with its `journal` cargo feature.
It declares `journal` with the first journaled commit ([Journal](#feature-marker-and-history)) and
`journal-compaction` with the first compaction lease ([Compaction](#journal-compaction)). A
fourth, `postgres-views` (format version 1, `photon-evt` 0.3, ADR 0008), records that a
PostgreSQL store's commit-wide views live in its evt-owned [views table](#postgresql-views-table).
Rust models it (it is in `SUPPORTED_FEATURES`), and a Rust PostgreSQL repository without the views
table refuses a store that declares it with `UnsupportedFeature`, on commits, snapshot writes,
compaction and rebuild view writes. Go does not model it, so a Go writer refuses the store too. The `historyDependent` set declares the entity types whose commit-wide projectors are
history-dependent ([Views](#views)), compaction is forbidden for them. The `retention` set
declares the entity types configured with retention (a positive `ttl`), fences are refused for
them ([Read fences](#read-fences)). Both sets are JSON arrays of entity-type names, sorted and deduplicated,
encoded with the shared JSON rules, stored as strings. An absent attribute is an empty set. Both
declarations are durable, shared state, not per-process registration: every writer and
maintenance tool that opens the log observes the same sets, which is what makes the compaction
and fence refusals hold across independently configured instances.

A writer may commit only if it supports every declared `(name, formatVersion)` pair: it
models the feature and reads and writes its stored format at exactly the declared version. A
writer that encounters a pair it does not support reads the feature set and refuses. The
per-feature version is what makes a format change detectable: bumping `journal` to `2` in the map
re-fails every older writer's revalidation, where a manifest of bare names would look unchanged
to a writer that already models `journal` at version 1.

The row is declared by the writer that first uses a feature, and updated, with a `version` bump,
by every later change to the manifest: adding a feature, bumping a feature's format version
when its stored format changes, or adding or removing an entity type from either set. Changing a
set is a declaration in the same protocol and re-fails every writer cached at the old `version`,
exactly as a feature change does.

Every commit on a v0.9 store includes one `ConditionCheck` on
`(SYSTEM#FEATURES, sk = 0)`: unconditional, not opt-in: the writer that most needs the refusal
is one that does not know a declared extension, and it cannot be relied on to have switched
enforcement on. The check is cheap when no features are declared (`attribute_not_exists(pk)`
passes), and it is a mandatory transaction item ([Writes](#writes)):

```text
ConditionExpression: attribute_not_exists(pk) OR version = :v
```

`:v` is the version the writer validated. A writer validates the feature set once, at first
write, and caches the version it validated: a table with no marker validates against
`attribute_not_exists(pk)` (cached as "no marker"), and a marker at version `v` validates against
`version = :v`. A declaration bumps `version` in the same conditional write that updates the
feature set, so every writer whose commits condition on the old version fails and re-validates.
At re-validation an unsupported writer reads the feature set, sees a `(name, formatVersion)` pair
it does not support, and refuses. The check costs one transaction item per commit
([Writes](#writes)). Standalone snapshot writes follow the same refusal protocol atomically:
DynamoDB includes the marker check and snapshot put in one transaction. PostgreSQL validates
under the shared feature advisory lock held through the snapshot-write transaction. Declaration
invalidates cached validation: declaring a feature is not proof that the declaring writer supports it.
Validation and per-commit condition construction use one locked cache snapshot, so concurrent
declarations cannot leave a commit with an unvalidated condition. PostgreSQL checks for a missing
feature relation with `to_regclass` before selecting it: a pre-marker log declares nothing, and
its transaction remains usable. Schema setup in both languages serializes DDL under
`pg_advisory_xact_lock(1702261762, hashtext(events_table))` to avoid catalog races on startup.

The declaration itself is a conditional write. Creating the row asserts `attribute_not_exists(pk)`
and writes `version = 1`. Updating it asserts `version = :observed`, writes the merged feature
map with sorted keys, and sets `version = :observed + 1`: each declaration transaction adds
exactly one to `version`, no matter how many features it adds or bumps. (One row per feature with
distinct sort keys could not do this: adding a feature would neither change an already-validated
row nor fail a condition against another key.)

Durable refusals read the manifest, not local configuration. Both set-backed refusals consult
the row itself, so they hold for every process that opens the log:

- `CompactBelow` first validates every declared feature/version pair against the writer's
  supported set, refusing an unsupported pair with `UnsupportedFeature` before deleting anything.
  It also reads `historyDependent` (on DynamoDB with `ConsistentRead = true`, regardless
  of the repository's read-consistency setting, so the check cannot miss a just-written set) and
  refuses an entity whose type appears in the set with a typed `HistoryDependentProjection` error
  before deleting anything ([Views](#views)). A maintenance tool that never registered the
  projector refuses all the same. PostgreSQL holds the shared feature advisory lock across
  validation and all deletes in one transaction. DynamoDB deletes in transactions of at most
  99 events plus a check on the observed marker (`version = :observed`, or
  `attribute_not_exists(pk)` when absent). A failed check re-reads and re-validates before retrying.
  This is per-batch fencing, not a lease over the entire DynamoDB compaction. A
  history-dependent declaration racing an in-progress multi-batch compaction can stop later
  batches but cannot roll back the already committed prefix, leaving a partially compacted
  stream. A history-dependent rebuild then reports `CompactionUncovered`, rather than silently
  replaying incomplete history. History dependence must therefore be declared before writing
  data of that entity type. PostgreSQL retains its single-transaction guarantee under the
  shared feature advisory lock. On a table with no marker row there is nothing declared and
  compaction proceeds, as it always has. A pre-v0.9 writer that knows nothing of the manifest
  cannot be stopped, and the guarantee binds v0.9 writers as everywhere else in this section.
- A fenced read refuses an entity type in `retention` with a typed `RetentionConflict` error
  before any write ([Read fences](#read-fences)). The check is keyed to the durable set, not to the writing
  instance's own retention configuration.
- On PostgreSQL the manifest row's `historyDependent` and `retention` columns hold the same JSON
  text, and the checks are ordinary reads inside the refusing operation's transaction: the
  strong-consistency distinction is DynamoDB-specific.

## Rebuild fence

Rebuilds are fenced durably (v0.9). The lock row and the generation counter are separate
items:

| Attribute        | Type | Rebuild-lock item (`pk = SYSTEM#REBUILD`, `sk = 0`) |
| ---------------- | ---- | --------------------------------------------------- |
| `pk`             | S    | `SYSTEM#REBUILD`                                    |
| `sk`             | N    | `0`                                                 |
| `owner`          | S    | owner token of the current lock holder              |
| `generation`     | N    | the odd generation the acquire or takeover produced: the lease's fencing token |
| `leaseExpiresAt` | N    | lease expiry, epoch seconds                         |
| `forceReleased`  | BOOL | only on the item a force-release leaves (`true`), which has no other attribute |

| Attribute       | Type | Generation item (`pk = SYSTEM#REBUILD#GENERATION`, `sk = 0`)                  |
| --------------- | ---- | ----------------------------------------------------------------------------- |
| `pk`            | S    | `SYSTEM#REBUILD#GENERATION`                                                   |
| `sk`            | N    | `0`                                                                           |
| `value`         | N    | monotonic counter, bumped per rebuild                                         |
| `forceReleased` | BOOL | optional. `true` after a force-release, cleared by the next completed release |

```json
{
  "pk": "SYSTEM#REBUILD",
  "sk": 0,
  "owner": "rebuild-4b1f0a2e",
  "generation": 5,
  "leaseExpiresAt": 1760000000
}
```

```json
{
  "pk": "SYSTEM#REBUILD#GENERATION",
  "sk": 0,
  "value": 5
}
```

The lock row above and this generation are one active-rebuild state: the lock exists, so the
generation is odd. After a force-release the lock item holds no lock and only the flag:

```json
{
  "pk": "SYSTEM#REBUILD",
  "sk": 0,
  "forceReleased": true
}
```

It names no owner and no lease, so no lease-bound condition below holds on it, but it is present,
so every commit's lock check keeps failing until a rebuild acquires from it and ends. The lock row also records the generation its acquire or takeover produced
(`generation`), the lease's fencing token: it is written in the same transaction as the
generation bump, so while the lock exists it equals the generation item's `value`. A lease is its
owner token and that generation. Owner tokens are caller-chosen, and two incarnations of a
worker may reuse one: a worker whose lease lapsed and was taken over, even by a later incarnation
under the same token, still holds the earlier generation, so every lease-guarded write below
conditions on both and the stale incarnation fails with `RebuildLeaseLost`.

The protocol. Acquire, takeover, release, and force-release are each one `TransactWriteItems`
that writes both items in a single transaction, so a crash can never leave the lock and the
generation disagreeing: the generation is odd if and only if a rebuild is in progress: odd
while a rebuild holds the lock, even when quiesced. The one exception is a force-release,
which releases the lock but deliberately leaves the generation odd, recording `forceReleased`:
that odd value means "derived state untrustworthy", not "rebuild in progress", and readers and
commits treat it the same way (below). On DynamoDB the lock item exists exactly while the
generation is odd: a held lock, or the item a force-release leaves in its place.

Every attribute name an expression touches is audited against DynamoDB's reserved-word list, which
is case-insensitive: `VALUE` and `OWNER` are reserved, so the expressions below reach them only
through the `#value` and `#owner` aliases, each shown with its `ExpressionAttributeNames` map. The
other attribute names in this spec's expressions (`pk`, `sk`, `seq`, `eventSeq`, `version`,
`leaseExpiresAt`, and `forceReleased`) are not reserved and appear literally, here and in the
write-condition table in [Writes](#writes).

- Acquire (a fresh lock: no lock row exists, or only the item a force-release left):

  ```text
  Put    (SYSTEM#REBUILD, sk = 0)  owner = :newOwner, leaseExpiresAt = :now + :lease
         ConditionExpression: attribute_not_exists(pk) OR forceReleased = :true
  Update (SYSTEM#REBUILD#GENERATION, sk = 0)
         SET #value = if_not_exists(#value, :zero) + :increment
         ConditionExpression: attribute_not_exists(#value) OR #value = :seenEven
                              OR (#value = :seenOdd AND forceReleased = :true)
         ExpressionAttributeNames: {"#value": "value"}
  ```

  The generation condition asserts the quiesced state the caller observed: absent-or-`0` before
  the first rebuild (`:seenEven = 0` covers the absent item), the stored even value after, or
(after a force-release) an odd value carrying `forceReleased = true`, the one odd generation
  that can exist without a lock row. `:increment` is one when the observed generation was
  absent or even and two when it was odd and force-released: either way the generation ends
  odd, matching the lock row that now exists. An odd value without the flag never passes: that
  state cannot arise, because the only odd-generation-without-lock transition (force-release)
  sets the flag in the same transaction. The lock put replaces the force-released item. A held
  lock never carries `forceReleased`, so the put still fails against one.

- Takeover (of an expired lease: one transaction, the same two items):

  ```text
  Put    (SYSTEM#REBUILD, sk = 0)  owner = :newOwner, leaseExpiresAt = :now + :lease
         ConditionExpression: leaseExpiresAt < :now AND #owner = :observedOwner
         ExpressionAttributeNames: {"#owner": "owner"}
  Update (SYSTEM#REBUILD#GENERATION, sk = 0)
         SET #value = #value + :two
         ConditionExpression: #value = :seenOdd
         ExpressionAttributeNames: {"#value": "value"}
  ```

  `:observedOwner` is the owner the caller observed when it decided to take over the expired
  lease. On takeover the lock row still exists, so the generation is necessarily odd: an
  acquire's even-value condition can never hold, and adding one would leave the generation even
  while a lock row exists. Takeover instead asserts the observed odd value and adds two: the
  generation stays odd (the lock is still held) but changes, so a reader that pinned the old
  epoch sees a new one and re-reads. A takeover racing another takeover fails one of the two
  conditions and retries from a fresh read.

- Renew: while it runs, the rebuild renews `leaseExpiresAt` with one conditional update of the
  lock item asserting the lease: its owner and its fencing generation:

  ```text
  UpdateExpression:    SET leaseExpiresAt = :expiry
  ConditionExpression: #owner = :owner AND #generation = :generation
  ExpressionAttributeNames: {"#owner": "owner", "#generation": "generation"}
  ```

- Release: one transaction:

  ```text
  Delete (SYSTEM#REBUILD, sk = 0)
         ConditionExpression: #owner = :me AND #generation = :generation
         ExpressionAttributeNames: {"#owner": "owner", "#generation": "generation"}
  Update (SYSTEM#REBUILD#GENERATION, sk = 0)
         SET #value = #value + :one REMOVE forceReleased
         ConditionExpression: #value = :seenOdd
         ExpressionAttributeNames: {"#value": "value"}
  ```

  `:generation` and `:seenOdd` are both the lease's fencing generation, so a release needs no read
  first: it fails unless the lock row still names the lease's owner under that generation and the
  generation item still holds it. A release restores the quiesced state (generation even) and clears `forceReleased`, so the
  next acquire sees a plain even value whether or not the rebuild started from a force-released
  generation.

- Force-release: one transaction, the operator's escape hatch for a lost or wedged worker:

  ```text
  Put    (SYSTEM#REBUILD, sk = 0)  forceReleased = true
         ConditionExpression: #owner = :requestedOwner
         ExpressionAttributeNames: {"#owner": "owner"}
  Update (SYSTEM#REBUILD#GENERATION, sk = 0)
         SET #value = #value + :two, forceReleased = :true
         ConditionExpression: #value = :seenOdd
         ExpressionAttributeNames: {"#value": "value"}
  ```

  Force-release ends the lease at once (the lock item no longer names the owner, so the
  released worker's renew, release, and guarded view writes fail with `RebuildLeaseLost`, and a
  new rebuild can begin without waiting for the lease to lapse) but it deliberately leaves the
  generation odd: it adds two, not one, and sets `forceReleased`. The force-released
  rebuild may have committed only some of its wipe and replay batches (its derived state is
  half-written and there is no replacement worker left to finish it) so readers and commits
  stay fenced until a later rebuild acquires the lock, replays, and completes a release, whose
  even generation and cleared flag end the fence. Readers get `RebuildUnavailable`. Every commit
  gets `RebuildInProgress`, the error a held lock gives, because the item the force-release puts
  in place of the lock fails the commit's lock check. Commits stay refused because a commit can
  derive durable data from the half-written state: a journaled commit
  ([Journal](#journal)) allocates scope positions from counter rows the failed rebuild may have
  cleared, and stamps them into the event's immutable metadata, duplicating positions that earlier
  events hold. Refusing every commit, not only journaled ones, keeps the rule the commit check
  already has (no commit while the generation is odd) and costs no action: the check is the
  same `ConditionCheck`. A takeover cannot recover this state (there is no lease to take over).
  Only a fresh acquire from the force-released odd generation can. To resume writes, run the
  rebuild again to its end. An operator who knows the failed rebuild wrote nothing derived (no
  wipe, no batch) may instead `Begin` and `End` without replaying, which settles the generation
  as it stands.

  Pre-release stores. No released version wrote the earlier force-release, which deleted the
  lock row. A DynamoDB store force-released by a pre-release v0.9 build holds an odd, flagged
  generation and no lock item, so its commits pass the lock check until a rebuild settles the
  generation (PostgreSQL and the in-memory store read the generation and refuse them). After
  upgrading, run a rebuild to its end on any store whose generation is odd with no lock. An
  acquire accepts that state through `attribute_not_exists(pk)`. A pre-release build cannot
  acquire over the force-released item (its put conditions on `attribute_not_exists(pk)` alone)
  and cannot decode it, so upgrade every rebuild worker before force-releasing.

- Commit-time check: every v0.9 commit includes a `ConditionCheck` asserting
  `attribute_not_exists(pk)` on the lock row (mandatory, like the feature-marker check, not
  opt-in per store) so a commit is refused whenever the generation is unsettled: any rebuild
  holds the lock, including an expired one, or a force-release left its item in place of the
  lock. Until a rebuild ends, it blocks writes. That is deliberate: commits stay safe while any
  lock item exists, at the cost of waiting out a crashed rebuild (or running a new one after a
  force-release). A commit that races a rebuild fails its check with `RebuildInProgress`
  ([Writes](#writes)), retryable once a rebuild ends: never as a fence conflict. A store that
  never ran a rebuild has no lock item, so its commits pass. The check sits at position 2 of every commit, after the feature-marker check
  and before every other action, in the commit that writes events, in a commit that writes only
  an outcome row, and in the [outcome-only transaction](#the-outcome-only-transaction) that
  persists a rejection. An out-of-band snapshot write, compaction, and a rebuild's own lifecycle
  and view writes carry no such check. It is a `ConditionCheck` that carries no expression
  attribute names or values, sized in the commit budget by its two key attributes like the
  marker check, and it is the second-ranked failure of a commit ([Failure
  classification](#failure-classification)): a failed marker check outranks it, and it outranks
  the outcome put, drift, a gap, and every other conflict, so a commit that raced a rebuild
  reports `RebuildInProgress` whatever else its cancellation reasons say, and no
  [failure-path probe](#failure-classification) runs for it. A commit that is refused before it
  reaches the store (a projector-only commit, an invalid commit, a reserved entity ID, a commit
  over its budget) keeps those errors during a rebuild, because they need no read of the lock.

Rebuild view writes (v0.9). While it replays, the rebuild worker writes its view rows in
`TransactWriteItems` batches of at most 99 view operations: the 100th item of every batch is a
`ConditionCheck` on the lock row:

```text
ConditionExpression: #owner = :me AND #generation = :generation AND leaseExpiresAt > :now
ExpressionAttributeNames: {"#owner": "owner", "#generation": "generation"}
```

The condition asserts transactionally, with every batch's writes, that the worker still holds its
lease (its owner and fencing generation) and that it has not expired. A worker that pauses past its lease and loses the lock to a takeover cannot
resume wiping or replaying views: its next batch fails the check and the worker aborts
immediately, so the new owner's release is never racing a stale worker's projection writes.
(Changing the generation protects readers. Only this per-batch condition protects the views from
the _old_ worker.) On PostgreSQL the equivalent is per transaction: every rebuild write
transaction takes the lock row itself with `FOR UPDATE` and asserts ownership and lease inside
the same transaction that carries the view statements:

```sql
SELECT owner, generation, EXTRACT(EPOCH FROM lease_expires_at)::bigint FROM evt_events__evt_rebuild_lock
WHERE id = 0 FOR UPDATE;  -- must return owner = $1 AND generation = $2 AND a lease past $3, else abort
```

(`evt_events__evt_rebuild_lock` stands for the configured derived name.) The row lock is held
for the length of the write transaction, so a takeover (which must `UPDATE` or `DELETE` that
row) blocks until the write transaction commits: the old worker either asserts the old owner
and commits first, or waits and then fails the assertion against the new owner and aborts. A
plain predicate read would hold no lock and leave exactly that window. A failed check aborts the
rebuild worker in both languages. Nothing is ever written by a worker that no longer holds the
lock.

The rows live in the reserved `SYSTEM#` namespace, skipped by enumeration, heads, and rebuild
scans, and neither row has a snapshot or a `ttl`.

Reader epoch check. A reader that needs consistency reads the generation before and after its
read and treats an odd or changed value as "rebuild in progress or completed: retry": the
generation increments when a rebuild acquires the lock, changes again when a takeover replaces an
expired lease, and increments once more when it releases after replay completes, so state built
under a stale epoch can be rejected and re-read. A force-release leaves the generation odd and
flagged, so readers keep retrying through it: the fence ends only when a later rebuild
completes and releases (even). On DynamoDB both generation reads set
`ConsistentRead = true`, regardless of the repository's read-consistency setting: two eventually
consistent reads can return the same stale even value while a rebuild holds the lock, and the
reader would accept state produced mid-rebuild. PostgreSQL's reads are transactionally consistent,
so the rule needs no flag there.

### Rebuild lifecycle API

Every backend (in-memory, DynamoDB, PostgreSQL) in both languages exposes the same operations over
the two rows (v0.9). The names below are Go's, with Rust's in parentheses. The semantics, the
errors, and the stored bytes are shared.

| Operation                                            | Effect                                                                                         |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `State` (`rebuild_state`)                            | Reads the generation, then the lock row, each with a consistent read.                          |
| `Generation` (`rebuild_generation`)                  | Reads the generation item alone with a consistent read: the reader primitive.                 |
| `Begin` (`begin_rebuild`)                            | Acquires the lock from a quiesced or force-released state, or takes over an expired lease.     |
| `Renew` (`renew_rebuild`)                            | Extends the holder's lease and returns the new expiry.                                         |
| `End` (`end_rebuild`)                                | Releases the lock and restores the quiesced (even) generation.                                 |
| `ForceRelease` (`force_release_rebuild`)             | The operator's release of a named owner's lock, leaving the generation odd (commits refused). |
| `WriteViews` (`write_rebuild_views`)                 | One guarded batch of view writes ([Rebuild view writes](#rebuild-view-writes)).                |

Values. A *generation* is its `value` (an absent item reads as `0`) and its `forceReleased`
flag (`false` when absent). It is *settled* when `value` is even and *unsettled* when odd. A *lock*
is its `owner` and `leaseExpiresAt`. A *state* is a generation and an optional lock. The item a
force-release leaves holds no lock: `State` reports none. A rebuild is
*in progress* when the lock row exists. `State` reads the generation first and the lock second.
The two reads are not one snapshot, so a caller that must decide on the generation uses
`Generation`, and one that must decide on the lock row uses the conditional writes below, which
assert both items in one transaction.

Owners and leases. An owner token is a caller-chosen, non-empty string of at most 512 UTF-8
bytes without U+0000. A lease is a duration of at least one second. It is rounded up to whole seconds, and a
lease below one second, an empty or oversized owner, and a non-UTF-8 owner or one containing U+0000 are refused with the
language's invalid-argument error before any request. Every operation reads the repository's clock
once, in whole Unix seconds, as `:now`. A lease taken at `:now` expires at `:now + :lease`, and the
lease has *expired* when `leaseExpiresAt < :now`: a lease is still held at the second it expires.
The clock is the writer's own, so clock skew between a rebuild worker and a taker-over shortens or
lengthens a lease by the skew. Choose leases far longer than the skew. Both languages let a test
inject the clock (Go `WithClock`, Rust's repository clock).

`Begin`. It reads the state, then decides:

| Observed state                                          | Action                                                       |
| ------------------------------------------------------- | ------------------------------------------------------------ |
| no lock row, generation even or absent                  | acquire, `:increment` 1                                      |
| no lock row, generation odd with `forceReleased`        | acquire from the force-released state, `:increment` 2        |
| lock row, `leaseExpiresAt < :now`                       | take over, observing the row's `owner` and the odd generation |
| lock row, `leaseExpiresAt ≥ :now`                       | refuse with `RebuildLockHeld` (owner and expiry), no write   |
| no lock row, generation odd without `forceReleased`. Or lock row with an even generation | refuse with `RebuildStateInvalid`, no write |

The two inconsistent states cannot arise from this protocol, because every transition writes both
items in one transaction. They are reported rather than repaired. On DynamoDB `Begin` reads the
two items one after the other, so a transition that lands between the reads can show such a pair
(a lock row beside the generation from before it): `Begin` reads again, and only a pair that
survives all the reads is reported, as `RebuildStateInvalid`. The acquire and the takeover are
the transactions above. If their conditions fail, another operation raced the read: `Begin` reads
the state again and decides again, at most eight times in all, and then fails with the transient
`RebuildConflict`. On success it returns a *lease*: the owner, the generation the transaction
produced (odd), and the new `leaseExpiresAt`. Every commit's lock check reads the lock item, so on DynamoDB it is a hot item: under heavy write
traffic a lifecycle transaction can lose several races in a row and `Begin` return the transient
`RebuildConflict`. The caller retries it. A takeover bumps the generation by two and an
acquire from a quiesced state by one, so a reader pinned to any earlier epoch sees a changed
generation either way.

Request shapes. The acquire's generation condition is the union written above, with all five
values always bound, because DynamoDB rejects a request that binds a value its expressions do not
use. A branch that does not apply binds its value to `-1`, which no generation equals:

| Acquire from                | `:zero` | `:increment` | `:seenEven`   | `:seenOdd`    | `:true` |
| --------------------------- | ------- | ------------ | ------------- | ------------- | ------- |
| absent generation           | `0`     | `1`          | `0`           | `-1`          | `true`  |
| even generation `v`         | `0`     | `1`          | `v`           | `-1`          | `true`  |
| force-released odd `v`      | `0`     | `2`          | `-1`          | `v`           | `true`  |

The acquire's lock put binds `:true` (`true`) for its `forceReleased = :true` branch, in every
row of the table. The lock item an acquire or takeover puts is the full item of the example above (`pk`, `sk`,
`owner`, `generation`, `leaseExpiresAt`) where `generation` is the odd generation the transaction
produces (the observed value plus `:increment`): and the takeover's `:now` and `:observedOwner`
are numbers and a string as named. A release names the lease (`:me`, `:generation`), a
force-release the owner alone (`:requestedOwner`) and puts the force-released item above, and the generation update's `:one`, `:two`, and
`:seenOdd` are numbers. Renew is one `UpdateItem` (not a transaction) on the lock item, as above.

`Renew`, `End`, and `WriteViews` take the lease `Begin` returned (owner and generation. In Rust
the `RebuildLease`), and fail with `RebuildLeaseLost` unless the lock row names that owner under
that generation. `Renew` returns the lease with its new expiry. It does not require the lease to be
unexpired: an owner whose lease lapsed but whom no one has taken over may renew it. `End` runs
the release transaction without reading first. A failed condition is `RebuildLeaseLost` as well. A
takeover (even by the same owner token) and a force-release both change the lock row, so a stale
lease cannot match it. `End` returns the settled generation. `ForceRelease` names the owner the
operator observed. It fails with `RebuildLeaseLost` when the lock row is gone or names another
owner (the rebuild it meant to release has already ended or been replaced), and returns the odd,
flagged generation. It never runs the rebuild's cleanup, and it does not let commits through:
every commit is refused with `RebuildInProgress` until a later rebuild ends.

Errors. The names are Go's, with Rust's variant in parentheses. All are typed in both
languages and none is a conflict or a stale-fence rejection.

| Error                                                | When                                                                                                                              |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `RebuildInProgress` (`Error::RebuildInProgress`)     | A commit's lock check failed: a rebuild holds the lock, or a force-release left the generation odd. Transient: retried with a backoff, returned when attempts run out, never a rejection. |
| `RebuildLockHeld` (`Error::RebuildLockHeld`)         | `Begin` found an unexpired lock. Names the owner and the expiry. Not retried by the engine.                                        |
| `RebuildLeaseLost` (`Error::RebuildLeaseLost`)       | `Renew`, `End`, `ForceRelease`, or a guarded write found the lock gone, owned by someone else, held under another generation (a later incarnation of the same owner token), or (guarded write) expired.         |
| `RebuildConflict` (`Error::RebuildConflict`)         | `Begin` lost its race eight times. Transient.                                                                                  |
| `RebuildStateInvalid` (`Error::RebuildStateInvalid`) | The two rows disagree in a way this protocol cannot produce.                                                                       |
| `RebuildUnavailable` (`Error::RebuildUnavailable`)   | A reader found an odd generation: a rebuild is in progress, or a force-release left derived state untrustworthy. Transient.    |
| `RebuildEpochChanged` (`Error::RebuildEpochChanged`) | A reader's generation changed between its before and after reads. Transient.                                                   |

### Rebuild view writes

A rebuild worker writes its view rows through `WriteViews`, one batch per call. On DynamoDB a
batch is one `TransactWriteItems` of at most 99 view operations (the same items a commit's
projector operations produce) followed by the guard as the 100th action:

```text
ConditionCheck (SYSTEM#REBUILD, sk = 0)
    ConditionExpression: #owner = :me AND leaseExpiresAt > :now
    ExpressionAttributeNames: {"#owner": "owner"}
```

A batch of more than 99 operations fails with `CommitTooLarge` before any write, and an empty
batch is refused as an invalid argument. A failed guard writes nothing and is `RebuildLeaseLost`:
the worker lost its lock to a takeover or a force-release, or let the lease lapse, and must stop. On
PostgreSQL the write is one transaction that selects the lock row `FOR UPDATE`, asserts the owner
and an unexpired lease, then runs the view statements the repository's view writer produces
([PostgreSQL](#postgresql)). A repository with no view writer refuses the batch with
`ViewsNotConfigured`.

### Rebuild epochs

A reader that needs derived state to be consistent fences its read against the generation. The
protocol is the reader epoch check above, in three shapes every backend and both languages share:

- Observe. Read the generation. An odd one fails with `RebuildUnavailable`, naming the
  generation and whether it is flagged `forceReleased`. An even one is an *epoch*, the value the
  read is made under.
- Verify. Read the generation again. An odd one fails with `RebuildUnavailable` and a settled
  one that differs from the epoch fails with `RebuildEpochChanged`, naming both values. A settled
  generation equal to the epoch means no rebuild started, finished, or was taken over while the
  read ran.
- Fenced read. Observe, run the read, verify. The read's result counts only when verify
  passes. A failed observe skips the read.

Both failures are transient: the caller waits and reads again, once a rebuild has ended. A command
handler that read a view makes its decision *under* an epoch, and returns the error from observe
or verify as the handler's own error: the engine returns it at once, records no outcome, and the
same command ID runs again later. That is what keeps a decision made on a half-rebuilt view from
being recorded as a rejection or an acceptance: a rebuild that begins after the verify is stopped
at the commit by the lock check (`RebuildInProgress`, transient), and one that began before it
fails the observe or the verify. No further action rides on the commit: the epoch check is the
reader's, and the commit's only rebuild action is the lock check. A reader that wants the
rebuild-in-progress state alone, rather than an epoch, reads `State`: a lock row means a rebuild
holds the fence now, and an odd generation with no lock and `forceReleased` means the fence
ended in a force-release (commits stay refused until a rebuild ends).

## Stream heads

Every stream has one head item recording its head. Commits condition on it for concurrency,
and a read fence is one check of it. It replaced the continuation check, the floor check, the
pinned conditions, and the fence's slot check and snapshot companion, which no longer exist
([ADR 0007](../adr/0007-per-stream-head-item.md), tracking
[#159](https://github.com/photon-grove/evt/issues/159)). This section is normative for both
languages and every backend.

### Item

| Attribute | Type | Head item (`sk = -1`)                                                 |
| --------- | ---- | --------------------------------------------------------------------- |
| `pk`      | S    | entity ID                                                             |
| `sk`      | N    | `-1`                                                                  |
| `head`    | N    | the highest event sequence ever committed to the stream, at least 1   |
| `ttl`     | N    | optional, epoch seconds. Written only for entity types with retention |

```json
{ "pk": "acct-1", "sk": -1, "head": 7 }
```

```json
{ "pk": "session-9", "sk": -1, "head": 3, "ttl": 1760086400 }
```

- The row is in the stream's own partition. It is not in a [reserved
  namespace](#reserved-namespaces), and it is not an event or a snapshot: no event or snapshot read,
  `latest(n)`, or compaction range returns it (every one bounds `sk` below at 0 or more. A negative
  lower bound is clamped to 0). A scan with an `entityType` filter never returns it, because it has
  no `entityType`. An unfiltered scan does, so every scanner skips it ([Event-writing paths,
  reads, and consumers](#event-writing-paths-reads-and-consumers)).
- The row carries only `pk`, `sk`, `head`, and `ttl`. An `Update` is billed on the larger of the item
  before and after, so the item stays well under 1 KB. No other attribute is added to it.
- `ttl` is written only for an entity type with positive retention, and is at least the `ttl` of
  every other item of the stream and never lowered: a commit raises it and an out-of-band snapshot
  write refreshes it in the same transaction, both by the [never-lower
  rule](#retention). It is not written for any other type, so the head item of a stream
  without retention is never deleted.
- `head` is not a DynamoDB reserved word. `ttl` is, and an expression reaches it through `#ttl`
  (`ExpressionAttributeNames: {"#ttl": "ttl"}`).
- The head item is concurrency-control metadata for the log, not a view. It is written only in the
  commit transaction that writes the events it counts, and it can be recomputed from the log (below).

### Invariants

- H1, monotone. `head` never decreases, and any commit that writes events to the stream raises it
  by at least one. It is not deleted (retained types excepted, by their `ttl`).
- H2, exact. After a commit that writes a stream, `head` is the stream's highest event sequence.
- H3, covered. A snapshot's `eventSeq` is at most `head`. A commit raises `head` to at least every snapshot it
  writes, and an out-of-band snapshot write conditions on `head >= :new` (below), so it is enforced.
- H4, derivable. `head` equals the derived head: the larger of the stream's highest event
  `sk` and its snapshot's `eventSeq`. Compaction deletes events at or below the snapshot's
  `eventSeq`, which is at most `head`, so it never changes the derived head.

A writer or repair tool that adds or removes events outside a commit maintains H1–H4 or leaves the
stream in the drift state described under [Classification](#failure-classification).

### Head updates

The stream group of [Writes](#writes) step 4 is, per written stream in ascending entity-ID byte
order:

1. The head update.
2. One put per event, in ascending sequence.
3. The stream's snapshot put, when the commit writes one.

There is no continuation check and no floor check. Step 5 of Writes emits one check per fenced
stream.

```json
{
  "Update": {
    "Key": { "pk": "acct-1", "sk": -1 },
    "UpdateExpression": "SET head = :last",
    "ConditionExpression": "head = :prev",
    "ExpressionAttributeValues": { ":last": 9, ":prev": 7 }
  }
}
```

A commit that appends events 8 and 9 to `acct-1` at head 7. For a type with retention the update
and its condition follow the [never-lower rule](#retention). When the stream's first sequence is 1
the condition is `attribute_not_exists(head)` and `:prev` is omitted.

| Write                                       | Condition                                                        |
| ------------------------------------------- | ---------------------------------------------------------------- |
| head update, create (first sequence 1)      | `attribute_not_exists(head)`                                     |
| head update, append (first sequence > 1)    | `head = :prev` (`:prev` = first sequence − 1)                    |
| event put                                   | `attribute_not_exists(sk)`                                       |
| first snapshot put in a commit              | `attribute_not_exists(seq)`                                      |
| later snapshot put in a commit              | `seq = :seq`                                                     |
| snapshot put outside a commit               | `attribute_not_exists(eventSeq) OR eventSeq <= :new`             |
| fenced stream, head 0                       | `attribute_not_exists(head)`                                     |
| fenced stream, head `:head` ≥ 1             | `head = :head`                                                   |
| feature-marker, outcome put, rebuild lock   | as in [Writes](#writes)                                          |

The head condition subsumes the continuation and floor checks of earlier drafts:

- Continuity: `head = first − 1` means events `1..first − 1` were committed (H2), so nothing is
  skipped and `first` and above are free.
- Floor: `snapshot.eventSeq ≤ head = first − 1 < first` (H3).
- A writer that loaded before another writer appended has a stale `:prev` and conflicts, because the
  other writer's commit raised the head (H1). Compaction does not move the head, so a writer whose
  load is current never conflicts with a compaction.

The worked example in [Writes](#writes) (appends to streams `b` and `a`, `a` carrying a snapshot,
fencing read-only `z` and `m`) sends nine actions with the rebuild-lock check. The old layout sent
eleven.

### Head checks

A fence on a stream the reader saw at head `H` is one `ConditionCheck` on the head item: `head = :H`
for `H ≥ 1`, `attribute_not_exists(head)` for `H = 0`. `H` is the derived head of the loaded stream
(H4). The worked example is in [Read fences](#read-fences). The check passes exactly when no commit
has written the stream since the reader's load. `head` only increases (H1), so a matching value
cannot have been reached by a different history: the compaction ABA that the snapshot companion
closed does not exist, and the companion is gone. A fenced stream that is also written contributes
only its head update. The fence's provenance, the conflict error, and
[Fence-aware retry](#fence-aware-retry) are unchanged. Fences stay refused for retained types
([Retention](#retention)).

### Budget

```text
items = Σ over written streams (events_s + 1 + [snapshot put in this commit])
                                                  head update + event puts + snapshot put
      + fenced read-only streams × 1              head check
      + 1                                         outcome put, when outcomes are enabled
      + 1                                         feature-marker check, always
      + 1                                         rebuild-lock check, always
      + projector puts and deletes
```

A commit that writes no snapshot for a stream pays one action beyond its events for that stream
whether it creates or appends. A single-stream commit holds
at most 97 event and projector operations when it writes no snapshot, and 96 when it writes
one (marker and rebuild lock both counted). Creating a
stream with a snapshot in the same commit is the one case that costs more than before (the snapshot
put used to replace the floor check). `CommitTooLarge` fires on the new count, before any write, on
every backend. The head update counts toward the byte budget by the rule used for any update: its
key attributes plus its expression strings, name placeholders and names, and attribute values.

### Failure classification

A failed commit is classified by the failing items' cancellation-reason indexes, and where several
items failed the engine ranks them (highest first), identically on every backend:

1. The feature-marker check, then the rebuild-lock check (unchanged).
2. The outcome put (`OutcomeConflict`, unchanged).
3. `StreamHeadDrift`.
4. `SequenceGapError` / `Error::SequenceGap`.
5. Any other conflict: a head update, an event put, a snapshot put, or a fence check (with its
   provenance).
6. Projector operations ([Views](#views)): the first failed one in transaction order, as a
   `ProjectorOperationError` / `Error::ProjectorOperation` naming the projector and the operation.
   Its reason is the item's cancellation reason code (`ConditionalCheckFailed`, `ValidationError`,
   or `ItemCollectionSizeLimitExceeded`). `TransactionConflict` and throttling on a projector item
   keep their transient classification.

`TransactionConflict`, throttling, and indeterminate writes are unchanged. Every failed written
stream and fence is evaluated before the ranking, so the result does not depend on which failed
first. Among ordinary conflicts the first failing item in transaction order is the one reported
(the written streams, then the fences, then projector conditions). A gap is the failing transaction
item, not a refusal before any write, so it ranks below the outcome conflict: if the outcome row
exists, the row is the answer. A read of the probe that itself fails is returned as the read's error
(retryable when the read is), never as a conflict or drift it did not establish.

The failure-path probe classifies a failed head update, and a failed fence check. It uses no
`ReturnValuesOnConditionCheckFailure`. Both languages do exactly this:

1. Derive `D1` with strongly consistent reads: the snapshot item's `eventSeq` and the highest event
   `sk` (`Query` of `sk > 0`, descending, limit 1), taking the larger.
2. Read the head item (`GetItem`, strongly consistent) as `S`, absent as 0.
3. `S < D1`: drift.
4. `S = D1`: no drift. A failed head update with `S < first − 1` is a gap, otherwise a conflict. A
   failed fence is a fence conflict.
5. `S > D1`: derive again as `D2`. `D2 < S` is drift. Otherwise a commit landed between the reads
   and the failure is an ordinary conflict.

For an entity type with retention, a head above the derived head, and a head item absent while
remaining items all have a `ttl` in the past, are the expired-tail transient and an ordinary
conflict, not drift ([Retention](#retention)).

`StreamHeadDrift` (Go `*StreamHeadDriftError`, Rust `Error::StreamHeadDrift`) carries the stream
ID, the stored head (or absent), and the derived head. It is not retryable: it is not classified
transient, fence-aware retry returns it at once, it writes no outcome row, and it is never recorded
as a `stale-fence` rejection. It is raised when:

- The stream's head update passed and an event put failed (the cancellation reasons show the head
  update as passing): an event exists above the head. For an entity type with retention this goes
  through the retention-aware probe first, because TTL can delete the head before an expired event:
  the engine reads the stream's remaining items (the snapshot and a `sk > 0` query projecting `sk`
  and `ttl`), and if every one has a `ttl` in the past the failure is a transient conflict that
  heals when TTL deletes them. Otherwise it is drift. A type without retention is drift at once.
- The probe finds drift.
- An out-of-band snapshot write finds the snapshot ahead of the head, or no head item (it reports
  the head the log would derive once the snapshot is written as the derived head).

A failed snapshot put whose head update passed is an ordinary conflict: an out-of-band snapshot can
bump the snapshot sequence without moving the head.

### Retention

Fences stay refused (`RetentionConflict`) for entity types with retention. The head item of such a
type carries a `ttl` at least that of every other item of the stream, and the engine never lowers it
(a commit raises it. An out-of-band snapshot write refreshes it in the same transaction, because
`PutSnapshot` stamps its snapshot's `ttl` at call time and would otherwise outlive the head item.
the backfill uses the maximum `ttl` across the partition). A retained stream disappears whole once every item has
expired and its entity ID is then reusable, but TTL deletion is lazy and unordered, so a partly
deleted stream is possible and transient. A head item without a `ttl` would make a fully expired
stream unrecreatable, and a head item with a `ttl` is not an incarnation-proof fence (TTL deletion
is lazy), which is why the refusal stands. See the ADR.

The never-lower rule. Two writers can configure different retention durations (the manifest
records only entity-type names) and a clock can step back, so stamping the commit's own `ttl` on
the head could shorten it. DynamoDB has no `max()` in an update expression, so the head `ttl` is
raised by value and guarded by a condition. No single durable retention duration is required. On
append, a retained stream's head update is:

```text
UpdateExpression:    SET head = :last, #ttl = :t
ConditionExpression: head = :prev AND (attribute_not_exists(#ttl) OR #ttl <= :t)
ExpressionAttributeNames: {"#ttl": "ttl"}
```

`:t` is the larger of the commit's own `ttl` and the largest `ttl` among the items the writer loaded
for the stream (the snapshot and the events after it). On create the update is
`SET head = :last, #ttl = :t` under `attribute_not_exists(head)`, with `:t` the commit's `ttl`. The
event items keep the commit's own `ttl`. Only the head takes the maximum. If an unseen writer (an
out-of-band snapshot) raised the stored `ttl` above `:t`, the condition fails as an ordinary
conflict, and the retry reloads, sees the larger `ttl`, and passes. An out-of-band snapshot write
uses the same `ttl` condition with `:t` its snapshot's `ttl`. The condition can fail on either
clause, so it reads the head item back and decides from the stored values: a head at or above
`:new` whose stored `ttl` is at least the snapshot's needs no refresh and is retried as a
`ConditionCheck` on `head >= :new`. A head at or above `:new` whose `ttl` is lower or absent (the head
was behind when the update failed, and a concurrent writer advanced it with a shorter `ttl`) is
retried as the refreshing update, so the snapshot never outlives the head item. The retry is
bounded (four times), after which the write fails as a transient error. A head below `:new` or
absent is `StreamHeadDrift`.

### Snapshot writes outside a commit

`PutSnapshot` (and a rebuild path that seeds a snapshot) keeps `attribute_not_exists(eventSeq) OR
eventSeq <= :new` on the snapshot put and adds the head item to its transaction, which becomes:

1. The feature-marker check.
2. The head item: for a type without retention a `ConditionCheck` with `head >= :new`. For a type
   with retention an `Update` with `head >= :new` and the [never-lower](#retention) `ttl`
   refresh.
3. The snapshot put.

`:new` is the snapshot's `eventSeq`. When `:new` is 0 (a snapshot of an empty stream, including a
snapshot-only partition the migration left without a head item) the head item may be absent: the
check is `attribute_not_exists(head) OR head >= :new`, and it is a `ConditionCheck` even for a
retained type, because an `Update` would create a head item with no `head` attribute. Otherwise a
failed head condition is `StreamHeadDrift` (the snapshot is ahead of the stream, or the stream has
no head item). A failed snapshot condition keeps its current
meaning, a no-op because a newer snapshot already covers the write. PostgreSQL checks
`head >= :new` under the entity lock in the same transaction.

### Event-writing paths, reads, and consumers

Every path that adds, removes, or snapshots events either maintains the head or is refused:

| Path                                                                                          | Effect                                                                                                                         |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Go `Commit`, `CommitWithSnapshot`, and Rust `commit`, `commit_transaction` (every backend)    | The head update is part of the commit (outcome-only and rejection commits included).                                           |
| `PutSnapshot`, `put_snapshot`, and rebuild seeding that writes a snapshot                     | Conditions on `head >= :new` and refreshes a retained head's `ttl` ([above](#snapshot-writes-outside-a-commit)).        |
| `CompactBelow`, `compact_below`                                                               | Unchanged. Never touches the head.                                                                                             |
| Fixture or reset tooling                                                                      | Deletes events only. Must delete the head item too.                                                                            |
| `evt-doctor migrate-heads`                                                                    | The only tool writing head items outside a commit.                                                                             |

- Event, snapshot, `latest(n)`, and compaction queries are unchanged. `CompactBelow` never deletes
  the head item and may delete the head event.
- Unfiltered scans fail on the head row today, in v0.8 and v0.9: Go's `decodeScanPage` skips only
  `sk == 0` and then decodes the empty `metadata`, and Rust's `read_page` hands any non-snapshot
  item to `event_from_item`. Both are reached through unfiltered `StreamAllEvents`, unfiltered
  `StreamEntities`, and rebuilds without an entity type. Required in both languages:
  - `decodeScanPage` and `read_page` skip every row with `sk < 1`.
  - `enumerateEntityIDs` projects `sk` and skips `sk < 0` rows (an orphan head would otherwise list
    a ghost entity ID. Snapshot rows still enumerate their entity).
  - Heads scans (`pk, sk, eventSeq`) skip `sk < 0` explicitly (Go's `headSeqFromItem` routes every
    `sk ≤ 0` row to the snapshot branch. Rust's `item_head` returns any non-zero `sk`).
  - A negative `after` is clamped to 0 in Go's `GetLatestEvents`.
- Diagnostics that list a whole partition (Rust's `partition_items`) return the head item.
- DynamoDB Streams records for the head item (`sk = -1`) are not events: one per written stream per
  commit, and one per stream from the backfill. A consumer skips them with an ESM or Pipes filter on
  the keys, which every view type including `KEYS_ONLY` carries:

  ```json
  { "dynamodb": { "Keys": { "sk": { "N": [{ "anything-but": ["-1", "0"] }] } } } }
  ```

  (`"0"` also drops the snapshot, which consumers already skip.) The `NEW_IMAGE` decoder skips
  `sk < 1`. In Go, `stream.DynamoDBHandler` drops such `INSERT` records. `KEYS_ONLY` wake-ups fire on every head update unless filtered.
- `evt-doctor` reports: head below the derived head, head above it, a head item with no events or
  snapshot, and a stream with events and no head item. A plain `evt-doctor` run reports them once the
  store declares `stream-heads` and exits 1 on drift. `migrate-heads --verify` is the same check
  with the migration's refusals. `migrate-heads --repair` raises a low head and
  creates a missing one. A head above the derived value is lowered only by `--repair --allow-lower`,
  which runs with every writer stopped and writes `SET head = :derived` conditioned on
  `head = :observed`. A head item with no event or snapshot left is a warning on DynamoDB when it has a `ttl` (a
  retained stream's head item outlives the rest until it expires), and a finding when it has none
  (it never expires, and a create of the stream's ID would fail against it) and on PostgreSQL. A
  head item over a snapshot of event sequence 0 has no derived head to lower to, so the repair
  reports it and leaves it. DynamoDB also reports a head item whose `ttl` is below an item of its
  stream (or that has one while a stream item never expires), and the repair raises or removes it.

### Required feature

The feature is `stream-heads`, format version 1, in the `features` map:

```json
{
  "pk": "SYSTEM#FEATURES",
  "sk": 0,
  "version": 4,
  "features": "{\"journal\":1,\"stream-heads\":1}"
}
```

A writer that implements this section requires `stream-heads: 1` in the manifest and otherwise
refuses with a typed `StreamHeadsNotMigrated` error (Go `*StreamHeadsNotMigratedError`, Rust
`Error::StreamHeadsNotMigrated`), the first time it validates the marker. The refusal covers every
write path that validates the marker: commits (outcome-only and rejection commits included),
`PutSnapshot`, `CompactBelow`, and the mutating `evt-doctor` commands other than `init` and
`migrate-heads`. The paths that make their own marker declarations consult the marker before
declaring, so a refused store is refused without any declaration of its own. That covers the Rust
journal's first journaled commit and Go's `DeclareHistoryDependent`, which a history-dependent
projector's first commit runs before the commit is sent. Read-only paths do not need it.

A store whose marker does not declare the feature (no marker row, or a row without it) is declared
by initializing it: Go `StoreInitializer.Initialize`, which every repository implements, Rust
`FeatureMarker::initialize`, or `evt-doctor init`. Initialization is idempotent, concurrent
initializers included. A store that already declares the feature is left alone after one manifest
read, with nothing scanned or written, and the call reports that it declared nothing (Go `false`,
Rust `Ok(false)`). Two jobs initializing the same empty store at once let exactly one of them write,
because the loser's conditional write observes the row the winner guarded on and re-reads it before
deciding, so the manifest version bumps once and no writer that cached the winner's version sees a
spurious manifest change. A manifest that declares a pair the caller does not support is refused
with `UnsupportedFeature` first. Otherwise initialization declares the feature only after it finds
no non-reserved item in the store, and refuses a populated store with `StreamHeadsNotMigrated`,
declaring nothing. Such a store is migrated instead. It declares `stream-heads` and nothing else,
because the extensions (`journal`, `journal-compaction`) are declared by their first use, which reads
and writes only the marker row.

On DynamoDB the check is a strongly consistent scan that reads until it finds one item outside the
`SYSTEM#` and `command-outcome#` namespaces or the table ends, so a populated table stops it at
once. The declaration is the ordinary declaration transaction (`version` created at 1, or bumped by
one). The scan and the declaration are two steps, and no transaction can exclude a writer that never
reads the marker, so the order closes the window instead: the declaration is committed first, and
the table is then scanned once more, strongly consistently, for a headless stream (a partition with
a snapshot or event items and no head item, confirmed by a strongly consistent read of its head item
because a scan is not atomic across items). From the declaration on, a marker-reading writer fails
its per-commit check or refuses the table. One that committed before it is durable by the second
scan. A headless stream means the table was not fresh after all, so initialization retracts the
declaration (it removes `stream-heads` from the manifest in a further declaration transaction, so
every cached validation is dropped) and refuses with `StreamHeadsNotMigrated`. A stream that has a
head item is another head-aware writer's and never causes a retraction. A writer that predates the
marker cannot be excluded by any protocol. The operator obligation is that no writer older than the
first head-aware writer touches the store once that writer has run, and `migrate-heads` verifies the
store for headless streams before it declares. On PostgreSQL
the declaration transaction, under the exclusive feature lock, first checks that the events and
snapshots tables hold no non-reserved row. A log whose schema predates the marker has no features
table and no head table, so it cannot write until `EnsureSchema` upgrades it. The in-memory
repository checks that it holds no events and no snapshots.

Writers do not scan. A DynamoDB writer refuses a store that does not declare the feature with a
typed `StoreNotInitialized` error (Go `*StoreNotInitializedError`, `evt.ErrStoreNotInitialized`, Rust
`Error::StoreNotInitialized`) on every write path above, without scanning it and without writing
anything, because it cannot tell a fresh table from one written before stream heads without a scan.
So a DynamoDB writer's role needs no `dynamodb:Scan` on the event log, and only the initializing
role does. The error is neither a conflict nor transient. A DynamoDB writer may opt into lazy
initialization (Go `Repository.WithLazyInitialization(true)`, Rust
`DynamoRepository::with_lazy_initialization(true)`) for tests, local emulators and quickstarts. Its
first write to a store that does not declare the feature then initializes the store as above, and is
refused with `StreamHeadsNotMigrated` when the store is populated. Its `CompactBelow`, which never
declares, refuses with `StreamHeadsNotMigrated`. PostgreSQL and in-memory writers always initialize
lazily. Their check is two `EXISTS` probes (PostgreSQL, under the lock a declaration takes anyway,
needing no privilege a writer lacks) or an in-process check, and their `CompactBelow` refuses an
undeclared store with `StreamHeadsNotMigrated`. A writer's first commit
conditions on the version it validated or declared. A pure validation of a marker (Go
`FeatureMarker.Validate`) applies the same refusal but never writes. A writer that does not
implement this section refuses a table that declares `stream-heads`, by the existing rule. The
declaration is never removed once a writer has committed under it (the retraction above happens
before any commit), so a pre-heads build cannot be returned to. The migration tool declares a
populated store with `FeatureMarker.DeclareStreamHeads` (Go) after it has backfilled and verified
every head.

### Migration

Migrating a table written by v0.8 (streams with no head items) is stop-the-world: there is no
release in which old and new writers coexist, and it is one-way. The procedure, in order:

1. Stop writers and take a backup. Stop every v0.8 writer and start no head-aware writer.
   Enforce it: an IAM deny on `PutItem`, `UpdateItem`, `DeleteItem`, `BatchWriteItem`, and
   `TransactWriteItems` (which has no IAM action of its own: its items are authorized by the item-level
   actions, so deny `ConditionCheckItem` as well) for every principal except the migration role (an identity policy on each
   writer principal, a table resource policy, or a service control policy), held until step 6.
   DynamoDB cannot stop writes by capacity (provisioned mode has a positive minimum, on-demand has
   no writable-capacity setting). Take an on-demand backup or confirm point-in-time recovery.
2. Upgrade readers. Deploy the scanner and consumer changes above (scan and rebuild jobs,
   `evt-doctor`, every Streams, ESM, or Pipes consumer with the filter), before any head item
   exists. The backfill emits `sk = -1` stream records.
3. Backfill. `evt-doctor migrate-heads` refuses a table whose marker declares `journal` or any
   feature the tool does not model, and a store that holds a stream in a [reserved
   namespace](#reserved-namespaces) (such a stream must be renamed first. Head-aware code hides it, so
   the tool neither backfills around it nor declares over it, and checks again before declaring). It scans the table (an explicit migration scan, projecting `pk`,
   `sk`, `eventSeq`, `ttl`), accumulating per partition across the whole scan (a partition split by
   a page boundary is finalized when the scan ends). It ignores items whose `ttl` has passed but
   which are not yet deleted, and skips a partition with nothing left. For each remaining partition
   it computes the derived head and the maximum `ttl` across the partition, skips a partition
   whose derived head is 0 (`head ≥ 1`), and writes the head item with `attribute_not_exists(head)`.
   It is idempotent and resumable, supports `--dry-run`, and never lowers a head. A head item whose
   partition mixes items with and without a `ttl` is written with no `ttl`, because a head item
   that expired before an item that never does would leave that stream without one. Scans are
   strongly consistent.
4. Verify. `evt-doctor migrate-heads --verify` rescans and requires, for every partition with a
   non-expired item, a head item equal to the derived head (expired-but-undeleted items ignored as
   above), and exits non-zero otherwise.
5. Declare. After a clean verification in the same invocation, repeated immediately before the
   declaration, and with `--confirm-writers-stopped`, the tool declares `stream-heads: 1` by the
   ordinary declaration transaction, then verifies once more and reports drift. The step-1 deny is
   the evidence that writers stayed stopped. The tool cannot prove it.
6. Start the new writers, then lift the step-1 deny.

On PostgreSQL steps 3 to 5 are one transaction (see [PostgreSQL](#postgresql-head-table)). Writers are
stopped before it and started after it.

The operator procedure, with the commands, the verification and repair findings, and the rollback,
is the [migration runbook](../guide/migrating-to-stream-heads.md). `migrate-heads` is Go only (the Rust
crate has no doctor). Rust writers run against a migrated store like any head-aware writer.

A v0.8 writer that runs after the declaration leaves the head item stale: head-aware writers then
fail that stream with `StreamHeadDrift`, and a fence on it can pass although the stream moved. v0.8
writers are not supported once heads are declared. `--repair` fixes the heads. Rollback in place is
not supported: pre-heads builds refuse the table, and v0.8 unfiltered scans fail on head rows.
Restore the step-1 backup to return to the old layout. See the ADR.

### PostgreSQL head table

```sql
CREATE TABLE IF NOT EXISTS evt_events__evt_stream_heads (
    entity_id   text   PRIMARY KEY,
    entity_type text   NOT NULL,
    head        bigint NOT NULL CHECK (head >= 1)
);
```

The relation is `{events}__evt_stream_heads`, derived and validated like the other engine relations.
Under the per-entity advisory locks already taken (the same order, written and fenced streams) a
commit runs, for each written stream in ascending entity-ID byte order:

```sql
-- create (first sequence 1): must affect one row
INSERT INTO evt_events__evt_stream_heads (entity_id, entity_type, head)
VALUES ($1, $2, $3) ON CONFLICT (entity_id) DO NOTHING;

-- append (first sequence > 1): must affect one row
UPDATE evt_events__evt_stream_heads SET head = $3 WHERE entity_id = $1 AND head = $2;
```

A fence is one read:

```sql
SELECT head FROM evt_events__evt_stream_heads WHERE entity_id = $1;  -- absent is 0; must equal :head
```

A failure is classified by the same probe as DynamoDB, inside the transaction. To report the same
failure as DynamoDB, PostgreSQL pins its order and ranks before it reports:

1. the locks
2. the marker `SELECT`
3. the rebuild assertion
4. a probe for an existing outcome row for the command (an existing row is `OutcomeConflict`,
   ranking above drift and gap as on DynamoDB, and the final insert's `23505` still resolves a real
   race)
5. every head statement and fence read, evaluated without stopping at the first failure
6. the ranking (drift, gap, then conflicts)
7. the event inserts, snapshot upserts, and the outcome insert

 A snapshot write outside a commit checks `head >= :new` in its transaction.

The continuity query, the floor query, and the two fence queries of earlier drafts do not exist.
The snapshot upsert keeps its sequence-chain check. `entity_heads` reads the marker first: once `stream-heads`
is declared it reads this table, and until then it keeps the aggregate over events and snapshots,
because `EnsureSchema` creates the table empty on a populated v0.8 database and a head-aware
process would otherwise report no entities (Go and Rust alike). Steps 3 to 5 of the migration
are one transaction under the exclusive feature advisory lock: the per-stream maximum of `sequence`
and `event_sequence` over both tables (skipping a maximum of 0), inserted `ON CONFLICT DO NOTHING`.
A verification query that finds no stream whose row is missing or unequal to the derived head,
lower or higher (otherwise the transaction aborts, and `--repair` is the remedy). Then the `stream-heads` declaration. PostgreSQL's reads are transactionally
consistent, so none of the DynamoDB consistency rules apply there, and it has no TTL, Streams, or
scan jobs to upgrade.

## Journal

The journal (ADR 0005) is the first Rust-first extension: per-scope ordered, replayable
delivery rows written in the commit that wrote the events. A consumer reads a scope with
`high_watermark` and `page`. Only `photon-evt` with the `journal` cargo feature implements it. Go does
not (the parity matrix records it as deferred), and a Go writer refuses a table that declares it
([Feature marker](#feature-marker)). The fixtures are generated by the Rust implementation
(`compat/fixtures/journal.json`), and a Go port writes code until it passes them byte for byte.

A scope is a named, independently ordered sequence: 1 to 512 UTF-8 bytes without U+0000
(`world:7`, `world:7/place:3`). The engine treats it as opaque. An application maps each event of
the journaled entity types to zero or more scopes with a function of the event alone (the
`ScopeResolver`, which a closure may implement, returning the scopes or a `Result` of them. An error
fails the commit with `InvalidJournal` before anything is written). The event takes the next position in each of its scopes: a `u64` starting at
1, contiguous, with no hole when every commit succeeds. Positions are written as decimal numbers
in JSON. Read them as unsigned 64-bit integers.

### Allocations in event metadata

An event's positions are stored on the event, in its metadata extension `evt.journal` (a value
of [`extensions`](#metadata), so no metadata key is added and pre-journal readers ignore it): a JSON
array of `{"scope":…,"position":…}` objects, ascending by scope bytes, with no scope twice and no
position 0, encoded by the shared JSON rules.

```json
"extensions": { "evt.journal": "[{\"scope\":\"world:7\",\"position\":1},{\"scope\":\"world:7/place:3\",\"position\":1}]" }
```

This is what makes a rebuild independent of any commit order: every journal row and every counter
is a function of stored events alone. The resolver is not consulted again after the commit, so
changing it changes only where future events go. Keys beginning `evt.` are reserved: a journaled
commit replaces the `evt.journal` key of every event it writes (removing it from an event that
has no scope), so a caller cannot forge an allocation. A reader that finds the key malformed,
unsorted, or with a position 0 refuses the event (`InvalidJournal`) rather than guess.

The writer learns its allocations from the commit itself: a commit returns its events as stored
(the commit receipt, `Repository::commit_with_receipt` in Rust), `evt.journal` included, and the
store returns those events from every entry point that hands events back. The allocations are
those of the attempt that committed, after any contention retry, and equal what a `page` read of
each scope returns at those positions. A replayed outcome returns no events, so a caller that
needs a replayed command's positions reads the events its outcome lists. This is API behavior,
not a stored shape: nothing extra is written.

### Rows and counters

Both are ordinary [view rows](#views) in the repository's views table (string `pk` and `sk`, the
five view attributes, no `ttl`), written in the same transaction as the events.

| Row     | `pk`                       | `sk`                                | `entityID` (owner)       | `entityType`      | `payload`                              |
| ------- | -------------------------- | ----------------------------------- | ------------------------ | ----------------- | -------------------------------------- |
| journal | `journal#<scope>`          | the position, 20 digits, zero-padded | the event's stream       | `journal`         | `{"scope":…,"position":…,"event":<the stored event>}` |
| counter | `journal-counter#<scope>`  | `COUNTER`                           | `SYSTEM#JOURNAL`         | `journal-counter` | `{"scope":…,"position":…}`             |

A journal row's `payload` embeds the stored event exactly as a stream envelope's `detail`
([Serialized event](#serialized-event)), allocations included. Zero-padding to 20 digits makes
the sort-key order the numeric order for every `u64`. The counter holds the highest position
allocated in the scope: the scope's high watermark.

```json
{
  "pk": "journal#world:7",
  "sk": "00000000000000000001",
  "entityID": "acct-1",
  "entityType": "journal",
  "payload": "{\"scope\":\"world:7\",\"position\":1,\"event\":{\"id\":\"acct-1:1\",\"sequence\":1,…}}"
}
```

The full bytes of these items, of a commit's events, and of the marker are in
`compat/fixtures/journal.json`.

A repository that does not write view operations (`writes_views()` false: a custom backend that
predates them) is refused with `ViewsUnsupported` before anything is planned or declared, because
the rows would otherwise be dropped while the events and their allocations were written. Likewise,
a repository that does not declare that it applies the counter's compare-and-set
(`Repository::applies_expected_payload`, default false. True for the in-memory and DynamoDB
repositories, and for PostgreSQL with the [views table](#postgresql-views-table)) is refused with `ExpectedPayloadUnsupported`, so a backend that ignored the condition
cannot write a counter unconditionally.

Metadata seen by other projectors. The `evt.journal` allocation is added when the journal
commits, after the store has run the application's commit-wide projectors, so it exists on a stored
event and not on a live one. To keep a live commit and a replay of the stored events in agreement
(ADR-0012), the engine does not show `evt.journal` to any projector but the journal's own: a
projector's view of an event has the key removed, live and on replay
(`CommitProjector::engine_metadata`, default false).

Ownership. The journal rows are produced by a commit-wide, history-dependent projector
([Views](#views)) and obey every rule of it: each row names the stream that wrote its event as
owner, the row is written only if absent (`attribute_not_exists(pk)`, so a position is claimed
exactly once and a write by any other stream fails), and the owner never changes. The projector is
a pure function of its commit view: grouping stored events by commit and running it reproduces the
live rows.

The counters are the one exception, and a specified one. A counter is shared by every stream
that writes its scope, so no stream can own it, and the rule that a view operation's owner is a
stream the commit wrote does not apply. Its owner is the constant `SYSTEM#JOURNAL`, in the reserved
`SYSTEM#` namespace, which no stream can use ([Reserved namespaces](#reserved-namespaces)), so the
owner still never changes and the repository's owner condition (`attribute_not_exists(pk) OR
entityID = :owner`) passes for every writer. This leans on no repository checking that an
operation's owner is a stream: the engine's check (`InvalidViewOperation`) runs in the projector
pipeline, which the journal's counter operations do not go through. A counter write is a
compare-and-set on the counter the commit read: `attribute_not_exists(pk)` when it read none,
otherwise `entityID = :owner AND payload = :expected`, binding the exact payload it read (an
engine-only view condition, crate-private, so projectors cannot set it. PostgreSQL refuses it
until the [PostgreSQL views table](#postgresql-views-table) lands).
A commit allocates a scope's positions from the counter it read, so the rows it writes are the
positions above it. If any is taken, or the counter moved, the commit fails whole.
The rows' `absent` conditions alone are not enough once [compaction](#journal-compaction) deletes
rows: a writer whose read went stale could otherwise claim positions whose
rows are gone. A commit sets a counter only together
with the rows up to it, so a counter only moves up while the journal is written through commits.
It can fall out of step by other means (a rebuild running beside writers, a restore, a lost row of
the table), and the journal heals a counter that is behind its rows: a writer whose position
was taken, with no counter having moved since it read them, allocates from the highest row of
the scope (a strongly consistent descending `Query`, `Limit` 1) and writes the counter back.
Replays derive a counter as the maximum position any event holds in the scope, which is
order-independent. Because the counter is not an owned row, the engine's `ReplayViews` is not used
for it. `replay`/`rebuild` handle counters.

### The commit

A journaled commit is a commit with extra view operations, so every rule of [Writes](#writes)
holds. For every commit that writes at least one event of a journaled entity type, in order:

1. The journal reads the counter of each scope the commit's events map to (strongly consistent
   `GetItem`. An absent counter is 0).
2. It allocates: the events in the commit's canonical order (streams ascending by entity-ID
   bytes, each stream's events by sequence), each event taking the next position in each of its
   scopes, scopes ascending by bytes.
3. It writes the allocations into the events' metadata and guards every row's size (below),
   before anything is written. The staged commit is then validated the way the repository will
   (event shape, reserved entity IDs, duplicate streams, view-operation keys), so a commit the
   repository would refuse fails before the marker is touched.
4. It appends to the commit's view operations, after the operations of the commit's own
   projectors: the journal rows in event then scope order, then one counter put per touched scope,
   ascending by scope.

Each row and each counter is one projector operation of the commit's action budget
([Writes](#writes)). A single-stream commit holds at most 97 event and projector operations
(96 when it writes a snapshot), so with `e` journaled events, each in `s` scopes, the events,
the `e × s` rows, and one counter per distinct scope must fit: `e + e × s + (distinct scopes) ≤ 97`.
A commit over the budget fails with `CommitTooLarge` before any write, like any other.

Contention. If another commit took a position first, the row put fails its `absent` condition
(or, when the rows are gone, the counter put fails its compare-and-set), which the repository
reports as a projector-operation failure that carries the journal's own `PositionTaken` error (a failed condition on any other item ranks above it, per
[Views](#views)). The journal then re-reads the counters (from the highest row, when none moved:
see Ownership above), allocates again on the same events, and retries, waiting between attempts
([Fence-aware retry](#fence-aware-retry)'s policy: attempts, exponential backoff with jitter,
optional deadline. Five attempts by default). A transient failure (throttling, or two transactions
meeting on a shared counter item) is retried the same way and returned as is when attempts run out.
Nothing else is retried here: a conflict on the stream or a fence outranks the journal's own
failures, so a plain `Conflict` is never the journal's doing and goes to the caller to re-prepare,
as does a failed outcome put. When attempts run out on taken positions the journal returns a
`Conflict` (retryable by the caller, and by fence-aware retry). A commit whose outcome is unknown
(`Backend`, `Indeterminate`) is never retried here. A hot scope serializes its writers on the
scope's counter item: every commit that writes the scope puts it.

Size guard. A row's size is the byte length of its `payload`. Every row of the commit is
measured after allocation. If any exceeds the configured cap (default 30,000 bytes) the commit
fails before any write with `JournalRowTooLarge`, naming the widest offending row: its scope,
position, event ID, size, and the cap. The cap is at most 370,000 bytes (inside the 380,000-byte
single-item budget) and 30,000 by default. The same measure is exposed as a pre-check that
needs no counter: it measures each row at the widest position (`u64::MAX`, 20 digits). For the
events the commit will store, with the same metadata, a pre-check that passes means the guard
passes. A handler does not see the commit's metadata (principal, extensions, command-ID length), so
the pre-check is otherwise advisory, and a configurable headroom widens its measure. An
application calls it in its command handler and turns the error into its own recorded rejection
(`journal-row-too-large`, with the scope, event, size, and cap in `details`). A row the guard
refuses anyway fails the commit with `JournalRowTooLarge`, and a store with outcomes records that
error as the same `journal-row-too-large` rejection (an outcome-only commit, so a replay of the
command ID gets the same answer) instead of returning it as an internal failure.

### Reads

`high_watermark(scope)` returns the scope's counter (a strongly consistent `GetItem`, 0 for a scope
with none). `page(scope, after, limit)` returns the scope's rows with a position above `after`,
ascending, `limit` between 1 and 1000:

- The counter is read first, then the rows with a strongly consistent `Query`
  (`pk = :pk AND sk > :after`, `Limit`, following `LastEvaluatedKey` until the rows are read or the
  end). It asks for `limit + 1` rows: the extra one is not returned, but it raises the reported
  watermark, so a full page can show that rows follow it when the counter is missing or behind.
- The page keeps the contiguous prefix starting at `after + 1`. The first gap is reported as
  the inclusive range of missing positions `{from, to}`, and the page stops before it. A gap is a
  jump in the rows' positions, or, when the rows end before the counter says they should (and the
  page is not full), the missing tail up to the high watermark. A row beyond the counter that
  landed between the two reads raises the reported watermark to itself and is not a gap. A reader
  whose `after` is above the high watermark (a journal restored or rebuilt shorter than its
  cursor) gets an empty page flagged `cursor_ahead`, which is not caught up: it must resync.
- `next_after` is the last row's position (`after` for an empty page): a reader never moves past a
  gap. `has_more` is true for a gap-free page short of the watermark. A reader polls from the same
  `after` to wait for new rows.

A gap is data, not an error: the missing rows may be in flight on a lagging replica (a reader on
eventually consistent storage), or lost (a deleted row, an interrupted rebuild). The reader retries
and escalates when it persists. A lost counter does not hide rows: the watermark follows the rows
the page finds.

Wake-ups. A consumer learns that a scope has new rows from the views table's DynamoDB
stream, filtered to the journal's partitions: `pk` beginning `journal#` (one record per row) or
`journal-counter#` (one per scope per commit), `eventName` `INSERT` or `MODIFY`. The keys are
enough (`KEYS_ONLY`). A `MODIFY` of a counter with a new image also carries its position. A
record is a wake-up, not a delivery: stream order is per item, not per scope, so the consumer reads
the scope with `page` from its own cursor. Removals are not wake-ups, and neither are keys in those
partitions that the journal does not write (another sort key, an invalid scope): a decoder skips
them rather than failing the batch, and the page read reports a corrupt journal. `photon-evt-lambda` (feature
`journal`) implements the filter patterns and the decode. `compat/fixtures/lambda.json` pins them.

### Feature marker and history

The first journaled commit declares the journal on the marker row ([Feature marker](#feature-marker)):
`journal` at format version `1`, and every journaled entity type added to `historyDependent`, each
in a declaration transaction (one `version` bump), just before the commit is sent, and after the
commit has been built: the counters are read and the rows allocated and size-guarded first, so a
commit that cannot be built (no views table, an oversized row, a failing resolver) declares
nothing. Nothing is written if the row already declares them. A store the inner writer refuses as
uninitialized is refused before anything is declared. The wrapper reads the marker the declaration
would consult anyway, so a writer that fails a store that does not declare `stream-heads` (Go
`*StoreNotInitializedError`, Rust `Error::StoreNotInitialized`) has that refusal surface before the
declarations, and the refusal writes nothing. If the commit then fails because the store is
uninitialized or not migrated to stream heads, everything the attempt declared is taken back (one
declaration, best effort). That is the `journal` feature and the `historyDependent` entries the
attempt added, so the table is not left declaring an extension nothing was written for, which would
block `evt-doctor migrate-heads`, or forbidding compaction for types nothing ever journaled.
`historyDependent` makes `CompactBelow` refuse those types in every process:
the rows are rebuilt from the events, so the events are never compacted. A build without the
`journal` cargo feature models only `stream-heads`, so it refuses the table on its first commit,
snapshot write, or compaction (`UnsupportedFeature`), as does Go. A build that does model the
journal refuses a newer format version the same way. The marker cannot tell a journaling writer from
one that commits events some other way, so every writer of a journal table must commit through the
journal. An event written otherwise is missing from its scopes, with no gap to show it. The cargo
feature is also build-wide: any dependency that enables it makes every repository in the build
accept a journal table, whether or not it is wrapped. The same blind spot applies to events that
existed before the journal was enabled for their type, or that were compacted: they have no
allocation and no row, and nothing reports it. Enable the journal before writing the events it
covers.

`evt-doctor migrate-heads` refuses a table that declares `journal` ([Migration](#migration)), which
is consistent with the row above: a journal table is already head-aware (the journal requires
`stream-heads`) and holds rows the Go tool does not model.

### Rebuild

Every row and counter is derived from stored events: for each event, one row per allocation in its
metadata, and each scope's counter is the highest position any event holds. The derivation needs no
order and no commit grouping, so a rebuild reads the events of the journaled types in any order
(an enumeration or a scan), and is idempotent. It runs under the rebuild lock ([Rebuild
Fence](#rebuild-fence)): the worker takes a lease (`begin_rebuild`), writes the rows and the counters
as view puts with no `absent` condition through the guarded writer (`write_rebuild_views`, batches of
at most 99 operations, each asserting the lease's owner and fencing token), and releases the lease
(`end_rebuild`), which settles the generation. Before each batch the worker renews the lease
(`renew_rebuild`) once half of it has passed since it was taken or last renewed, so a rebuild that
outlasts its first lease is not taken over; a renewal that finds the lock gone (taken over or
force-released) stops the run before another write. While the lock is held every live commit,
journaled or not, fails with `RebuildInProgress`, so the unconditional rewrite of counters cannot
lower a counter under a live writer, and a worker that lost its lock writes nothing
(`RebuildLeaseLost`). Read the events after the lease is taken: a commit that lands between the
read and the lock keeps its rows (a rebuild does not delete), but the rebuild may write a counter
below them, which the next allocation heals from the highest row. Rust's `rebuild_with_lock`
takes the events already read, so it is for a table no one writes to, such as one whose commits a
force-release still refuses. A rebuild that fails once it attempted a write keeps the lock (its
rows may be half-written) until the lease lapses and a retry takes it over, or an operator
force-releases it. The projection rebuild can carry the journal in its own run
(`ProjectionRebuild::with_journal`, [Views](#views)), so one lease and one generation cover the
journal and the commit-wide views. One that fails before its first write releases the lock only if its begin
acquired it from a settled generation; a takeover of a lapsed lease, or an acquire after a
force-release, keeps it on any failure, as the projection rebuild does ([Views](#views)). A force-release does not let journaled
commits through: the failed rebuild may have cleared counters, and a commit that allocated from
them would stamp duplicate positions into immutable event metadata, so every commit is refused
with `RebuildInProgress` until a rebuild runs to its end ([Rebuild fence](#rebuild-fence)). It does not delete: wipe the journal
partitions first to rebuild from scratch. Two records holding one position of a scope never come from
this journal and fail the rebuild (`InvalidJournal`), whatever their order. Only an identical record
given twice is one row, so the result never depends on the order of the events.

Consumers. A page or watermark read while a rebuild rewrites rows would show missing rows or a
counter that is behind. A consumer of a table whose journal can be rebuilt reads under the reader
epoch check ([Rebuild epochs](#rebuild-epochs)): `page_at_epoch` and `high_watermark_at_epoch` observe the
generation, read, and verify it again, and fail with `RebuildUnavailable` (a rebuild holds the lock,
or a force-release left derived state untrustworthy) or `RebuildEpochChanged` (one started or
finished during the read). Both are transient: keep the cursor, back off, and read the same page
again. The engine's regroup-and-replay of the projector
(`GroupCommits` → `ReplayViews`) reproduces the rows (not the counters) from the same events.

### Journal compaction

Journal compaction (ADR 0005) deletes a scope's oldest rows, `1..=checkpoint`, after storing them as a
snapshot: a manifest and its chunks. The checkpoint becomes the scope's floor. A reader
whose cursor is below the floor gets a `410 Gone` handoff naming the snapshot, installs it, and pages
on from the checkpoint. Compaction is explicit (an operator or a scheduled job calls it), per scope,
and never runs in a command or read path. It never touches events: the journaled entity types are
history-dependent, so their events are never compacted, and every compacted row can always be
derived again.

Rows. Every compaction row is an ordinary [view row](#views) in the views table, in the scope's
compaction partition, owned by the engine (`SYSTEM#JOURNAL`, like the counters), with `entityType`
`journal-compaction`:

| `pk`                          | `sk`                            | Row      | `payload`                                                                                          |
| ----------------------------- | ------------------------------- | -------- | -------------------------------------------------------------------------------------------------- |
| `journal-compaction#<scope>`  | `LEASE`                         | lease    | held: `{"scope":…,"token":…,"owner":…,"leaseExpiresAt":…}`. Released: `{"scope":…,"token":…}`      |
| `journal-compaction#<scope>`  | `MANIFEST`                      | manifest | `{"scope":…,"checkpoint":…,"chunks":["<chunk digest>",…]}`                                         |
| `journal-compaction#<scope>`  | `chunk#<index, 20 digits>`      | chunk    | `{"scope":…,"index":…,"from":…,"through":…,"rows":[<journal row payload>,…]}`                      |
| `journal-compaction#<scope>`  | `audit#<checkpoint, 20 digits>` | audit    | `{"scope":…,"checkpoint":…,"digest":…,"chunks":…,"deleted":…,"owner":…,"token":…,"completedAt":…}` |

Payloads are encoded by the shared JSON rules, fields in the order shown. A chunk embeds each row's
`payload` (the row's encoding, the same bytes the journal stored for it), joined by `,`. A digest is the lowercase hex SHA-256 of a row's
`payload`: the manifest lists each chunk's digest by index, and the manifest's own digest identifies
the snapshot. The full items of a compaction are in `compat/fixtures/journal.json` (`compaction`):

```json
{
  "pk": "journal-compaction#world:7",
  "sk": "MANIFEST",
  "entityID": "SYSTEM#JOURNAL",
  "entityType": "journal-compaction",
  "payload": "{\"scope\":\"world:7\",\"checkpoint\":2,\"chunks\":[\"b3a9cd3bf2fa399307a8e530e6ba6ad8ee9145562577e0408b61cd6d1ca509f6\"]}"
}
```

Every compaction row is trusted only if it is the engine's: at its key, owned by
`SYSTEM#JOURNAL` (which no stream, and so no projector, can be), with `entityType`
`journal-compaction`. A row anything else wrote there is `ForeignJournalRow`, and compaction,
leases, and readers refuse it rather than act on it. The conditions of compaction's own writes
also require the engine owner (`entityID = :engine AND payload = :expected`). This defends against
projectors and stream-owned writes. Direct write access to the views table (a `ViewRepository`
put, which takes any owner) is trusted, as it is for the counters. A foreign manifest also fails
the scope's commits that read the floor (a new or repaired counter) until it is deleted.

Compaction rows are not projections of events and no rebuild writes them, but they hold no
domain state either: the manifest and chunks are a function of the stored rows and the checkpoint,
the lease is coordination, and the audit row is a log. Wiping them loses nothing a reader needs: a
rebuild then restores every row, and the scope reads as never compacted.

Canonical chunks. The rows `1..=checkpoint` are split into chunks from position 1, in order: a
chunk is closed before the row that would make it hold more than 500 rows or a `payload` over
375,000 bytes. Both limits are part of the format. A closed chunk depends only on the rows up to
the one that closed it, so compacting through 4 and then 10 stores the same manifest and chunks as
compacting through 10 at once: a later run resumes the manifest's last chunk and rewrites only it
and the chunks after it. The manifest is at most 375,000 bytes too (about 5,500 chunks, some 2.7
million rows): a run that cannot fit is refused by its preflight, before it writes anything
(`InvalidJournal`). Compact such a scope in smaller steps.

Lease. A scope has at most one compaction at a time. `begin_compaction(scope, owner, lease)`
reads the lease row and puts a held lease with the next token (1 for a scope with none), its
expiry the repository's clock plus `lease` in whole seconds, conditioned on the row it read (absent,
or its exact `payload`). An unexpired lease is refused (`CompactionLeaseHeld`, held up to and
including its expiry second). A lapsed one is taken over the same way. `renew_compaction` and
`end_compaction` (which writes the released payload, keeping the token) are conditioned on the
lease's exact payload. `force_release_compaction(scope, owner)` is the operator's: it releases the
named owner's lease whatever its token or expiry. A lease that no longer matches is
`CompactionLeaseLost`. The first acquire on a table declares `journal-compaction: 1` on the feature
marker, after validating the marker (a declared feature this build does not model is refused).

Writes. Every compaction write is one `TransactWriteItems` of up to 99 view actions followed by
a `ConditionCheck` on the rebuild generation item (events table) that it still holds the settled
epoch the run observed (`#value = :epoch`, or `attribute_not_exists(#value)` for epoch 0). A put
with an expectation is conditioned `attribute_not_exists(pk)` or `entityID = :engine AND payload =
:expected` (`:engine` binding `SYSTEM#JOURNAL`). A row delete
carries the view delete's owner condition (`attribute_not_exists(pk) OR entityID = :owner`, the
row's stream). Every write of a run also checks the lease row's exact payload, and the run stops
first if its lease has lapsed by the repository's clock. A run renews its lease in place (by the
lease's length) before a write when less than half of it is left. A failed epoch check is
`RebuildEpochChanged` (or `RebuildUnavailable`), a failed lease or manifest condition
`CompactionLeaseLost`. Nothing of that transaction is written. Throttling and transaction conflicts
are transient.

A run. `compact(lease, through)` with `floor ≤ through ≤ high watermark` and `through ≥ 1`
(otherwise `InvalidArgument`, before any write), under a settled rebuild epoch:

1. Build, if `through` is above the floor. A preflight first streams the whole range and
   writes nothing: it resumes the manifest's last chunk (checked against its digest), reads the
   rows above the floor up to `through` (strongly consistent), and chunks them, so a missing row
   anywhere in the range, or a manifest over its limit, is refused (`InvalidJournal`) before any
   write. A second pass then writes the chunks, each checked against the preflight's digest, so a
   run reads the range above the floor twice. The run keeps its lease during the preflight too.
   Each new chunk at a new index is written alone. It is unreferenced until the manifest swap.
2. Swap the manifest: put the new manifest, conditioned on the old one's exact payload (or
   absent), in the same transaction as the rewritten last chunk of the old manifest, if it changed.
   From here `through` is the floor.
3. Delete every journal row at or below `through` that is there, 98 per transaction.
4. Audit: put `audit#<through>` (overwriting a previous run's of the same checkpoint).

A run with `through` equal to the floor skips steps 1 and 2: it finishes an interrupted run, or
prunes rows a rebuild restored. Every step is idempotent and leaves the scope consistent, so a run
that stops for any reason is finished by compacting again. `compact_with_lease` takes a lease,
runs, and releases it (also after a failure). A crash between writing new chunks and the swap
leaves unreferenced chunks at indexes the next run overwrites. Compaction is maintenance with its
own transactions: no commit carries a compaction action, so the commit budget is unchanged
(97 event and projector operations, 96 with a snapshot).

Readers and `410 Gone`. Reading a compaction row takes the extension trait
`JournalCompactionStore` (`read_compaction_row`). `JournalStore` is unchanged from the first journal release. `page`,
`page_at_epoch`, `JournalRepository`, and every compaction function require the extension, so a
store that cannot read the floor fails to compile with them rather than skip the `410` check or
allocate below a floor (`high_watermark` needs only `JournalStore`). The in-memory, DynamoDB and
PostgreSQL (with its views table) repositories implement it. `page` is unchanged until it meets a gap. It then reads the manifest
(after the rows), and if the floor is above the page's last contiguous position (`next_after`) the
read fails with `JournalGone`: the scope, `after`, the snapshot's `checkpoint`, its chunk count, and
its manifest digest, and nothing of the deleted rows. An HTTP layer maps it to status 410. The
reader fetches the manifest (`read_manifest`) and each chunk (`read_chunk`, checked against the
manifest's digest. A chunk missing or not matching is the transient `JournalSnapshotMoved`: read the
manifest again), installs the rows, sets its cursor to `checkpoint`, and pages on. Because a run
swaps the manifest before it deletes a row, a reader that sees a deleted row always reads the floor
that explains it, so a compaction racing a reader never shows as a gap. Rows below the floor that
are still there are served as usual. The `JournalGone` vector is in the fixture (`compaction.gone`).

Allocation. A compacted scope's rows below the floor no longer guard their positions. Two rules
keep positions unique without adding an action to the commit:

- The counter put is a compare-and-set on the counter the commit read (Ownership above). A writer
  that read the counter before other commits and a compaction deleted their rows fails on the
  counter, re-reads it, and allocates again.
- A commit whose counter reads 0 (a new scope, or a lost counter), and every counter the journal
  repairs, allocates above the scope's floor too (one more strongly consistent read of the
  manifest), so a lost counter never reallocates a compacted position.

A counter lowered to a nonzero value below the floor by means outside the engine (a partial restore
of the views table) is not detected. As for the uncompacted journal, restore the views table whole, or rebuild it.

Rebuild. A rebuild restores compacted rows: it derives every row from the stored events and
does not read or write the compaction partition. The manifest stays, so the floor and the snapshot
stay valid (the restored rows are byte for byte the chunks' rows), and readers below the floor are
served the restored rows. Compacting again at the manifest's checkpoint prunes them. Compaction is
fenced against rebuilds through the epoch: `begin_compaction` and `compact` refuse an odd generation
(`RebuildUnavailable`), and a rebuild that begins during a run stops it at its next write. A wipe of
the views table removes the compaction rows with the journal. The rebuild then yields an
uncompacted journal.

Marker. A build that models `journal` but not `journal-compaction` refuses a compacted table: it
would read deleted rows as a gap and could allocate below the floor.

### Backends

DynamoDB (a views table), the in-memory repository, and PostgreSQL with its
[views table](#postgresql-views-table) (`with_views_table()`, [Journal on PostgreSQL](#journal-on-postgresql)).
A PostgreSQL repository with an application view writer cannot express the counter's
compare-and-set, so its journal reads are refused with `ViewsNotConfigured`.

## PostgreSQL

The schema is created by Go's `postgres.Repository.EnsureSchema` or Rust's
`PostgresRepository::ensure_schema`, which run the same idempotent DDL. Rust's also creates the
Rust-only [views table](#postgresql-views-table), which Go's does not. Table names default to
`evt_events` and `evt_snapshots` and can be changed in both implementations. The v0.9 auxiliary
relations derive from the configured events table name through a reserved infix
(`{events}__evt_command_outcomes`, `{events}__evt_features`, `{events}__evt_rebuild_lock`,
`{events}__evt_rebuild_generation`, `{events}__evt_stream_heads`, and the entity-type index
`{events}__evt_entity_type_idx`)
so multiple event logs in one database never share engine rows: equal command IDs in unrelated
logs do not collide, and one log's feature marker or rebuild lock never gates another log
(`evt_events` yields `evt_events__evt_command_outcomes`, `evt_events__evt_features`,
`evt_events__evt_rebuild_lock`, `evt_events__evt_rebuild_generation`,
`evt_events__evt_stream_heads`, and `evt_events__evt_entity_type_idx`). The infix is what keeps two logs apart: a configured base
name of `orders` derives only names containing `orders__evt_`, and because neither configured
table name may contain the infix `__evt_` (case-insensitively. Both implementations return a
validation error at construction otherwise), one log's events or snapshots table can never equal
another log's derived relation: the collision `orders` deriving `orders__evt_features` while a
second log configures `orders__evt_features` as its own events table is rejected outright. The
infix also renames the pre-v0.9 entity-type index, whose old `{events}_entity_type_idx` form
was collision-prone the same way. A schema upgraded from a pre-v0.9 release recreates the index
under the new name. Both implementations validate a derived name by the same rules as a
configured one. Names are interpolated unquoted, so both reject names that are not plain
identifiers or are PostgreSQL reserved keywords. Validated unquoted names are canonicalized to
lowercase before deriving engine advisory-lock keys, so differently cased handles share locks.
The snapshots table name is at most 58 bytes, leaving room for its `_pkey` index.
The configured events table name must be at
most 34 bytes (both implementations return a validation error at construction otherwise)
so every derived name fits PostgreSQL's 63-byte identifier limit without truncation. The longest
derived relation name, `{events}__evt_rebuild_generation_pkey`, adds 29 bytes to the base name
(`34 + 29 = 63`), ahead of `{events}__evt_rebuild_generation` (+24),
`{events}__evt_entity_type_idx` (+21), and `{events}__evt_stream_heads_pkey` (+23). Both also reject a pair of names where two of the
relations the schema creates (the seven tables, the index, and each table's `{table}_pkey`; the
[views table](#postgresql-views-table) adds its own) would
share a name after case folding, because `CREATE TABLE IF NOT EXISTS` would skip the second one.

```sql
CREATE TABLE IF NOT EXISTS evt_events (
    entity_id   text   NOT NULL,
    sequence    bigint NOT NULL,
    event_id    text   NOT NULL,
    event_type  text   NOT NULL,
    version     bigint NOT NULL,
    entity_type text   NOT NULL,
    payload     bytea  NOT NULL,
    metadata    jsonb  NOT NULL DEFAULT '{}'::jsonb,
    created_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (entity_id, sequence)
);
CREATE INDEX IF NOT EXISTS evt_events__evt_entity_type_idx ON evt_events (entity_type);

CREATE TABLE IF NOT EXISTS evt_snapshots (
    entity_id      text   PRIMARY KEY,
    entity_type    text   NOT NULL,
    sequence       bigint NOT NULL,
    event_sequence bigint NOT NULL,
    payload        bytea  NOT NULL,
    updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS evt_events__evt_command_outcomes (
    command_id text        PRIMARY KEY,
    status     text        NOT NULL CHECK (status IN ('accepted', 'rejected')),
    digest     text        NOT NULL,
    response   bytea,
    events     jsonb       NOT NULL DEFAULT '[]'::jsonb,
    rejection  jsonb,
    code       text,
    created_at timestamptz NOT NULL DEFAULT now(),
    CHECK ((status = 'rejected' AND rejection IS NOT NULL AND code IS NOT NULL)
           OR (status = 'accepted' AND rejection IS NULL AND code IS NULL))
);

CREATE TABLE IF NOT EXISTS evt_events__evt_features (
    id                integer PRIMARY KEY,
    version           bigint NOT NULL,
    features          text   NOT NULL,
    history_dependent text   NOT NULL DEFAULT '[]',
    retention         text   NOT NULL DEFAULT '[]'
);

CREATE TABLE IF NOT EXISTS evt_events__evt_rebuild_lock (
    id               integer PRIMARY KEY,
    owner            text        NOT NULL,
    generation       bigint      NOT NULL,
    lease_expires_at timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS evt_events__evt_rebuild_generation (
    id             integer PRIMARY KEY,
    value          bigint   NOT NULL,
    force_released boolean  NOT NULL DEFAULT false
);

CREATE TABLE IF NOT EXISTS evt_events__evt_stream_heads (
    entity_id   text   PRIMARY KEY,
    entity_type text   NOT NULL,
    head        bigint NOT NULL CHECK (head >= 1)

```

- Every transaction the engine opens (commits, out-of-band snapshot writes, compaction, the
  rebuild lifecycle and its guarded view writes, feature declarations, `EnsureSchema`, and the
  stream-head migration and repair writes) runs at `READ COMMITTED`, set explicitly whatever the
  server's or role's `default_transaction_isolation` (Go issues `SET TRANSACTION ISOLATION LEVEL
  READ COMMITTED` as the first statement, Rust starts it with `START TRANSACTION ISOLATION LEVEL
  READ COMMITTED`). The one exception is Go's read-only stream-head scans (`VerifyStreamHeads`
  and the dry runs of the migration and repair), which take no locks and want one consistent
  `REPEATABLE READ READ ONLY` snapshot. A Go `DB` that is itself an ambient transaction must
  already run at `READ COMMITTED`: PostgreSQL cannot change the level of a transaction under way,
  so the repository refuses to begin inside one at a stricter level.
  The fence reads below (the rebuild lock and generation, stream heads, the feature manifest) run
  after advisory-lock waits, and only `READ COMMITTED` takes each statement's snapshot after the
  wait: a `REPEATABLE READ` or `SERIALIZABLE` snapshot is taken at the transaction's first
  statement, so a commit that waited would not see a rebuild that began, or a commit that moved a
  fenced stream, while it waited. Single statements outside a transaction always see the latest
  committed rows.
- A commit is one transaction: the entity locks, the feature-marker `SELECT`, a probe for an
  existing outcome row, the head statements and fence reads ([Stream Heads](#postgresql-head-table)),
  one insert per event, projector statements, the snapshot upserts, then the outcome insert.
  Projector statements run after the events, so a writer that lost a race fails on its head
  statement (a conflict) before it reaches a view row. Commit-wide
  view operations execute inside the commit transaction in both languages in v0.9. evt
  defines no PostgreSQL view schema yet (applications own their view tables; the planned
  [views table](#postgresql-views-table) is the exception) so each repository is
  configured with a view writer that turns one view operation into one SQL statement (Go
  `postgres.Repository.WithViewWriter`, Rust `PostgresRepository::with_view_writer`), and a
  repository without one refuses a commit that carries view operations with `ViewsNotConfigured`.
  The engine executes the statement the writer returns, in the pinned order, and decides whether
  the operation's condition held: an `absent` put must raise a unique violation (`23505`) of the
  table's `(pk, sk)` key constraint when the row exists, which is the failed condition, and the
  writer names that constraint with the statement (Go `ViewStatement.KeyConstraint`, Rust
  `PgStatement::with_key_constraint`. An `absent` put without one is `InvalidViewOperation`). A
  unique violation of any other constraint of the table says nothing about the requested row, so
  it is an ordinary failure of the statement, with the SQLSTATE as its reason. Because the owner never changes, the
  writer must enforce it in SQL, and the engine reads the outcome from the affected-row count: a put
  without `absent` is an upsert guarded by the owner, whose count is zero when another stream owns
  the row. A `present` delete deletes the owner's row, and a count of zero fails the condition. A
  delete without a condition reports the rows of another owner instead of the rows it deleted (a
  count above zero fails the condition). The engine hands the writer the owner with the operation. A projector statement that the database rejects is a projector
  operation failure (a lost connection is a backend error), and so is an integrity violation
  raised at `COMMIT`, which only a deferred constraint on a projector's table can cause (it
  names no operation: Go `*evt.ProjectorError`, Rust `Error::Projector`).
- A failed head statement is an optimistic-concurrency conflict (or drift or a gap, by the
  [failure-path probe](#failure-classification)). In Go, conflicts are `evt.ConflictError`s wrapped in a
  transient `policy.ClassifiedError`, so the fence-aware retry loop retries them as it does on
  DynamoDB. An event insert that finds its sequence already stored, after the stream's head
  statement passed, is an event above the head: `StreamHeadDrift`. In Rust, a serialization failure
  (`40001`) or deadlock (`40P01`), raised by any statement in the commit (head statement,
  projector, insert, or snapshot upsert), is `Error::Transient` and is retried.
- Commits and out-of-band snapshot writes first take a per-entity transaction lock,
  `SELECT pg_advisory_xact_lock(1702261760, hashtext($1))` with the entity ID. Both languages run
  this exact statement, so a snapshot write cannot interleave with a commit of the same stream. A multi-stream commit locks every stream in its read set, written and fenced, once
  each, in ascending entity-ID byte order (the bytewise order that also pins the transaction
  layout, never a locale collation). Byte order is a total order over the IDs, so two commits
  that lock overlapping sets always acquire the shared streams in the same sequence and cannot
  wait on each other in a cycle. The one cycle the order cannot exclude runs through two
  distinct IDs whose `hashtext` values collide, which share one advisory lock. PostgreSQL's
  deadlock detector aborts one of the transactions (`40P01`), which Rust retries as
  `Error::Transient` and Go returns as the database error.
- The head table makes the floor a consequence of the head condition: a snapshot's `event_sequence`
  never exceeds the head (H3), so a commit that starts at `head + 1` starts above it.
- Each commit snapshot checks the snapshot sequence chain, as the DynamoDB snapshot put's
  condition does ([Writes](#writes)). Under the entity's advisory lock, just before its upsert, the
  commit reads the stored row's sequence with `SELECT sequence FROM evt_snapshots WHERE entity_id =
  $1` (both languages run this statement). With no row, the snapshot's sequence must be 1. With a
  row, it must be the stored sequence plus one. Otherwise the commit fails as an
  optimistic-concurrency conflict and the transaction rolls back, so nothing is written: Go returns
  an `evt.ConflictError` wrapped in a transient `policy.ClassifiedError` (the fence-aware retry
  loop retries it), and Rust returns `Error::Conflict`. The check runs after the view statements,
  so a failed view statement is reported first ([Known differences](#known-differences)). A
  racing writer usually fails earlier, on its head statement. The check still catches a commit
  built from a stale snapshot sequence, such as a Go context loaded before a catch-up snapshot
  ([Snapshot policy](#snapshot-policy)), exactly as DynamoDB and the in-memory repositories do.
- The snapshot upsert only replaces a snapshot whose `event_sequence` is lower or equal
  (`ON CONFLICT (entity_id) DO UPDATE … WHERE EXCLUDED.event_sequence >= evt_snapshots.event_sequence`).
  In a commit the sequence check above has already passed. The `WHERE` keeps an out-of-band
  snapshot write (which checks no sequence) monotonic.
- `metadata` is `jsonb`, which normalizes whitespace and key order. Compare it as JSON, not bytes.
  `payload` is `bytea` and keeps its exact bytes.
- Entity heads read the head table once the store declares `stream-heads`. Until then they take
  `MAX` over event sequences and snapshot event sequences per entity, because `EnsureSchema`
  creates the head table empty on a populated database ([Stream Heads](#postgresql-head-table)).

v0.9 rows. The DynamoDB items of [Command outcomes](#command-outcomes),
[Feature marker](#feature-marker), and [Rebuild fence](#rebuild-fence) are PostgreSQL rows:

- `{events}__evt_command_outcomes` holds one row per command (`command_id` is the command ID without
  the `command-outcome#` prefix). `digest` and `code` are text as on DynamoDB. `response` is
  `bytea`, the same raw bytes whose base64 the DynamoDB item stores. `events` is a `jsonb` array
  of event IDs (the same array, in the same stream-ID-then-sequence order) and `rejection` a
  `jsonb` object with keys `code`, `message`, `details`. Compare both as JSON, not bytes. The
  `CHECK` constraints mirror the once-in-final-state rule. The outcome insert is a plain `INSERT`
  into the commit transaction. A unique violation (`23505`) on the outcomes table means another
  writer recorded the outcome first: the commit is ambiguous, and the caller recovers by
  re-reading the row by command ID ([Ambiguous-write recovery](#ambiguous-write-recovery)). The
  outcome insert runs last, after the snapshot upserts.
- `{events}__evt_features` holds exactly one row, `id = 0`. `features` is the canonical JSON object
  text (feature name → format version) byte-identical to the DynamoDB `features` attribute, and
  `history_dependent` and `retention` hold the same sorted JSON-array text as the DynamoDB
  `historyDependent` and `retention` attributes. The
  commit-time check is a `SELECT` of
  `version` in the commit transaction: mandatory in every v0.9 commit, as on DynamoDB,
  including the no-marker case. A row whose `version` differs from the cached one, or a row that
  appeared after the writer validated an empty table, fails the check: the writer re-validates
  the feature set, then retries, as on DynamoDB
  ([Writes](#writes)). Declarations take the
  exclusive advisory lock below for their short read-modify-write. Commit-time checks take the
  shared lock, so a declaration cannot slip between a writer's check and its commit.
- `{events}__evt_rebuild_lock` (`id = 0`) and `{events}__evt_rebuild_generation` (`id = 0`) mirror the lock
  and generation items. `lease_expires_at` is `timestamptz` rather than epoch seconds, and
  `force_released` mirrors the generation item's `forceReleased` flag.

Advisory locks. The per-entity commit lock stays `pg_advisory_xact_lock(1702261760,
hashtext($1))`, keyed by the entity ID alone: two event logs in one database that share an entity
ID merely serialize each other's commits on it, which is safe. The engine-row locks derive from
the configured events table name, so two logs never block each other's engine rows: class key
`1702261761`, with the second key `hashtext('{events}:features')` for the feature marker and
`hashtext('{events}:rebuild')` for the rebuild fence. (`{events}` is the configured events table
name.)

- A multi-stream commit takes the per-entity lock for every stream in its read set (written
  and fenced) in the order pinned above (ascending entity-ID bytes, each ID once), then runs
  the head statements and fence reads below, then the inserts. A concurrent writer blocks on the
  lock instead of moving a stream past a fenced read.
- Fence reads (v0.9, ADR 0007) run inside the commit transaction after the locks:

  ```sql
  SELECT head FROM evt_events__evt_stream_heads WHERE entity_id = $1;   -- absent is 0; must equal :head
  ```

  An equality, not an upper bound: the head only increases, so a value that matches cannot have
  been reached by a different history, including after compaction. PostgreSQL cannot lock the
  absent row of a stream with no events (`SELECT … FOR KEY SHARE` locks only rows that were
  actually returned), so the advisory lock plus this read are the fence.

- Rebuild fence (v0.9): the durable `{events}__evt_rebuild_lock` row and the generation
  row fence commits, as the DynamoDB lock item does. After taking the shared advisory lock, every
  commit asserts the generation is settled (no lock row, and an even generation) in the same
  order as the DynamoDB transaction (the feature-marker `SELECT` first, then the refusals that
  need only the manifest (a fence on a retained type) then this assertion. DynamoDB makes those
  refusals before it sends the transaction):

  ```sql
  SELECT EXISTS (SELECT 1 FROM evt_events__evt_rebuild_lock WHERE id = 0)
      OR EXISTS (SELECT 1 FROM evt_events__evt_rebuild_generation WHERE id = 0 AND value % 2 <> 0);
  -- true (a lock row, including an expired one, or an odd generation) refuses the commit
  ```

  A commit that finds either fails its check with `RebuildInProgress` ([Writes](#writes)),
  retryable once a rebuild ends: a crashed rebuild keeps blocking commits, and so does one an
  operator force-released, same as DynamoDB. PostgreSQL keeps no force-released lock row (a
  force-release deletes the row). The commit reads the generation instead, which costs no
  action budget there. The shared lock
  (`pg_advisory_xact_lock_shared(1702261761, hashtext('{events}:rebuild'))`, taken after the
  entity locks, the marker check, and the refusals that need only the manifest, held to `COMMIT`) makes the assertion safe without serializing commits against each other: acquire,
  takeover, and release take the exclusive lock
  (`pg_advisory_xact_lock(1702261761, hashtext('{events}:rebuild'))`) for their short
  transactions only, so no acquire or release can slip between a commit's assertion and its
  `COMMIT`. Acquire, takeover, release, and force-release are each one transaction with the same
  two statements as the DynamoDB transaction: the conditional lock insert, update, or delete
  (fresh acquire asserts absence (accepting the odd generation only when `force_released` is
  set, as on DynamoDB) takeover asserts `owner = :observedOwner AND lease_expires_at < :now`.
  release and force-release assert the owner) and the conditional generation bump
  (`attribute_not_exists(value) OR value = :seenEven OR (value = :seenOdd AND force_released)`
  to acquire, with the same `:increment` as on DynamoDB (one from an absent or even generation,
  two from a force-released odd one)
  `SET value = value + :two` against `value = :seenOdd` to take over,
  `SET value = value + :one REMOVE force_released` (cleared) against `value = :seenOdd` to
  release, and `SET value = value + :two, force_released = true` against `value = :seenOdd` to
  force-release, keeping the generation's parity and flag semantics exactly as pinned in
  [Rebuild fence](#rebuild-fence)). A takeover moves odd to odd (changed), so readers pinned to
  the old epoch re-read. A force-release leaves the generation odd with the flag set, so commits
  stay refused and readers stay fenced until a later rebuild completes and releases. While it
  replays, the rebuild's view writes are transactions that each take the lock row `FOR UPDATE`
  and assert `owner = :me AND generation = :generation AND lease_expires_at > :now` in the same
  transaction, so a worker that
  lost the lock to a takeover blocks on it, then aborts instead of writing: the transactional
  equivalent of the DynamoDB per-batch `ConditionCheck`
  ([Rebuild fence](#rebuild-fence)).

  The lifecycle operations ([Rebuild lifecycle API](#rebuild-lifecycle-api)) run in one
  transaction each, under the exclusive advisory lock, and read the state inside it, so a
  conditional statement that matches no row means a writer outside the protocol moved the rows: the
  attempt rolls back and `Begin` decides again, at most eight times, then fails with the transient
  `RebuildConflict` (release and force-release report `RebuildLeaseLost`). Leases are stored as
  `timestamptz` and compared as whole epoch seconds (the same seconds the DynamoDB item stores)
  by converting both sides in SQL:

  ```sql
  -- acquire (the lock row; a unique violation means a lock row appeared since the read: read again)
  INSERT INTO evt_events__evt_rebuild_lock (id, owner, generation, lease_expires_at)
  VALUES (0, $1, $3, to_timestamp($2::bigint::double precision));   -- $3 = the generation after the bump
  -- acquire (the generation; zero rows affected: the state moved, read again)
  INSERT INTO evt_events__evt_rebuild_generation (id, value, force_released)
  VALUES (0, $1, false)
  ON CONFLICT (id) DO UPDATE SET value = evt_events__evt_rebuild_generation.value + $1
  WHERE evt_events__evt_rebuild_generation.value = $2
     OR (evt_events__evt_rebuild_generation.value = $3
         AND evt_events__evt_rebuild_generation.force_released);   -- $1 = :increment, $2 = :seenEven, $3 = :seenOdd
  -- takeover
  UPDATE evt_events__evt_rebuild_lock
  SET owner = $1, generation = $5, lease_expires_at = to_timestamp($2::bigint::double precision)
  WHERE id = 0 AND owner = $3
    AND lease_expires_at < to_timestamp($4::bigint::double precision);
  UPDATE evt_events__evt_rebuild_generation SET value = value + 2 WHERE id = 0 AND value = $1;
  -- renew
  UPDATE evt_events__evt_rebuild_lock
  SET lease_expires_at = to_timestamp($2::bigint::double precision)
  WHERE id = 0 AND owner = $1 AND generation = $3;
  -- release (bound to the lease: $2 is its fencing generation; the generation row must still hold it)
  DELETE FROM evt_events__evt_rebuild_lock WHERE id = 0 AND owner = $1 AND generation = $2;
  UPDATE evt_events__evt_rebuild_generation
  SET value = value + 1, force_released = false WHERE id = 0 AND value = $1;
  -- force-release
  DELETE FROM evt_events__evt_rebuild_lock WHERE id = 0 AND owner = $1;
  UPDATE evt_events__evt_rebuild_generation
  SET value = value + 2, force_released = true WHERE id = 0 AND value = $1;
  -- reads
  SELECT value, force_released FROM evt_events__evt_rebuild_generation WHERE id = 0;
  SELECT owner, generation, EXTRACT(EPOCH FROM lease_expires_at)::bigint
  FROM evt_events__evt_rebuild_lock WHERE id = 0;
  ```

  The acquire's `:seenEven`/`:seenOdd` take the same values as the table above (`-1` for the
  branch that does not apply). A generation row exists once the first rebuild begins. A store
  whose schema predates the rebuild fence has neither relation: a commit's assertion treats the
  missing lock relation as no lock (nobody can have taken it), and the lifecycle operations fail
  until `EnsureSchema` has created them.

- Feature marker: declarations take
  `pg_advisory_xact_lock(1702261761, hashtext('{events}:features'))` (exclusive) around the
  read-modify-write of `{events}__evt_features`. Commit-time checks take
  `pg_advisory_xact_lock_shared(1702261761, hashtext('{events}:features'))`, which is why the
  check-then-commit race above cannot happen: the commit holds the shared lock to `COMMIT`, and a
  declaration's exclusive lock waits for every commit holding the shared lock. Commits do not
  serialize against each other.

### PostgreSQL views table

[ADR 0008](../adr/0008-postgresql-views-table-and-journal.md), `photon-evt` 0.3, Rust only.
Implemented: the table and its DDL, the view repository (`PgViewRepository`), the commit target
(`with_views_table()`) with the expected-payload condition, and the `postgres-views` marker
feature. The conformance suites of commit-wide views, the expected payload, the view repository and
the rebuild run on it.

`ensure_schema` creates one more derived relation, the views table, and two indexes:

```sql
CREATE TABLE IF NOT EXISTS evt_events__evt_views (
    pk          text COLLATE "C" NOT NULL,
    sk          text COLLATE "C" NOT NULL,
    entity_id   text   NOT NULL,
    entity_type text   NOT NULL,
    payload     text   NOT NULL,
    ttl         bigint NOT NULL DEFAULT 0,
    PRIMARY KEY (pk, sk)
);
CREATE INDEX IF NOT EXISTS evt_events__evt_views_type_idx
    ON evt_events__evt_views (entity_type, pk, sk);
CREATE INDEX IF NOT EXISTS evt_events__evt_views_ttl_idx
    ON evt_events__evt_views (ttl) WHERE ttl > 0;
```

- The relations derive from the configured events table name like the others, and the name rules
  above apply to them: the table (`{events}__evt_views`, +11 bytes), its key
  (`{events}__evt_views_pkey`, +16), and the indexes (`{events}__evt_views_type_idx`, +20, and
  `{events}__evt_views_ttl_idx`, +19) stay under the 29 bytes the 34-byte limit leaves, and all four
  join the set of relations checked for a case-folded collision.
- The database encoding must be `UTF8`: the byte order and the exact-bytes rule below hold only for
  UTF-8 text. `ensure_schema` creates the table on any encoding, so a store that never uses its
  views is unaffected; the view repository and `with_views_table()` check
  `current_setting('server_encoding')` once, on first use, and refuse any other encoding
  (`InvalidConfig`).
- Each column is the [view item](#views) attribute of the same name: `entity_id` is `entityID`
  (the owner), `entity_type` is `entityType`, and `ttl` is the item's `ttl` in epoch seconds, `0`
  when the item has none. An empty `sk` is stored as `VIEW`, as on DynamoDB.
- `pk` and `sk` collate as `"C"`, so the primary key orders by UTF-8 bytes, which is DynamoDB's
  sort-key order. Every `ORDER BY` below relies on it.
- `payload` is `text`, not `jsonb`, and keeps its exact bytes (`jsonb` normalizes whitespace and
  key order). The [journal](#journal) digests and the expected-payload condition compare payload
  bytes, so normalization would break both.
- Key size. A btree index entry holds at most 2,704 bytes, less than DynamoDB's 2,048-byte `pk`
  plus 1,024-byte `sk`. A row whose `entity_type`, `pk` and `sk` together exceed 2,600 UTF-8 bytes
  is refused before any write: `InvalidArgument` from the view repository, `ViewKeyTooLong` on the
  commit path (see [Known differences](#known-differences)).

View repository (`PgViewRepository`, `photon_evt::ViewRepository`), outside the commit path:

| Operation | Statement |
| --- | --- |
| put | `INSERT … ON CONFLICT (pk, sk) DO UPDATE SET entity_id = EXCLUDED.entity_id, entity_type = EXCLUDED.entity_type, payload = EXCLUDED.payload, ttl = EXCLUDED.ttl`: no condition, no owner check |
| delete | `DELETE … WHERE pk = $1 AND sk = $2`: no condition |
| get | `SELECT … WHERE pk = $1 AND sk = $2` |
| list by partition | `SELECT … WHERE pk = $1 AND sk > $2 ORDER BY sk LIMIT $3` (no `sk` bound on the first page) |
| list by entity type | `SELECT … WHERE entity_type = $1 AND (pk, sk) > ($2, $3) ORDER BY pk, sk LIMIT $4` (no key bound on the first page) |

- A batch of writes is one transaction. A repeated `(pk, sk)` keeps its last row, as in Rust on
  DynamoDB, and the rows are written in `(pk, sk)` byte order, so two batches over the same keys
  lock them in the same order and cannot deadlock. A batch is atomic here (DynamoDB's
  `BatchWriteItem` is not), which the contract allows. A serialization failure or deadlock
  (`40001`, `40P01`) of any view statement is `Error::Transient`.
- Every read sees every committed transaction, including lists by entity type (DynamoDB's index
  is eventually consistent). A page without a limit holds at most 1,000 rows.
- The cursor is the last row's keys as a JSON object, keys sorted and escaped like every other Go
  JSON, in padded base64url: `pk` and `sk` for a partition list, plus `entityType` for an
  entity-type list, the same shape DynamoDB's `LastEvaluatedKey` produces. A full page returns a
  cursor even when no row follows, as on DynamoDB, and an empty cursor is the first page. A cursor
  with the wrong keys, or one that continues another partition or entity type, is
  `InvalidArgument`.
- TTL. Readers return a row whose `ttl` has passed, as DynamoDB does until its sweep deletes it.
  `PgViewRepository::purge_expired(now)` deletes them through the partial index, a batch at a time:
  `DELETE … WHERE (pk, sk) IN (SELECT pk, sk FROM … WHERE ttl > 0 AND ttl <= $1 ORDER BY ttl LIMIT 1000) AND ttl > 0 AND ttl <= $1`,
  repeated until a batch deletes nothing. The outer condition repeats the expiry because the
  subquery picks keys from its snapshot: a row a concurrent write renewed (a new `ttl`, or none)
  while the delete waited on it is re-checked against the committed row and kept. An operator or a
  scheduled job runs it. Journal rows,
  counters and compaction rows carry no `ttl`, so it never touches them.

Commit target. `PostgresRepository::with_views_table()` makes the views table the target of a
commit's view operations, in place of an application view writer (`with_view_writer`; a
repository has one or the other). The engine builds each statement itself, under the same
contract as a view writer's ([PostgreSQL](#postgresql)), and every put replaces the whole row as
DynamoDB's `Put` replaces the item (`ttl` included, `0` when the operation sets none):

- an `absent` put is a plain `INSERT` whose unique violation (`23505`) of
  `{events}__evt_views_pkey` is the failed condition;
- any other put is the owner-guarded upsert
  (`… DO UPDATE SET … WHERE evt_events__evt_views.entity_id = EXCLUDED.entity_id`, zero rows when
  another stream owns the row);
- a `present` delete deletes the owner's row (`… AND entity_id = $owner`) and fails on zero rows;
- an unconditional delete deletes the owner's row and fails when the row belongs to another owner.

Each statement is sized in the commit budget as the DynamoDB item it mirrors would be (its
attribute names and values), not by its SQL text, so `CommitTooLarge` fires at the same commit on
both backends.

With the views table, and only with it, the repository applies the engine's expected-payload
condition (`applies_expected_payload()` is true). An operation that expects the payload it read is:

```sql
-- the commit read no row: claim it
INSERT INTO evt_events__evt_views (pk, sk, entity_id, entity_type, payload, ttl)
VALUES ($1, $2, $3, $4, $5, 0);                         -- 23505 on the key: the condition failed
-- the commit read a row: replace exactly that row
UPDATE evt_events__evt_views
SET entity_type = $4, payload = $5, ttl = 0
WHERE pk = $1 AND sk = $2 AND entity_id = $3 AND payload = $6;   -- zero rows: the condition failed
```

A failed condition is a projector operation failure, ranked as on DynamoDB ([Views](#views)). An
application view writer still refuses the condition (`InvalidViewOperation`).

Isolation. Commits, compaction batches and rebuild view writes on a repository with the views table
run at `READ COMMITTED`, like every engine transaction ([PostgreSQL](#postgresql)), whatever the
server's default: a `REPEATABLE READ` snapshot, taken at the first statement, would read a rebuild
generation or a counter from before the lock. Under `READ COMMITTED` an `UPDATE` that waits on a row
a concurrent commit is changing re-checks its `WHERE` against the committed row, so two commits
that read the same counter cannot both pass: the second matches zero rows.

Rebuild view writes (`write_rebuild_views`) use the commit target's statements without the
`absent` and `present` conditions, owner guard included, so a rebuild row whose key another owner
holds fails with `ConditionalCheckFailed` as it does on DynamoDB. Rebuild deletes are the
unconditional delete above. Both run under the lock-row guard of the
[rebuild fence](#postgresql).

Feature marker. A repository configured `with_views_table()` declares the feature `postgres-views`
(format version 1) before its first commit or rebuild write, outside that transaction (the
declaration takes the exclusive marker lock), once per handle and its clones, after checking the
database is `UTF8`. It then requires the feature: a store that stops declaring it (an operator
removed it) fails the commit as `Error::Transient`, and the retry declares it again. A writer that
does not support it refuses the store with `UnsupportedFeature`, as for any unknown feature
([Feature marker](#feature-marker)): a Go writer and a Rust repository that uses `with_view_writer`
or no view target cannot write a store whose views live in `{events}__evt_views`, so commit-wide
rows never split across two tables.

### Journal on PostgreSQL

[ADR 0008](../adr/0008-postgresql-views-table-and-journal.md), `photon-evt` 0.3, on a repository
configured `with_views_table()`. Implemented: the journal's commits, its reads and its compaction,
with the shared journal, journal-rebuild and compaction conformance suites on PostgreSQL. Planned:
the wake-ups below. The [journal](#journal) and its [compaction](#journal-compaction) are specified
backend-neutrally above. This section pins the PostgreSQL statements.

Rows. Journal rows, counters and compaction rows are rows of `{events}__evt_views`, column for
attribute, with the same keys, owners, entity types and payload bytes as the DynamoDB items, so
`compat/fixtures/journal.json` pins both backends.

Commits. The journal's row puts and counter puts are view operations of the commit, so they run as
the commit target's statements above: each row is an `absent` insert, and each counter is the
expected-payload operation. A failed row insert or counter update is the journal's
`PositionTaken`, retried as on DynamoDB ([The commit](#the-commit)), and a serialization failure
or deadlock (`40001`, `40P01`) is `Error::Transient`.

Reads (`JournalStore`, `JournalCompactionStore`), each one statement, each seeing every committed
transaction:

```sql
-- read_counter / read_counters
SELECT pk, payload FROM evt_events__evt_views WHERE pk = ANY($1) AND sk = 'COUNTER';
-- read_last_position
SELECT sk FROM evt_events__evt_views WHERE pk = $1 ORDER BY sk DESC LIMIT 1;
-- read_rows ($2: `after` as 20 zero-padded digits)
SELECT pk, sk, entity_id, entity_type, payload, ttl FROM evt_events__evt_views
WHERE pk = $1 AND sk > $2 ORDER BY sk LIMIT $3;
-- read_compaction_row
SELECT pk, sk, entity_id, entity_type, payload, ttl FROM evt_events__evt_views
WHERE pk = $1 AND sk = $2;
```

Compaction writes (`CompactionStore::write_compaction`, 1 to 99 writes to distinct keys) are one
`READ COMMITTED` transaction:

1. With an `epoch`: take the shared rebuild advisory lock
   (`pg_advisory_xact_lock_shared(1702261761, hashtext('{events}:rebuild'))`) and read the
   generation. Unless it is the epoch's, roll back: `EpochChanged`.
2. Lock the rows the batch names, in one order every batch uses: the scope's `LEASE` row first,
   then the rest in ascending `(pk, sk)` byte order:
   `SELECT entity_id, payload FROM evt_events__evt_views WHERE pk = $1 AND sk = $2 FOR UPDATE`.
   Payloads that are not UTF-8, written or expected, are refused (`InvalidArgument`) before any of
   this, as on DynamoDB.
3. Check every write's condition against what step 2 read: `Any` passes, `Absent` needs no row, and
   `Payload(bytes)` needs a row owned by `SYSTEM#JOURNAL` whose payload is exactly those bytes.
   Then apply the writes in step 2's order, each guarded again in its own statement:
   - a put with `Absent` is a plain `INSERT` (a violation of `{events}__evt_views_pkey` fails it);
   - any other put is an upsert of the whole row;
   - a delete is `DELETE … WHERE pk = $1 AND sk = $2 AND entity_id = $owner`, which a row absent
     at step 2 passes.
4. A failed condition, at step 3's check or in a statement, rolls everything back:
   `Refused(i)`, where `i` is the first failing write in request order, as the in-memory and
   DynamoDB stores report it. A serialization failure or deadlock is `Error::Transient`.
   Otherwise `COMMIT`.

`FOR UPDATE` cannot lock an absent row, so two batches that find the same key absent could both
pass step 2. The protocol keeps that from mattering: every batch of a scope either puts the
scope's `LEASE` row with `Absent` (the first acquire, a plain insert, which two racing acquirers
cannot both make) or checks it by payload (a row that step 2 locks first), so batches of one scope
serialize on their lease row before they read any other key. A `Check` with `Absent` on any other key has no `23505` backstop and
relies on that serialization alone. Compaction takes no lock a commit waits on (it never writes
counters, and it takes the shared rebuild lock before anything else), so the two cannot deadlock.
A commit that re-inserts a deleted position below the floor still fails on its counter.

Wake-ups. After its view statements, a commit that wrote journal rows runs, once per distinct
scope in ascending byte order:

```sql
SELECT pg_notify('evt_events__evt_journal', $1);   -- $1: the scope itself, not its journal# pk
```

- The channel is the canonical (lowercase) events table name with `__evt_journal` (+13 bytes).
  The payload is the scope, at most 512 bytes (`MAX_SCOPE_BYTES`), well under `NOTIFY`'s 8,000.
- PostgreSQL delivers a transaction's notifications at `COMMIT`, in commit order, and drops them on
  rollback, so a wake-up never names a write that did not happen. A notification writes nothing
  and is not counted in the commit's action budget.
- A listener (`JournalListener`) holds one connection with `LISTEN` on the channel and yields
  scope wake-ups. A wake-up is not a delivery: the consumer pages the scope from its own cursor,
  exactly as with a DynamoDB stream record (Wake-ups, under the journal's Reads above).
- Notifications sent while a listener is disconnected are lost. The listener reports every
  (re)connect, and the consumer then pages each scope it follows, and again on a polling interval
  (default 30 seconds), as a backstop.
- Compaction and rebuild do not notify. A compaction moves no reader's position, and a rebuild
  changes the generation, which a reader detects on its next read.
- `with_wakeups(false)` turns the notifications off for a deployment that only polls.

## Stream envelope

The stream envelope is the cross-language wire format. Go ships no publisher for it, so a
consumer that publishes onward wraps each committed event in the EventBridge-style envelope itself. Go decodes the envelope with
`projectors.StreamRecordFromEnvelope`. Rust encodes the same bytes
(`photon_evt::wire::envelope::encode`) and decodes both SNS messages and raw-delivery SQS bodies
(`decode`).

```json
{"version":"","id":"acct-1:1","detail-type":"account:opened","source":"evt-compat","account":"","time":"0001-01-01T00:00:00Z","region":"","resources":null,"detail":{...serialized event...}}
```

Message attributes, all strings:

| Attribute       | When                                              |
| --------------- | ------------------------------------------------- |
| `entityType`    | always                                            |
| `eventType`     | always                                            |
| `commandId`     | metadata has a non-empty command ID               |
| `traceparent`   | the trace carrier has a non-empty `traceparent`   |
| `correlationId` | the command ID if present, else the `traceparent` |

Decoding rejects an envelope whose event has no entity ID or event ID.

## Snapshot policy

A store snapshots when a commit reaches or crosses the next multiple of the snapshot interval
(Go `evt.CalculateAdditionalEvents`, Rust `photon_evt::snapshot_events_due`):

```text
next = interval - (current_sequence mod interval)
snapshot if interval > 0 and events_in_commit >= next
```

- The snapshot always covers the whole commit: its `eventSequence` is the commit's last event.
- Its sequence is the previous snapshot sequence plus one (1 for the first).
- The default interval is 5 in both implementations. An interval of 0 disables snapshots.
- An entity type can override the store's interval: Go `snapshots.Store.WithSnapshotSize(type, n)`,
  Rust `Aggregate::SNAPSHOT_INTERVAL`. The override applies wherever the type is committed,
  transactions included. Rust's `Some(0)` disables snapshots for the type; Go has no per-type
  disable (a non-positive size removes the override).

For example, with interval 3, a 6-event commit at sequence 1 snapshots at event 7, and a 1-event
commit at sequence 7 does not snapshot because the next boundary is 9.

### Oversized snapshots

A snapshot is one item, never chunked, so the aggregate's state must stay bounded: keep unbounded
history (every reaction an aggregate has seen, say) in events, not in state. A state that outgrows
the per-item budget would otherwise make every commit that reaches the interval fail with
`CommitTooLarge` ([Writes](#writes)), however small its events, bricking the stream.

So a store measures each snapshot before it stages it, and leaves out one that does not fit:

- The measure is the snapshot item's preflight size (the same estimate the commit budget uses)
  plus a `ttl` attribute at its widest, 22 bytes (the name and the 19 digits of the largest
  int64), whether or not the type is retained: Go `evt.SnapshotCommitSize`, Rust
  `photon_evt::snapshot_commit_size`.
- A snapshot whose measure is over 380,000 bytes (Go `evt.MaxCommitItemBytes`, Rust
  `photon_evt::MAX_COMMIT_ITEM_BYTES`) is not written. The commit proceeds without it, as a commit
  that does not reach the interval would: the stored snapshot stays, the loaded or executed
  state keeps its snapshot sequence, and the next commit that reaches the interval tries again,
  with the same sequence. The store logs the skip as a warning (Go `slog`, Rust `tracing`).
- The rule applies wherever the engine writes a snapshot: commands, transactions (each written
  stream), outcome commits, and catch-up snapshots on load. It is the same on every backend,
  PostgreSQL included, whose rows have no such limit, so a stream's snapshots do not depend on
  where it is stored.

Loads of such a stream replay every event after the last snapshot that fit, and compaction cannot
move past it, so the skip is a safety net, not a mode to run in. A repository commit built by hand
(`CommitWithSnapshot`, `Commit::with_snapshot`) is not measured: an oversized snapshot there still
fails with `CommitTooLarge`. An out-of-band `PutSnapshot` / `put_snapshot` is not budgeted, and
DynamoDB refuses an item over 400 KB.

A store can also write a catch-up snapshot on load (Go `WithCatchUpSnapshotThreshold`, Rust
`Store::with_catch_up_snapshot_threshold`, both off by default). When a load replays at least the
threshold of events after the snapshot (every event, without one), it writes the folded state as a
standalone snapshot: sequence the loaded snapshot sequence plus one, `eventSequence` the loaded
head. It uses the monotonic standalone snapshot write, so it never lowers a stored snapshot, and a
failed write is logged and does not fail the load. Rust's loaded state then carries the new snapshot
sequence, so a commit from it writes the next one. Go's loaded context keeps the old sequence, so
on every backend a commit from the same load that also snapshots conflicts on the snapshot
sequence and is retried.

## Loading and duplicate commands

A store loads an entity from its snapshot plus events after the snapshot's `eventSequence`, or from
every event when there is no snapshot. An entity with no events loads at sequence 0.

Loaded events must continue the sequence without a gap: the first event after a snapshot is its
`eventSequence` plus one, and a stream without a snapshot starts at 1. A gap means another writer
snapshotted and compacted the stream between the snapshot read and the event read, or events
expired. Applying events across the gap would build the wrong state. Rust's `Store::load` reads the
stream again, up to three times, then returns `Error::Conflict`. Go's `snapshots.Store.LoadAggregate`
returns a conflict error at once, because it has already modified the entity the caller passed in.
The error is a `policy.ClassifiedError` with class `transient`, so the fence-aware retry
loop retries it with a fresh entity, and `evt.IsConflictErr` still matches it. A gap that does not heal,
such as a prefix that DynamoDB TTL expired under `WithRetention`, fails every load. Before this
check, such a stream loaded with the wrong state.

Like any read, a load can be one compaction behind. If another writer snapshots and compacts the
stream during the load, the event read can stop short without a gap: it is empty when the new
snapshot is exactly at the head, and a paginated DynamoDB query can return a contiguous first page
before the later events are deleted. The load then returns an older state. That state was real when
it was read, so this is ordinary staleness, not a wrong state. Neither language reads the snapshot
again to detect it, which would cost a read on every load. A commit from the stale load starts at or
below the new snapshot's `eventSequence`, so its head condition (`head = first − 1`) fails, which is
a conflict, and the retry policies reload and run the command again.

A command whose metadata carries a command ID already recorded by an event replayed since the
latest snapshot is a duplicate and writes nothing. Command IDs folded into a snapshot are no
longer checked, so the dedupe window is the events after the snapshot.

In v0.9 this window is superseded by [Command outcomes](#command-outcomes): the durable
`command-outcome#` row checks every command ID globally, including IDs folded into snapshots. The
window remains as a cheap pre-check on load, and on an upgraded log it is what still catches
older duplicates: pre-v0.9 events carry command IDs but no outcome rows, so the load-time check
is retained for them.

That retention is a known upgrade limitation, documented here rather than papered over with a
backfill: no tool materializes outcome rows for pre-v0.9 commands. IDs already folded into a
snapshot at upgrade bypass the new global check immediately, and IDs still visible as events
after the latest snapshot keep only the load-time window: once those events fold into a snapshot
and compact, their IDs are no longer checked at all. A duplicate of a pre-v0.9 command beyond the
latest snapshot is therefore not detected. The once-per-command-ID guarantee applies to
commands executed after outcomes are enabled.

## Upcasting

Upcasters migrate stored events from older payload versions when they are read. They run in
declaration order, each once, and each sees the output of the ones before it. Stored events are
never rewritten. A failed upcast or decode fails the load.

## Compaction

`CompactBelow(entity, through)` (Go `evt.Compactor`, Rust `Repository::compact_below`):

- Deletes events with sequence in `[1, through]`, only when the stored snapshot covers them
  (`snapshot.eventSequence >= through`). Otherwise it deletes nothing and returns the
  compaction-uncovered error.
- Never deletes the snapshot. `through < 1` is a no-op. It is idempotent.
- On DynamoDB, the snapshot read and the key query are strongly consistent even when the repository
  is configured for eventually consistent reads, so compaction cannot miss recent events.
- A compacted stream must be loaded or rebuilt from its snapshot, never by replaying from sequence 1.
- Compaction may delete the stream's head event (when `through` equals the snapshot's
  `eventSequence`). The snapshot's `eventSequence` is then the stream's head, and commits continue
  from it ([Continuity](#continuity)).
- A commit whose first event is at or below the snapshot's `eventSequence` is a conflict on every
  backend (its head condition `head = first − 1` fails), so a writer that loaded before compaction
  cannot recreate compacted events. Compaction itself never writes or deletes the head item.

See [ADR 0001](../adr/0001-event-compaction-and-snapshot-truncation.md).

## Known differences

These differences are deliberate and covered by tests. Keep them documented here.

- U+0000 in PostgreSQL view rows ([PostgreSQL views table](#postgresql-views-table)). PostgreSQL
  `text` cannot hold it, so the view repository refuses it in a key, owner, entity type or payload
  with `InvalidArgument`, where DynamoDB and the in-memory repository store it.
- View key size on PostgreSQL ([PostgreSQL views table](#postgresql-views-table)). A btree index
  entry holds at most 2,704 bytes, so the views table refuses a row whose `entity_type`, `pk` and
  `sk` together exceed 2,600 UTF-8 bytes (`InvalidArgument` from the view repository), which
  DynamoDB would accept up to its 2,048-byte `pk` and 1,024-byte `sk`. Real keys are far shorter.
- `null` payloads. Go keeps a JSON `null` payload as a nil `[]byte` and re-encodes it as
  `null`. Rust decodes it to empty bytes and writes `""`. Only hand-built JSON can contain a `null`
  payload. Neither store writes one.
- Event versions. Rust refuses to decode a stored event whose version, after upcasting, is not
  the version its type declares (`PayloadError::VersionMismatch`). Go decodes it into the current
  struct. Deploy readers before writers when an event version changes.
- Floats. Not normalized across languages, as described under [JSON encoding](#json-encoding).
- Duplicate-command window. Both languages only see command IDs in events after the latest
  snapshot. This is shared behavior, listed here because it surprises readers. The `dedupe-window`
  scenario covers it. Superseded in v0.9 by command outcomes
  ([Command outcomes](#command-outcomes)). The window remains as a load-time pre-check, and on an
  upgraded log it is the only guard for pre-v0.9 command IDs, which have no outcome rows: a
  pre-v0.9 duplicate beyond the latest snapshot is not detected (a documented upgrade limitation,
  no backfill).
- Resetting between attempts. Go resets the entity the caller supplied to its original value
  before each re-preparation (a deep copy of its exported fields) and, for an entity that is not a
  pointer to a struct, attempts the command once and returns a conflict as an error. Rust loads a
  fresh aggregate for every attempt. Neither is observable in the stored data.
- Drift found at insert time (PostgreSQL). DynamoDB reports "the head update passed and an event
  put failed" from the cancellation reasons, so it ranks that drift with the rest. PostgreSQL pins
  its statement order (head statements, then ranking, then event inserts) and has no reason to read
  the events before the inserts, so it finds the same drift when an insert reports a stored
  sequence. In a multi-stream commit where another stream also fails its head statement as a gap or
  conflict, PostgreSQL reports that failure instead of the drift. A single stream, and every drift
  the probe finds, rank identically on every backend.
- Snapshot conflicts against view operations (PostgreSQL). PostgreSQL runs its view statements
  before the snapshot upserts, as the order above pins. A stale snapshot sequence, which DynamoDB
  and the in-memory repository rank as a conflict ahead of any projector operation, is therefore
  reported on PostgreSQL only if no view statement failed first. Head, gap, drift, fence, and outcome
  failures rank identically on every backend.
- Projector kind declaration. Go's `CommitProjector.History()` is a required method. Rust's
  `CommitProjector::history()` defaults to empty, a current-state projector. In both, a projector
  that declares no history is given no events and no commit ID, so a Rust projector that forgets
  the declaration sees an empty `events` list and an empty commit ID rather than reading undeclared
  history.
- Row ownership on PostgreSQL. DynamoDB and the in-memory repository evaluate the owner
  condition themselves. PostgreSQL cannot see the application's table, so the application's view
  writer enforces it in SQL, and the engine reads the outcome from the affected-row count (above).
  A writer that ignores the owner commits a handoff that the other backends refuse. The same
  conformance suite exercises the rule against the writer it is given.
- View-writing capability. Go's `ViewWritingRepository.WritesViews()` returns a bool and
  Rust's `Repository::writes_views()` does too, so a decorator reports the capability of the
  repository it wraps instead of claiming it unconditionally.
- Projector operation errors. Go's `*evt.ProjectorOperationError` exposes the operation's
  mapped error (`Err`) and the backend's cause (`Cause`), both matchable with `errors.Is`. Rust's
  `Error::ProjectorOperation` exposes them as `mapped()` and `cause()`, and its `source()` is the
  mapped error when there is one, else the cause. The fields that name the projector and the
  operation, and the reasons, are the same.
- PostgreSQL metadata. Stored as `jsonb`, so its bytes differ from the encoded JSON. Compare it
  as JSON.
- View repository. PostgreSQL has no view repository in either language: evt
  defines no view schema there, and the application's view writer is its only access (above). Go's
  streaming iterators (`ViewStreamer`) are not ported. Rust pages with a cursor. Rust refuses a
  cursor with no `pk` and `sk` string, or one that belongs to another partition or entity type,
  with `Error::InvalidArgument`, where Go forwards it to DynamoDB. The in-memory repository
  returns a cursor only when a row follows the page (DynamoDB returns one for every full bounded
  page). A Rust typed view decodes with serde, so a JSON `null` does not decode into a struct (Go
  leaves it zero) and field names match exactly (Go matches case-insensitively). Use
  `#[serde(default)]`.

- The journal. Rust only. Go does not implement it, records it as deferred in the parity
  matrix, and refuses a table that declares `journal` (a Go writer fails its first commit after the
  declaration. `evt-doctor migrate-heads` refuses such a table). The journal's fixtures are
  generated by Rust, the reverse of the core fixtures. Its counters are view rows with a constant
  engine owner rather than an owning stream ([Journal](#rows-and-counters)). The Rust PostgreSQL
  repository does not support it.

## Compat scenarios

The head item changed the recorded action order of `multi-stream` and `read-fences` (the
fixtures regenerate from the Go implementation) and added two scenarios, `stream-heads-snapshot-guard`
and `stream-heads-drift`. The harness grew the ops they need: `putSnapshot` (an out-of-band snapshot
write) and `appendRawBypassingHead` (an event appended with no head update). The remaining ADR 0007
scenarios (`stream-heads-migration`, `stream-heads-compaction`) are not in the shared scenarios: the
migration tool is Go only and covered by the Go live suites. See
[ADR 0007](../adr/0007-per-stream-head-item.md#migration-and-compatibility).

The v0.9 core reshape extends `compat/scenarios.json` with the interleaved Go/Rust
scenarios below. Go generates the core golden fixtures for them
(`go -C go test ./internal/compat -run TestFixtures -update`), Rust must reproduce them byte for byte,
and the live interleaved runs (`scripts/compat-integration.sh dynamo|postgres`) execute the same
steps on real backends. Both conformance suites (Go's with the fixtures, Rust's with the live runs)
implement every scenario in this list. The names are the shared keys
in `compat/scenarios.json`. The `metadata-extensions` case is implemented with metadata extensions
in the current single-stream harness, and it does not enable outcomes. `commit-wide-views` and
`commit-wide-projector` are implemented with commit-wide projectors. The `outcomes-*` scenarios,
`reserved-namespaces`, and `fence-aware-retry` are implemented with command outcomes and rejections:
they set `"outcomes": true`, so both writers run them on
stores with outcomes enabled and a command ID on every step, and the fixtures pin each stored
outcome row and the `TransactWriteItems` request order of every step. The other scenarios are
unchanged. The harness grew the ops and fields the outcomes scenarios need (`resolveOutcome`, an
outcome-only commit, and `injectCommitFault`, which makes a commit apply (or drop) while the
caller observes an indeterminate error, so `outcomes-ambiguous` exercises the real ambiguous path
rather than only the re-read branches). The commit-wide projector scenarios add `projectors` on
transaction steps and a shared commit-wide projector on the account domain. `rebuild-fence` adds the
`rebuild` op below. The other v0.9 scenarios add `readLatest` (`latest-n`), `enumerate` and an
`entityPrefix` that puts a write in a reserved namespace (`reserved-namespaces`), `repeat` on a view
operation and `pad` on an event payload (`commit-too-large`), `executeTransaction`, a multi-stream
command under fence-aware retry with an `interfere` that moves a stream before its first commits
(`fence-aware-retry`), `groupCommits` (`commit-grouping`), and `declare`, one declaration on the
feature marker (`feature-marker`). [`compat/README.md`](https://github.com/photon-grove/evt/blob/main/compat/README.md) holds the op
table. The harness scopes command IDs to the run and scenario, because outcome rows are global to
the table, and uses a digest that replaces the run name in the target stream IDs, so a command
digests the same in every run and the committed digests hold against live backends.
`compat/fixtures/outcomes.json` pins the digest vectors (canonical bytes and digest) and the
encodings of the outcome rows (DynamoDB item, its budgeted size, PostgreSQL row).

The `rebuild` op. A `rebuild` step names an `action` and an `owner`, and runs the
lifecycle call on the step's writer. The harness scopes an owner token to the run and scenario
(`compat-<run>-<scenario>-<owner>`), like a command ID, and the table's lock and generation are
global to the table, so a step asserts the generation as a delta against the generation it
read at the start of the step, never an absolute value. Actions: `begin` (with `leaseSeconds`),
`renew` (with `leaseSeconds`), `end`, `forceRelease` (the owner it releases), `generation` (a
reader's observe), `writeViews` (one guarded batch writing one view row scoped to the run, with
`owner`), and `wait` (with `seconds`: the live runs sleep, and the fixture runs advance the
injected clock). The expectation's `result` is `ok`, `held` (`RebuildLockHeld`), `leaseLost`
(`RebuildLeaseLost`), `settled` or `unavailable` (the reader's observe), and an `execute` or
`transaction` step while the generation is unsettled (a rebuild holds the lock, or a force-release
left it odd) expects `rebuildInProgress`. `delta` is the generation after
the step minus the generation before it, and `forceReleased` the flag after it. A scenario holds the
lock across its steps, which would refuse every other scenario's commits, so it is marked
`exclusive` (the interleaved run skips it and the live script runs it alone afterwards) and ends
with the table settled.

A declaration changes the manifest of the whole table: an unsupported feature refuses every other
scenario's commits, and an entity type in a durable set refuses their fences or compaction. So the
`feature-marker` scenario is `exclusive`, like `rebuild-fence`, and the refusals the durable sets
drive run there rather than in `read-fences` (the retention refusal) or `commit-grouping` (the
historyDependent compaction refusal). Its retention type is scoped to the run (`retained-{id}`), and
it retracts every declaration it makes. A failed run is settled by the Go driver's `settle`, which
also retracts the compat declarations a failed step left behind. Each live step runs in a fresh
process, so the other language validates the manifest anew; the refusal of a writer whose cached
validation predates a declaration is in both conformance suites (Go's `RunFeatureMarkerSuite`,
Rust's `feature_marker_cases`).

A fenced-and-written stream emits no fence checks. The fixture pins every fenced transaction's action order (fence checks after the written streams' groups). A fence on a stream whose type is in the manifest's durable `retention` set is refused with `RetentionConflict`: including by a writer that configured no retention itself (in the exclusive `feature-marker` scenario).                                                                                |
| `fence-aware-retry`    | read fences, fence-aware retry | Classification is per failing item: a head-update or event-put failure in a commit that also carries caller-stamped fences still re-prepares and succeeds. A failed caller-stamped fence produces the persisted `stale-fence` rejection at once, without preparing again, whose only remedy is a new command ID: the old ID replays the rejection. An engine-filled conflict re-prepares and only the committing attempt writes. Exhausted attempts persist the `retries exhausted` rejection, which replays identically. A command whose write set changes between attempts keeps one identity. Each case is executed by one language and replayed by the other. Both languages also run these cases in their conformance suites on every backend. The fixtures pin the outcome rows, every request of every attempt (including the interfering writer's), the rejection bytes, the rename digest, and the policy defaults. |
| `metadata-extensions`  | metadata extensions | `principalId`, `causationId`, and `extensions` round-trip in both directions, including the defaults: `causationId` written as the command ID when unset, `extensions` written as `{}`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `commit-grouping`      | metadata extensions, commit-wide projectors | A multi-stream commit's events carry one `commitId` across all its streams. A rebuild of a history-dependent projector replays every commit grouped by `commitId`, each group's events in the pinned (stream ID, sequence) order, and pre-v0.9 events without `commitId` replay as single-event commits. A rebuild of a current-state projector never replays (it loads every aggregate's final state and derives the complete row set through the state entry point, producing the same rows over a compacted prefix as over a full log. `CompactBelow` refuses an entity type in the durable `historyDependent` set) including from a process that never registered the projector. The scenario pins the grouping (`groupCommits`); the compaction refusal runs in the exclusive `feature-marker` scenario, and the state entry point's rebuild joins it when the rebuild ports ship the entry point. |
| `commit-wide-views`    | commit-wide projectors | Multi-stream transactions carry projector operations: puts at a `pk` outside `{entityType}#{entityId}`, deletes, and conditioned operations. The fixture pins each transaction's action order (the marker check, the projector operations in declaration then emission order, then the written streams' groups) and the final view rows, which the other language reads. A failed condition is a projector operation failure in both languages, names the projector and the operation, and writes no event. A `pk` over 2,048 or an `sk` over 1,024 UTF-8 bytes fails with `ViewKeyTooLong`, a repeated `(pk, sk)` with `DuplicateViewKey`, and operations with no event with the projector-only refusal, all before any write. |
| `commit-wide-projector` | commit-wide projectors | The shared account domain registers a commit-wide projector on its stores. Commands executed by either language, alone and in a multi-stream transaction, produce byte-identical view rows from the same commit view (the events and the state each stream had after the commit), including a rejection that carries events. |
| `latest-n`             | latest(n) | With more than `n` events on a stream, both languages read the last `n` events newest-first, excluding the snapshot item, and after compaction only the events that remain.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `feature-marker`       | feature marker | A declaration bumps `version`. The other language's cached version fails its condition and revalidates. A bump of a feature's format version fails the older writer the same way. A writer that does not support a declared `(name, formatVersion)` pair refuses to commit, and so does a commit by either language after the `stream-heads` format is bumped to 2. Adding or removing an entity type from `historyDependent` or `retention` bumps `version` the same way, and the refusals those sets drive hold across independently configured instances.                                                                                                                                                                                                                           |
| `stream-heads-snapshot-guard` | stream heads | An out-of-band snapshot never covers more than its stream's head: a snapshot ahead of the head, or on a stream with no head item, is refused as `StreamHeadDrift` in either language and writes nothing, so the stream stays writable. A snapshot at or below the head is written, a regressing one is a silent no-op, and a snapshot of an empty stream (event sequence 0) needs no head item. |
| `stream-heads-drift`   | stream heads | An event appended with no head update (`appendRawBypassingHead`) leaves the head behind the log: every later write to the stream, in either language, fails with `StreamHeadDrift`: from a command, from a transaction, and from a fence on the stream. Drift is never retried, never exhausted into a `stale-fence` rejection, records no outcome, and writes nothing. |
| `rebuild-fence`        | rebuild fence | While one language holds `SYSTEM#REBUILD`, the other's commit fails with `RebuildInProgress` and writes nothing, and the other's `Begin` is `RebuildLockHeld`. `End` bumps the generation by one to the settled value and commits resume. A takeover of an expired lease bumps it by two while it stays odd, and the displaced worker's guarded view write is `RebuildLeaseLost` and writes no row. The reader epoch check sees odd and changed generations in the other language. A force-release ends the lease and leaves the generation odd with `forceReleased` set, so commits stay refused with `RebuildInProgress` and readers stay fenced, until a later `Begin` (bumping by two) and `End` (bumping by one) settle it and clear the flag, and the refused command then commits. The fixtures pin the exact requests of every lifecycle transaction and the lock-check action in every commit's action order. |
| `reserved-namespaces`  | reserved namespaces | A commit or transaction whose entity ID begins with `SYSTEM#` or `command-outcome#` is refused before any write, and so is an out-of-band `PutSnapshot` with a reserved ID. Enumeration and heads skip the engine rows (the outcome rows) either language wrote.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Changing the format

The format changes only on purpose. A change must:

1. Update the Go implementation and regenerate the fixtures:
   `go -C go test ./internal/compat -run TestFixtures -update`.
2. Update the Rust implementation until `cargo test --workspace` passes against the new fixtures.
3. Pass the live cross-language suite on both backends (`scripts/compat-integration.sh`).
4. Keep older stored data readable: add upcasters for changed event payloads and fixture coverage
   for the old shape.
5. Update this document and `docs/internal/behavioral-invariants.md`.
